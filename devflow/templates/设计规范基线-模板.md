## 1. 命名规范

### 1.1 数据库命名

| 规范项 | 规则 | 示例 |
|-------|------|------|
| 表命名 | `snake_case, t_<domain>_<entity>` | `t_order_main`, `t_user_profile` |
| 字段命名 | `snake_case, 主键 id, 审计字段 created_at/updated_by` | `order_no`, `user_name`, `created_at` |
| 索引命名 | `idx_<table>_<columns>` | `idx_order_user_id`, `idx_user_email` |
| 外键命名 | `fk_<table>_<ref_table>` | `fk_order_user`, `fk_detail_order` |

### 1.2 API 命名

| 规范项 | 规则 | 示例 |
|-------|------|------|
| 字段命名 | `camelCase` / `snake_case` | `orderNo`, `userName` / `order_no`, `user_name` |
| 枚举命名 | `UPPER_SNAKE_CASE` | `ORDER_STATUS`, `USER_ROLE` |
| 布尔字段 | `is_*` / `has_*` 前缀 | `isActive`, `hasPermission` |

### 1.3 命名转换规则 (v3.27.16 新增)

**缩写词处理策略**：

| 策略 | 说明 | 示例 |
|------|------|------|
| `preserve_case` | 保留原大小写 | `user_id` → `userID`, `url_path` → `urlPath` |
| `first_capital` | 仅首字母大写 | `user_id` → `userId`, `url_path` → `urlPath` |
| `all_lowercase` | 全部小写 | `user_id` → `userid`, `url_path` → `urlpath` |

**常见缩写词**：ID, URL, API, HTTP, JSON, XML, HTML, CSS, SQL, UUID, URI

**转换示例**（基于选定策略）：

| snake_case | camelCase (preserve_case) | camelCase (first_capital) |
|------------|---------------------------|---------------------------|
| `user_id` | `userID` | `userId` |
| `api_key` | `apiKey` | `apiKey` |
| `url_path` | `urlPath` | `urlPath` |
| `xml_parser` | `xmlParser` | `xmlParser` |

> **说明**：本规范一旦冻结，P2 详设必须统一使用选定的转换策略。不一致的转换会导致 Linter 报错。

## 2. API 设计规范

### 2.1 基本约定

| 规范项 | 规则 |
|-------|------|
| API 风格 | RESTful / RPC / GraphQL / 混合 |
| 路由规范 | `/api/v1/<resource>` 或 `/api/v1/<domain>/<resource>` |
| 版本策略 | URL 路径 / 请求头 |
| HTTP 方法 | GET 查询，POST 创建，PUT 全量更新，PATCH 部分更新，DELETE 删除 |

### 2.2 响应包装

**是否强制包装**：是 / 否

**包装结构**：
```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": "2024-01-01T00:00:00Z"
}
```

**错误响应**：
```json
{
  "code": 400,
  "message": "参数错误",
  "errors": [
    {"field": "email", "message": "邮箱格式不正确"}
  ],
  "timestamp": "2024-01-01T00:00:00Z"
}
```

### 2.3 分页规范

| 规范项 | 规则 |
|-------|------|
| 分页方式 | offset-limit / page-size / cursor |
| 请求参数 | `offset=0&limit=20` / `page=1&pageSize=20` |
| 响应结构 | `{total, items}` / `{hasMore, nextCursor, items}` |

## 4. 错误处理规范

### 4.1 错误处理模式

**模式**：`Result<T>` / 异常+全局处理器 / 错误码

**示例**：
```java
// Result<T> 模式
public Result<User> getUser(Long id) {
    if (!exists(id)) {
        return Result.error("USER_NOT_FOUND", "用户不存在");
    }
    return Result.success(user);
}

// 异常模式
public User getUser(Long id) throws BusinessException {
    if (!exists(id)) {
        throw new BusinessException("USER_NOT_FOUND", "用户不存在");
    }
    return user;
}
```

### 4.2 错误码规范

| 规范项 | 规则 | 示例 |
|-------|------|------|
| 错误码格式 | `ERR-<MODULE>-<CODE>` / 数字码 | `ERR-ORDER-001`, `40001` |
| 国际化 | 需要 / 不需要 | `i18n.t('error.user_not_found')` |

## 5. 数据规范

### 5.1 日期时间

| 规范项 | 规则 |
|-------|------|
| 格式 | ISO 8601 / `yyyy-MM-dd HH:mm:ss` |
| 时区处理 | UTC 存储，展示时转本地 / Asia/Shanghai |
| 数据库类型 | TIMESTAMP / DATETIME |

### 5.2 数值处理

| 规范项 | 规则 |
|-------|------|
| 小数 | `DECIMAL(19,4)` / `BigDecimal` |
| 金额 | 分为单位 / 元为单位 |
| 货币 | ISO 4217 货币码（CNY, USD）|

### 5.3 软删除

| 规范项 | 规则 |
|-------|------|
| 是否启用 | 是 / 否 |
| 标记字段 | `deleted_at` (TIMESTAMP) / `is_deleted` (BOOLEAN) |
| 唯一索引 | 需包含软删除标记 |

### 5.4 审计字段

| 规范项 | 规则 |
|-------|------|
| 是否必需 | 是 / 否 |
| 标准字段 | `created_at`, `created_by`, `updated_at`, `updated_by` |
| 字段类型 | TIMESTAMP / BIGINT (秒级时间戳) |

## 9. 架构决策记录（ADR）机制

### 9.1 ADR 触发条件

以下设计决策**必须**记录 ADR：
- 分库分表策略
- 缓存架构（Redis/本地缓存）
- 异步处理（MQ/线程池）
- 第三方组件引入
- 数据迁移策略
- 性能优化方案

### 9.2 ADR 模板

```markdown
## ADR-{编号}: {决策标题}

**状态**: 提议 / 接受 / 废弃

**决策**: {一句话描述}

**背景**: {为什么需要这个决策？PRD 有什么要求？}

**方案**: {具体采用什么方案？}

**理由**: {为什么选这个方案？}

**替代方案**: {考虑过哪些其他方案？为什么没选？}

**影响**: {这个决策对系统的影响？}

**合规性**: {是否符合 design-conventions？如果不符合，原因是什么？}
```

### 9.3 ADR 存放位置

**路径**: `docs/详细设计/{feature}-设计决策.md`

**Gate 检查**: P2 Gate 会检查关键设计是否有对应 ADR
