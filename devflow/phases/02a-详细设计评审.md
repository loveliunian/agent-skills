# Phase 2a: 详细设计评审 (Detailed Design Review)

## 目标

- 验证详细设计的完整性（字段级 100%）
- 验证设计可实现性、可测性
- 验证需求追溯（acceptance-traceability）100% 覆盖 P0 验收点
- 提前发现设计缺陷，避免带入编码阶段

## 进入条件

- [ ] P2 详细设计已完成（`<feature>-详细设计.md` 存在）
- [ ] 设计覆盖率 = 100%
- [ ] 五个语义锚点齐备（data-model / api-contracts / business-rules 在详设；acceptance-traceability 在需求追溯文档；implementation-handoff 在实现交接文档），实现交接含基线/变更/不变量
- [ ] P0 验收点清单已冻结

## 评审角色（v3.9.7：+DBA，共 5 角色）

> 角色定义、探针主责矩阵与 DF/AW 输出契约见 `subagents/design-review-committee.md`；深度规范见 `concepts/review-depth-methodology.md`。

| 角色 | 评审重点 |
|------|----------|
| **架构师** | 系统分层、跨域决策、性能、可扩展性、成熟组件复用（完整版 §10.1 / 分文档 §10，`anchor: component-reuse`）、公共抽取（`anchor: common-extraction`） |
| **后端专家** | 数据模型（五列）、接口契约（六列）、事务、并发、规范遵循（设计决策记录《规范遵循》，`anchor: standards-compliance`，默认阿里巴巴 Java 开发手册） |
| **前端专家** | UI 交互、组件拆分、可访问性 |
| **测试开发** | 可测性、边界条件、异常路径 |
| **DBA** | **数据库设计决策文档（`docs/详细设计/<feature>-数据库设计决策.md`，`anchor: design-decisions`）逐行核问 DDR**：字段类型/长度/索引每个决策的理由须有业务口径、规范引用或量化数据支撑——"经验/习惯/常用"不通过；迁移/Flyway 四方言一致性 |

**深度要求（v3.16.25）**：先执行适用主责探针（六类深挖探针）再下结论；DF 按实际发现，零发现必须附 `ZERO-DF` 核查清单、证据锚点和验证方式；AW ≥3 条；表层 SF ≤5 条/角色。不得为满足数量凑问题。

## 独立评审收据（编排器强制，v3.16.26；v3.24.0 对齐真实协议）

评审者 ID 不能只写在报告里（自报字符串不可信）。收据为**两阶段 + 平台证明**：
编排器在报告文件产出**之前**对全部六角色 `begin`，聚合报告**冻结后**统一 `complete`——
报告已存在时 `begin` 会被拒绝（杜绝报告定稿后整批补写收据）。

```bash
RR="$SKILL_ROOT/scripts/review-receipt.sh"
OUT=docs/评审/<feature>-设计评审报告.md
IN=docs/详细设计/<feature>-详细设计.md
# REVIEW_SESSION_ID：本轮评审唯一共享 ID（AUTHOR+五角色同 session——Gate 按单 session 校验）
SESSION="rev-<feature>-<YYYYMMDD-HHMMSS>"   # 仅 [A-Za-z0-9._-]

# 0) 平台证明环境（必填，缺失时 begin/complete 直接失败）：
#    REVIEW_ATTESTATION_PUBKEY=<公钥文件路径>   # 评审发起方持有对应私钥；本 skill 永不自签
#    每个事件一份 attestation JSON（schema devflow-review-attestation-v1，平台签发）：
#    {"payload":{schema,feature,session_id,role,agent_id,event,input_sha,output_sha,issued_at,nonce},
#     "signature_b64": "<平台私钥对 payload 的 SHA256 签名>"}

# 1) spawn 各角色拿到 agent_id 后、报告产出前：六角色全部 begin（此时 OUT 必须尚不存在）
#    begin/complete 均须携带 --attestation <file>（与事件字段逐一匹配，verify 校验签名）
#    v3.30.12: attestation 文件名一律用 ASCII agent_id——中文 role 经字符清洗会变成
#    下划线（架构师→_________），同字数角色互相覆盖（m01-base 实测）
for pair in "AUTHOR:<author-agent-id>" "架构师:<id1>" "后端专家:<id2>" "前端专家:<id3>" "测试开发:<id4>" "DBA:<id5>"; do
  bash "$RR" begin --feature <feature> --role "${pair%%:*}" --agent-id "${pair##*:}" \
    --session-id "$SESSION" --input "$IN" --output "$OUT" \
    --attestation "$TMPDIR/attest-${pair##*:}.begin.json"
done

# 2) 各角色独立评审（各自会话），编排器汇总成聚合报告并冻结（此后不再改写）
#    v3.28.9: begin 与 complete 之间必须发生真实评审工作——每角色时长低于
#    DEVFLOW_REVIEW_MIN_SECONDS（默认 60s）即被拒（1 秒盖章式"签名仪式"不构成评审）。

# 3) 聚合报告冻结后：逐一 complete（六条收据绑定同一冻结报告的 SHA；输入详设中途被改即拒绝）
for pair in "AUTHOR:<author-agent-id>" "架构师:<id1>" "后端专家:<id2>" "前端专家:<id3>" "测试开发:<id4>" "DBA:<id5>"; do
  bash "$RR" complete --feature <feature> --role "${pair%%:*}" --agent-id "${pair##*:}" \
    --session-id "$SESSION" --input "$IN" --output "$OUT" \
    --attestation "$TMPDIR/attest-${pair##*:}.complete.json"
done

# 4) Gate 自动 verify；收据缺失/未 complete/SHA 不匹配/评审者==作者/签名无效 → P2a 阻断
```

> **一键引导（v3.27.11）**：手写六角色 begin/complete 与平台签名易错，推荐用封装脚本
> （私钥由评审发起方持有，落盘 `.devflow/<feature>/review-keys/`；本 skill 永不自签）：
>
> ```bash
> bash "$SKILL_ROOT/scripts/review-attest-init.sh" keygen    <feature>
> bash "$SKILL_ROOT/scripts/review-attest-init.sh" env       <feature>   # 导出 REVIEW_ATTESTATION_PUBKEY
> # 报告产出前：
> bash "$SKILL_ROOT/scripts/review-attest-init.sh" begin-all    <feature> <session> \
>   docs/详细设计/<feature>-详细设计.md docs/评审/<feature>-设计评审报告.md \
>   "AUTHOR:<id>,架构师:<id>,后端专家:<id>,前端专家:<id>,测试开发:<id>,DBA:<id>"
> # 报告冻结后：
> bash "$SKILL_ROOT/scripts/review-attest-init.sh" complete-all <feature> <session> \
>   docs/详细设计/<feature>-详细设计.md docs/评审/<feature>-设计评审报告.md "<同上角色表>"
> ```

规则：

- **共享 session**：`REVIEW_SESSION_ID` 是本轮评审（review run）的唯一 ID，AUTHOR+五角色共用；
  各角色自己的**会话**由平台 agent 会话区分（agent_id 唯一）。报告头与五角色收据表的
  REVIEW_SESSION_ID 都等于它——"每角色各自唯一 session"与 Gate 的单 session 校验互斥，以本口径为准。
- **时序**：spawn 返回 agent_id 之后、该角色产出落盘之前 `begin`（输出文件必须尚不存在）；
  所有角色完成、聚合报告冻结之后统一 `complete`——先 complete 再合并会让先前签名失效。
- **修复复审**：每轮评审（初审/复审）使用新的 `REVIEW_SESSION_ID`；新一轮重新走
  begin → 独立评审 → 冻结聚合 → complete 全流程，不复用旧 session。
  **v3.28.9 同输入拦截**：输入详设 SHA 未变时 begin 会被拒——复审必须先改产物；
  确需对同一输入重审（如评审标准升级），显式 `--rerun-reason "<原因>"`（记入台账）。
- **v3.28.9 真实性门禁**：① 每角色 begin→complete 时长 ≥ `DEVFLOW_REVIEW_MIN_SECONDS`
  （默认 60s，verify 侧复查）；② session-id 尾部时间戳与当前时钟漂移 >30 分钟即拒绝
  （时区/时钟源错误早暴露）。
- `begin` 阶段报告文件已存在 → 拒绝；`complete` 阶段输入详设 SHA 与 `begin` 不一致 → 拒绝（评审基线漂移）。
- 收据记录 `input_artifact_sha`（详设）与 `output_report_sha`（报告）：报告在收据后被改写 → Gate 阻断。
- 评审者 agent_id 禁止与 AUTHOR agent_id 相同；角色映射由 session 台账锁定（同角色换 agent / 同 agent 换角色均拒绝）。
- attestation 由平台生命周期事件签发（不得用模型自签替代平台证明）；无 `REVIEW_ATTESTATION_PUBKEY`
  时 begin/complete 会以明确错误失败——先配置证明环境再启动评审。
- 各平台 spawn 方式的语义定义见 `references/agent-runtime-adapter.md`（`spawn_fresh` / `wait_all` / `record_receipt` 两阶段）。

## Gate 检查

```bash
bash "$SKILL_ROOT/scripts/p2a_design_review_gate.sh" <feature>
```

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 评审报告存在 | `wc -l > 0` |
| 2 | 5 角色均有评审（含 DBA） | 5 个角色章节都存在 |
| 3 | 所有角色 = ✅ | `grep -c '✅'` ≥ 5 |
| 4 | 遗留问题 = 0 | v3.14.1 起 p2a 硬阻断：出现"遗留/待修复/TBD/FIXME"即 FAIL |
| 5 | 需求追溯 100% 覆盖 P0 | `grep -cE 'M-[0-9]{2}-F[0-9]{2}-A[0-9]{2}' <design> == grep -cE 'M-[0-9]{2}-F[0-9]{2}-A[0-9]{2}' <acceptance>` |
| 6 | P2 设计覆盖率 = 100% | `s2_design_coverage_gate.sh` exit = 0 |
| 7 | 设计质量四要素 | 详设显性含组件复用/公共抽取；规范遵循在设计决策记录；DDR 在数据库设计决策文档（v3.9.7；v3.27.15 移出详设） |
| 7b | 领域专项清单（v3.14.1） | `gen-domain-checklist.sh <feature> --stage design` 生成后逐项 ✅/❌/N-A，存在未答项 gate 阻断 |
| 8 | 深层发现 DF（v3.16.25） | 每个角色有 DF 或 ZERO-DF 核查证据（空标题 ZERO-DF 拦截），DF 五字段非空、文档位置 §x.y |
| 9 | 对抗场景走查 AW（v3.14.0） | `- AW-` 条目 ≥3，场景/走查路径/结果三段非空，结果的 §锚点解析到详设真实标题或 DF 编号（v3.24.0） |
| 10 | 六类探针执行记录 | 六类逐行标记“已执行”或“不适用+理由”，证据锚点解析到详设真实标题（v3.24.0）；详设含 REUSE/MODIFY/DELETE 基线时 CODE-BASELINE 探针必答（A02） |
| 10b | 严重性修订纪律（A13） | 严重性修订表：修订后严重性变化的行，修订理由与确认评委必填——无理由降级直接 P0（v3.24.0） |
| 11 | 中文文风（v3.18.0） | 按 `concepts/中文文风规范.md` 抽查：每个主要章节主语可辨、结论带依据、无「对X进行了Y」式空动词、无校验器/Gate 内部术语；不合格项按 DF 记录 |

## 评审循环

持续执行直到：
1. 所有角色结论 = ✅
2. 遗留问题 = 0
3. 所有 Gate 通过

## 与 P0b 的关系

| 维度 | P0b（PRD） | P2（详设） |
|------|-----------|-----------|
| 对象 | PRD | 设计 |
| 角色 | 业务/技术/测试/安全 | 架构/后端/前端/测试/DBA |
| 追溯 | — | 需求追溯（acceptance-traceability）P0 验收点 |

## 反模式

❌ 评审只走过场，不提具体问题
❌ 用一句话问题凑数（无触发场景、无影响链的发现不计入 DF 配额）
❌ 零 DF 直接给 ✅（必须附已核查清单 + §锚点证据）
❌ SF 表层 nitpick 数量超过 DF 数量
❌ 未执行主责探针就下结论
❌ 评审记录"已阅"，但无修改闭环
❌ 追溯不全就放行到 P3
❌ 用 P0b 评审替代 P2 评审
