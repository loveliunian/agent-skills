# Phase 2a: 详细设计评审 (Detailed Design Review)

## 目标

- 验证详细设计的完整性（字段级 100%）
- 验证设计可实现性、可测性
- 验证需求追溯（acceptance-traceability）100% 覆盖 P0 验收点
- 提前发现设计缺陷，避免带入编码阶段

## 进入条件

- [ ] P2 详细设计已完成（`<feature>-design.md` 存在）
- [ ] 设计覆盖率 = 100%
- [ ] 需求追溯锚点（anchor: acceptance-traceability）存在
- [ ] P0 验收点清单已冻结

## 评审角色（v3.9.7：+DBA，共 5 角色）

> 角色定义、探针主责矩阵与 DF/AW 输出契约见 `subagents/design-review-committee.md`；深度规范见 `concepts/review-depth-methodology.md`。

| 角色 | 评审重点 |
|------|----------|
| **架构师** | 系统分层、跨域决策、性能、可扩展性、成熟组件复用（§12.1）、公共抽取（§12.2） |
| **后端专家** | 数据模型（五列）、接口契约（六列）、事务、并发、规范遵循（§13，默认阿里巴巴 Java 开发手册） |
| **前端专家** | UI 交互、组件拆分、可访问性 |
| **测试开发** | 可测性、边界条件、异常路径 |
| **DBA** | **设计决策记录 DDR（§2.3）逐行核问**：字段类型/长度/索引每个决策的理由须有业务口径、规范引用或量化数据支撑——"经验/习惯/常用"不通过；四方言 DDL 一致性 |

**深度要求（v3.16.25）**：先执行适用主责探针（六类深挖探针）再下结论；DF 按实际发现，零发现必须附 `ZERO-DF` 核查清单、证据锚点和验证方式；AW ≥3 条；表层 SF ≤5 条/角色。不得为满足数量凑问题。

## 评审产物

`docs/review/<feature>-design-review-report.md`（基于 `templates/详细设计评审报告-模板.md`）

## 独立评审收据（编排器强制，v3.16.26）

评审者 ID 不能只写在报告里（自报字符串不可信）。v3.20.3 起收据为**两阶段**：编排器必须在报告文件产出**之前**对全部六角色 `begin`，各角色评审落盘后再 `complete`——报告已存在时 `begin` 会被拒绝（杜绝报告定稿后整批补写收据）。

```bash
RR="$SKILL_ROOT/scripts/review-receipt.sh"
OUT=docs/review/<feature>-design-review-report.md
IN=docs/detailed-design/<feature>-design.md

# 1) spawn 前：六角色全部 begin（此时 OUT 必须尚不存在）
for pair in "AUTHOR:<author-agent-id>" "架构师:<id1>" "后端专家:<id2>" "前端专家:<id3>" "测试开发:<id4>" "DBA:<id5>"; do
  bash "$RR" begin --feature <feature> --role "${pair%%:*}" --agent-id "${pair##*:}" \
    --session-id <REVIEW_SESSION_ID> --input "$IN" --output "$OUT"
done

# 2) 各角色评审落盘后：逐一 complete（绑定输出 SHA；详设中途被改即拒绝）
bash "$RR" complete --feature <feature> --role 架构师 --agent-id <id1> \
  --session-id <REVIEW_SESSION_ID> --input "$IN" --output "$OUT"

# 3) Gate 会自动 verify；收据缺失/未 complete/SHA 不匹配/评审者==作者/报告在 begin 前已存在 → P2a 阻断
```

规则：

- `REVIEW_SESSION_ID` 由编排器生成（如 `rev-<feature>-<YYYYMMDD-HHMMSS>`），仅允许 `[A-Za-z0-9._-]`，收据与报告必须一致。
- `begin` 阶段报告文件已存在 → 拒绝；`complete` 阶段输入详设 SHA 与 `begin` 不一致 → 拒绝（评审基线漂移）。
- 收据记录 `input_artifact_sha`（详设）与 `output_report_sha`（报告）：报告在收据后被改写 → Gate 阻断。
- 评审者 agent_id 禁止与 AUTHOR agent_id 相同；角色映射由 session 台账锁定（同角色换 agent / 同 agent 换角色均拒绝）。
- 各平台 spawn 方式的语义定义见 `references/agent-runtime-adapter.md`（`spawn_fresh` / `wait_all` / `record_receipt` 两阶段）。

## Gate 检查

```bash
bash "$SKILL_ROOT/scripts/p2a_design_review_gate.sh" <feature>
```

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 评审报告存在 | `wc -l > 0` |
| 2 | 5 角色均有评审（含 DBA） | 5 个角色章节都存在 |
| 3 | 所有角色 = ✅ | `grep -c '✅'` ≥ 5 |
| 4 | 遗留问题 = 0 | v3.14.1 起 p2a 硬阻断：出现"遗留/待修复/TBD/FIXME"即 FAIL |
| 5 | 需求追溯 100% 覆盖 P0 | `grep -cE 'M-[0-9]{2}-F[0-9]{2}-A[0-9]{2}' <design> == grep -cE 'M-[0-9]{2}-F[0-9]{2}-A[0-9]{2}' <acceptance>` |
| 6 | P2 设计覆盖率 = 100% | `s2_design_coverage_gate.sh` exit = 0 |
| 7 | 设计质量四要素 | 详设显性含组件复用/公共抽取/规范遵循/DDR（v3.9.7） |
| 7b | 领域专项清单（v3.14.1） | `gen-domain-checklist.sh <feature> --stage design` 生成后逐项 ✅/❌/N-A，存在未答项 gate 阻断 |
| 8 | 深层发现 DF（v3.16.25） | 每个角色有 DF 或 ZERO-DF 证据，DF 五字段非空、文档位置 §x.y |
| 9 | 对抗场景走查 AW（v3.14.0） | `- AW-` 条目 ≥3 且每条含 `结果:` 收尾（DF 引用或 §锚点证据） |
| 10 | 六类探针执行记录 | 六类逐行标记“已执行”或“不适用+理由”，并附证据 |
| 11 | 中文文风（v3.18.0） | 按 `concepts/中文文风规范.md` 抽查：每个主要章节主语可辨、结论带依据、无「对X进行了Y」式空动词、无校验器/Gate 内部术语；不合格项按 DF 记录 |

## 评审循环

持续执行直到：
1. 所有角色结论 = ✅
2. 遗留问题 = 0
3. 所有 Gate 通过

## 与 P0b 的关系

| 维度 | P0b（PRD） | P2（详设） |
|------|-----------|-----------|
| 对象 | PRD | 设计 |
| 角色 | 业务/技术/测试/安全 | 架构/后端/前端/测试/DBA |
| 追溯 | — | 需求追溯（acceptance-traceability）P0 验收点 |

## 反模式

❌ 评审只走过场，不提具体问题
❌ 用一句话问题凑数（无触发场景、无影响链的发现不计入 DF 配额）
❌ 零 DF 直接给 ✅（必须附已核查清单 + §锚点证据）
❌ SF 表层 nitpick 数量超过 DF 数量
❌ 未执行主责探针就下结论
❌ 评审记录"已阅"，但无修改闭环
❌ 追溯不全就放行到 P3
❌ 用 P0b 评审替代 P2 评审
