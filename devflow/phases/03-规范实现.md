# Phase 3: 全栈编码实现

> **技术栈范围（v3.23.0）**：先按 `references/runtime-profile.md` 解析并冻结 `PROFILE_ID` 与能力位；下述 Java/Spring/Flyway 规则仅在 `PROFILE_ID=java-spring-flyway` 时生效，其他技术栈使用项目 Profile 的等价 adapter（缺能力位即 `BLOCKED`）。

> **Java 编码强制规范（v3.18.3；v3.19.0 修订适用范围）**：生成任何 Java 代码（Entity/Repository/Service/Controller/DTO/单测）前，
> 必须对照 `concepts/Java开发手册_黄山版.md` 相应章节执行——命名（POJO/Service/DAO、异常/日志）、
> 常量与枚举、集合与并发处理、控制语句、OOP、注释与命名行宽、异常与事务、日志、应用分层与二方库。
> 手册【强制】条款违反即 P3b 评审 FAIL（引用章节号），无豁免。
>
> **与四方言铁律的优先级（铁律 5 优先）**：手册「MySQL 数据库」章节为方言专有条款
> （如 unsigned、IFNULL、ISNULL() 等），与本 skill 的 h2/postgresql/oracle/kingbase
> 四方言一致性契约不兼容——**该章节以四方言契约为准**：方言专有写法仅当冻结目标库
> 确含 MySQL 且不破坏其余方言一致性时可用，且必须在详设中记录方言适配说明；
> 二者冲突时四方言优先，不视为违反手册。
>
> 执行口径：机检脚本（check-code-standards.sh）只覆盖可自动化子集；全量【强制】合规由
> P3b 评审逐条核对并引用章节号，机检通过不等于合规完成。


## 目标

基于详细设计文档，实现完整的全栈代码：
- **后端**：Java/Spring Boot API、Service、Repository层
- **前端**：Vue/TypeScript 组件、页面、API调用
- **数据库**：Flyway SQL迁移脚本

**完成判定**：先跑 `scripts/build-watchdog.sh gate <feature>` 产出 P3-build 收据；Phase 最终完成由 `scripts/p3_completion_gate.sh` 退出码判定；任何编译、测试、覆盖率、四方言、权限或Seed失败均阻断P3b。

**经验教训应用**：
- L-P3-001：MockMvc 全绿 ≠ 真实容器可用（验证基线必须包含真实运行）
- L-P3-002：P3b 代码审查必须独立角色（禁止自评）
- L-STACK-002：认证通道必须在 P3 完成（不能只用 dev-privileged 绕过）
- L-MON-001：build-watchdog 必须留痕（写完即编译）
- 详见 `concepts/lessons-learned.md`

## 主Agent调度模式

> **重要**：主Agent负责任务分解和调度，子Agent负责实际编码工作。
> **铁律**：不同复杂度的任务必须使用不同类型的Agent，禁止混用。

### Agent角色定义（借鉴 ECC）

| 角色 | Agent类型 | 职责范围 |
|------|-----------|----------|
| `sql-dev` | `shell` | SQL迁移脚本编写 |
| `backend-dev` | `generalPurpose` | 后端代码 + 单测 |
| `frontend-dev` | `generalPurpose` | 前端代码 + 联调 |
| `code-reviewer` | `generalPurpose` | Code Review |
| `test-engineer` | `generalPurpose` | 测试策略 + 用例 |

### 调度粒度参考（按文件数粗分；调度用启发式，不是 /plan 的任务分级）

| 级别 | 文件数 | 范围 | 调度方式 |
|------|--------|------|----------|
| XS | 1 | 单文件修改 | 主Agent直接执行 |
| S | 1-2 | 单函数、单组件 | 主Agent直接执行或单一子Agent |
| M | 3-5 | 一个垂直功能切片 | 子Agent，可并行但文件/契约不得重叠 |
| L | 5-8 | 多组件功能 | 先拆为多个 M 级垂直切片 |
| XL | 8+ | **必须拆分** | 拆分为 M 级垂直切片 |

### 调度策略

```
主Agent（调度）
    │
    ├── XS/S任务 → 主Agent直接执行或单一子Agent
    │
    ├── M级任务 → generalPurpose 子Agent（可并行）
    │       ├── sql-dev：SQL迁移脚本
    │       ├── backend-dev：后端代码 + 单测
    │       └── frontend-dev：前端代码
    │
    └── L/XL任务 → 必须拆分为M级垂直切片
```

### 子Agent任务分配

当主Agent确定要执行Phase 3时，应：

1. **分析详细设计文档**，确定需要实现的模块
2. **读取 `任务/执行契约.md`（兼容历史 `tasks/plan.md`）**（Task/Target/Action/依赖/Verify），按 Task 拆分；需要并行调度时再按文件数粗估粒度
3. **按垂直切片拆分**（每个切片覆盖数据、API、客户端、测试和可达性）
4. **分配专业Agent角色**：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Agent角色任务分配                              │
├─────────────────────────────────────────────────────────────────┤
│  sql-dev (shell)                                                │
│    └── SQL迁移脚本编写                                           │
│        ├── 建表语句                                             │
│        ├── 字段变更                                             │
│        └── 初始数据                                             │
│                                                                  │
│  backend-dev (generalPurpose)                                    │
│    └── 后端代码 + 单测                                          │
│        ├── Entity/DTO                                          │
│        ├── Repository                                          │
│        ├── Service + 单测                                      │
│        └── Controller                                         │
│                                                                  │
│  frontend-dev (generalPurpose)                                  │
│    └── 前端代码                                                 │
│        ├── TypeScript类型                                       │
│        ├── API调用                                             │
│        ├── Vue组件                                             │
│        └── 页面交互                                            │
└─────────────────────────────────────────────────────────────────┘
```

5. **并行启动子Agent**（M级任务可并行）
6. **收集结果**，验证通过后进入下一步

### 子Agent执行指令模板

启动子Agent时，传递以下上下文：

```
Agent角色：sql-dev | backend-dev | frontend-dev
任务规模：XS | S | M | L
```

## 垂直切片执行

每个切片必须包含完整的前后端功能，且能独立运行、测试和验收：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Phase 3 垂直切片编码顺序                       │
├─────────────────────────────────────────────────────────────────┤
│  切片1: 基础CRUD                                                │
│    ├── SQL建表 + 后端API + 前端列表页                           │
│    ↓                                                            │
│  切片2: 详情功能                                                 │
│    ├── SQL字段 + 后端详情API + 前端详情页                       │
│    ↓                                                            │
│  切片3: 业务逻辑                                                 │
│    ├── SQL业务表 + 后端业务逻辑 + 前端交互                      │
│    ↓                                                            │
│  切片4: 高级特性                                                 │
│    ├── SQL高级字段 + 后端高级功能 + 前端高级UI                  │
└─────────────────────────────────────────────────────────────────┘
```

> **垂直切片优势**：每个切片都是可运行的完整功能，可以独立测试和部署

并行前必须确认各切片的文件集合、数据库对象、接口契约和验收点互不重叠；共享契约先由主 Agent 冻结，再由子 Agent 消费。

## Step 0: 任务规模评估与拆分

### 任务规模评估（借鉴 addyosmani/planning-and-task-breakdown）

| 规模 | 文件数 | 范围 | 建议 |
|------|--------|------|------|
| **XS** | 1 | 单函数修改、配置变更 | 直接执行 |
| **S** | 1-2 | 单组件、单API | 子Agent |
| **M** | 3-5 | 单功能切片 | 子Agent并行 |
| **L** | 5-8 | 多组件功能 | 主Agent执行 |
| **XL** | 8+ | 太大了 | **必须拆分** |

### 拆分原则

- 一个任务应能在1-2个focused session内完成
- 验收标准用3个以内的bullet point描述
- 任务标题不应包含"和"、"或"等连接词
- 跨多个独立子系统的是多个任务

### 垂直切片任务模板

每个垂直切片任务应包含：

```markdown
## Task [N]: [功能名称]

**描述：** 实现[具体功能]，包含[前后端完整链路]

**验收标准：**
- [ ] [后端] API可正常调用
- [ ] [前端] 页面可正常展示
- [ ] [测试] 单元测试通过

**依赖：** [前置任务编号或"无"]

**文件清单：**
- `backend/.../Service.java`
- `frontend/.../index.vue`
- `backend/.../V1.x__xxx.sql`

**规模：** S | M | L
```

#### Service

```java
/**
 * 用户Service
 * 负责：用户相关业务逻辑
 */
@Service
@RequiredArgsConstructor
public class UserService {
    
    private final SysUserRepository userRepository;
    
    /**
     * 更新用户信息
     *
     * @param request 更新请求
     * @return 更新后的用户
     * @throws BusinessException 当用户不存在时抛出
     */
    public SysUser updateUser(UserUpdateRequest request) {
        // 1. 参数校验
        validateRequest(request);
        
        // 2. 查询用户
        SysUser user = userRepository.findById(request.getId())
            .orElseThrow(() -> new BusinessException("USER_NOT_FOUND", "用户不存在"));
        
        // 3. 更新字段
        if (request.getGender() != null) {
            user.setGender(request.getGender());
        }
        
        // 4. 保存
        return userRepository.save(user);
    }
    
    private void validateRequest(UserUpdateRequest request) {
        if (request == null) {
            throw new BusinessException("REQUEST_NULL", "请求不能为空");
        }
    }
}
```

#### Controller

```java
/**
 * 用户Controller
 * 负责：用户相关API
 */
@RestController
@RequestMapping("/api/users")
@RequiredArgsConstructor
public class UserController {
    
    private final UserService userService;
    
    /**
     * 更新用户信息
     */
    @PutMapping("/{id}")
    public Result<SysUser> updateUser(
            @PathVariable Long id,
            @RequestBody @Valid UserUpdateRequest request) {
        request.setId(id);

    }
}
```

## 质量标准

> **核心原则**："质量标准"不是 check-list 文字，而是**每个标准都有对应的 grep/find 命令**。Agent 自评"完成"必须附命令输出。
>
> **跨平台兼容性**：以下命令已用 `grep -E` / `find -name | xargs` / `find | grep` 替代 GNU 专用语法，在 macOS BSD grep / Linux GNU grep / Windows Git Bash 3.2 通用。详见 `references/windows-compatibility.md`。

| # | 标准 | 验证命令（POSIX 通用，必须通过） | 常见失效模式 |
|---|------|----------------------------------|----------------|
| 1 | TODO 残留为 0 | `grep -rn "TODO" backend/<service>/src/main/java \| wc -l \| tr -d ' '` 输出 = 0 | 大量 TODO 残留进入下一阶段 |
| 2 | **所有 Controller 至少 1 个 `@PreAuthorize`** | `find backend/<service>/src/main/java -name "*Controller.java" -type f \| xargs grep -L "@PreAuthorize" 2>/dev/null \| wc -l` = 0 | 多个 Controller 裸奔无权限注解 |
| 3 | Mapper 数 = 实体数 | `find backend/<service>/src/main/java -name "*Mapper.java" -type f \| wc -l \| tr -d ' '` = `find backend/<service>/src/main/java -name "*.java" -type f \| grep "/entity/" \| wc -l \| tr -d ' '` | 新增表无对应 Mapper |
| 4 | Flyway 多 DB 脚本齐备 | `for v in h2 oracle postgresql kingbase; do test -d backend/<service>/src/main/resources/db/migration/$v && echo $v OK; done` 输出 4 行 | 某模块漏建某方言目录 |
| 5 | **核心业务单测覆盖率 ≥ 80%** | `mvn test jacoco:report && test -f target/site/jacoco/index.html` | 用例数少通过率虚高 |
| 6 | 后端编译通过 | `mvn -q compile` exit = 0 | — |
| 7 | 后端测试通过 | `mvn -q test` exit = 0（**不允许 BUILD SUCCESS 但 ERROR**） | 上次 maven test 状态需以 XML 报告为准 |
| 8 | 前端 build 通过 | `(cd frontend && npm run build)` exit = 0 | — |
| 9 | 前端 type-check 通过 | `(cd frontend && npm run type-check)` exit = 0 | — |

## Red Flags 🚩

以下情况必须停止并汇报：

| 红旗 | 问题 | 正确做法 |
|------|------|----------|
| 无SQL就写代码 | 后端依赖不存在的表 | 必须先写SQL迁移脚本 |
| 实现与Spec不符 | 编码不按设计 | 严格对照Spec |
| 跳过测试 | "代码简单不用测" | 必须有测试 |
| 硬编码值 | 魔法数字/字符串 | 提取为常量 |
| 空catch块 | catch后什么都不做 | 必须记录或处理 |
| 前端用any | 类型不安全 | 必须定义完整类型 |

---

## 关键原则

1. **SQL先行** - 先定义数据模型，再写代码
2. **Spec对照** - 实现必须与详细设计一致
3. **类型安全** - 前后端都要有完整的类型定义
4. **测试验证** - 每个核心模块必须有测试
5. **小步提交** - 每完成一个小模块就提交代码

## 架构陷阱自检

> **铁律**：P3 编码完成后，进 P3b (Code Review) 前**必须**跑 `check-arch-pitfalls.sh --all`，critical > 0 阻塞。

```bash
# 一键全跑（11 类陷阱）
bash "$SKILL_ROOT/checks/check-arch-pitfalls.sh" --all

# 期望：CRITICAL = 0, WARN 可接受
# 退出码 0 = PASS, 1 = FAIL
```

**P3 编码阶段必查的 11 类陷阱**：

| 类别 | 编码阶段必读章节 |
|------|------------------|
| §6 代码规范 | 巨型 Service ≤500 行、DTO 重复、ObjectMapper 绕过、未命名线程池 |
| §8 性能 | N+1 查询、本地无界缓存、Outbox 散落、异步执行器分裂 |
| §7 文档同步 | 接口路径、版本号、端口与代码同源 |

**失败处理**：
1. 看 `[CRITICAL]` 行的"位置"
2. 跳到 `concepts/architecture-pitfalls.md` 对应章节
3. 按"修复"段操作
4. 重跑 `check-arch-pitfalls.sh --all` 直到 0 critical

**实战案例**（避免重蹈覆辙，更多见 examples/xyls/domain-checklist.md）：
- ❌ 千行级巨型 ServiceImpl → 必须按职责拆分（如 Import/Export 独立 Service）
