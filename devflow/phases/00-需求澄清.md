# Phase 0: 需求澄清 (Requirements Clarification)

## 目标

- 消除需求中的模糊点和歧义
- 确认各方对需求的理解一致
- 补充缺失的需求细节
- **拆分 PRD 功能点为原子验收点**（一个验收点 = 一个行为 = 一个测试用例）
- 产出原子验收点清单（ID 格式：`M-{模块号}-F{功能号}-A{验收点号}`），状态必须 FROZEN

> **技术约束继承（v3.28.13）**：同项目非首个 feature，技术约束先跑
> `devflow-state.sh constraints-inherit <feature> [--from <source>|@latest]`——从最近
> 冻结的 feature 继承机器块（来源已漂移则拒绝），P0 只澄清 **delta**（本 feature
> 特有约束的增删）。继承稿仍须完整走 s0 门禁 + constraints-freeze；冻结的是本
> feature 文件自身 SHA，P1 校验契约不变。

## 澄清维度

| 维度 | 问题示例 |
|------|----------|
| **功能性** | 这个功能具体要做什么？输入输出是什么？边界条件有哪些？ |
| **业务流程** | 完整的业务流程是什么？有哪些分支和异常？ |
| **数据要求** | 数据从哪里来？需要存储哪些字段？数据量预估？ |
| **性能要求** | 响应时间要求？并发量要求？ |
| **兼容性** | 需要兼容哪些系统/版本？ |
| **异常处理** | 异常情况如何处理？错误提示是什么？ |

## 澄清问卷模板

```markdown
## 需求澄清问卷

### 功能确认
1. 核心功能：用户可以做什么？
2. 关键流程：数据如何流转？
3. 输入输出：有哪些输入参数？期望输出是什么？

### 边界条件
1. 最小输入量是多少？
2. 最大输入量是多少？
3. 异常输入如何处理？

### 业务规则
1. 有哪些业务规则需要校验？
2. 规则优先级如何？
3. 冲突时如何处理？

### 性能指标
1. 响应时间要求？
2. 并发量要求？
3. 数据量预估？

### 依赖关系
1. 依赖哪些外部系统？
2. 依赖哪些内部服务？
3. 有没有数据同步需求？

### 技术硬约束（必须冻结）
1. 用户/PRD 是否指定必须使用或禁止使用某个组件、产品、版本、许可证或部署方式？
2. 每条约束的来源锚点、确认人和生效状态是什么？
3. 若 Agent 建议偏离，是否已获得用户明确批准并更新 PRD？

### 权限与事实源对账（L-P0-001）
> **经验教训**：权限码双口径应在 P0b 拦截，不应等到 P2a

1. PRD 中定义的权限码是否与 `docs/详细设计/_权限矩阵.md` 事实源一致？
2. 如存在权限矩阵事实源，P0 阶段是否已完成对账？
3. 不一致时以哪个为准？（建议：事实源优先，PRD 需修订）

### 异常处理
1. 可能出现的异常场景？
2. 异常时的用户提示？
3. 需要记录日志吗？
```

## 深挖探针（强制，在拆分验收点之前执行）

> **目的**：不仅问"这个需求是什么意思"（澄清），还要问"这个需求是否自洽/是否遗漏"（深挖）。
> 每个探针产出要么 pass（未发现问题），要么 findings（发现待确认问题写入澄清记录），
> 要么 not_applicable（须给理由）。blocking 级发现不确认不能进 P2。

| # | 探针 | 检查什么 | 典型发现 |
|---|------|----------|----------|
| 1 | **逻辑矛盾** | PRD 不同章节/功能点之间是否有冲突描述？A 说 X、B 说 Y、X 和 Y 能同时成立吗？ | 功能 A 说"删除后不可恢复"，功能 B 说"支持从回收站恢复" |
| 2 | **状态完整性** | 有状态的实体（订单/用户/组织），所有状态转换路径覆盖了吗？有没有到不了/回不去的状态？ | 用户有"待激活"状态，但没有从"待激活"到"已激活"的触发条件 |
| 3 | **数据流闭环** | 数据从创建到归档/删除，全生命周期有没有断链？有没有"只写不读"或"只读不写"的字段？ | 日志表只写不读（谁消费？）；统计字段依赖上游但上游未定义 |
| 4 | **并发冲突** | 两个用户同时操作同一数据会怎样？有没有时序问题？ | 两个管理员同时编辑同一组织，谁生效？乐观锁还是后写覆盖？ |
| 5 | **失败链路** | 多步流程中间某步失败，前面的步骤回滚吗？重试吗？用户看到什么？ | 创建用户+发短信，短信失败用户已创建——回滚还是保留+重发？ |
| 6 | **隐含假设** | PRD 没说但默认成立的前提是什么？ | "假设只有一个管理员""假设操作顺序执行""假设网络不会断" |
| 7 | **权限边界** | 谁能做/谁不能做？边界清晰吗？"不能做"时用户看到什么？ | PRD 说"管理员可编辑"，但没说普通用户尝试编辑时看到 403 还是隐藏按钮 |
| 8 | **验收完备性** | 每个功能点的验收标准能否实际测试？有没有"测不了"的模糊描述？ | "系统应快速响应"——多快算快？没有量化指标无法测试 |

**执行时机**：读完 PRD 后、拆分验收点前。

**产物**：发现写入 `clarification.json` 的 `deep_probes[]`，渲染到澄清记录 Markdown 的《深挖探针》章节。

**blocking 级发现的处置**：必须在澄清记录中获得用户确认（`confirmed=true`）才能进 P2；未确认的 blocking 发现等于"PRD 未就绪"。

**经验教训**：越早发现逻辑矛盾，修复成本越低——P0 发现是改一句话，P2 发现是改详设+接口+表，P6 发现是改代码+重测。

## 原子验收点拆分（强制）

> **P0 阶段必须产出**：`docs/需求/<feature>-验收点.md`
>
> **拆分粒度**：一个验收点 = 一个行为 = 一个测试用例
>
> **经验教训参考**：本阶段应用 L-P0-001（权限码对账）教训，参见 `concepts/lessons-learned.md`

### 拆分步骤

```
Step 1: 阅读 PRD，识别所有功能点（F01, F02, ...）
Step 2: 每个功能点拆分为原子验收点（A01, A02, ...）
Step 3: 每个验收点标注可验证方式（API / UI / 单元测试）
Step 4: 标注 PRD 原文锚点（章节/行号）
Step 5: 多 Agent 评审 → 冻结（FROZEN）
Step 6: 移交 P2 详设，作为需求追溯（acceptance-traceability）源
```

### P0 技术约束产物（强制）

除验收点外，必须生成 `docs/需求/<feature>-技术约束.md`，使用
`templates/技术约束-模板.md`。`MUST_USE`、`MUST_NOT_USE`、固定版本和许可证均为
`FROZEN` 硬约束；P1 不得以加权评分或 Agent 自主决策覆盖。

机器契约要求（v3.16.26）：

- 约束以**机器契约块**（`constraint_id/type/required_product/required_version/status/confirmed` key=value）为准，Gate 只解析机器字段，不从自然语言推断合规。
- 每条约束 `status=FROZEN`、`confirmed=true`（DRAFT 或未确认会被所有后续 Gate 阻断）。
- 无硬约束也必须写 `constraint_set=NONE` + `confirmed=true` 契约块。
- **输入物料冻结（铁律 18/19）**：澄清阶段登记的脚手架路径（`--scaffold`）、原型图/交互稿
  （`--prototype`）、设计规则（`--design-rules`）、UI 规范（`--ui-spec`）均为输入物料事实源，
  须在澄清记录中列明路径与版本（图片/链接给 SHA 或获取时点）；物料是设计硬约束，
  P1 重合度审计与 P2 详设必须以其为准。
- P0 Gate 通过后、进入 P1 前，运行冻结命令把文件 SHA 记入 state：

```bash
bash "$SKILL_ROOT/scripts/s0_acceptance_gate.sh" <feature>
bash "$SKILL_ROOT/scripts/devflow-state.sh" constraints-freeze <feature>
```

### ID 格式规范

```
M-{模块号}-F{功能号}-A{验收点号}

示例：M-01-F01-A01
  └─┘ └─┘ └─┘
   模块  功能  验收点

- 模块号：2 位数字（01-99）
- 功能号：2 位数字（01-99）
- 验收点号：2 位数字（01-99）
```

### 验收点模板

| 验收点ID | 验收点描述 | 验证方式 | PRD原文锚点 | 状态 |
|----------|------------|----------|-------------|------|
| `M-{xx}-F{y}-A{z}` | {行为描述} | API / UI / 单元测试 | `docs/PRD/{file}.md#L{line}` | FROZEN |

### Gate 检查

```bash
bash "$SKILL_ROOT/scripts/s0_acceptance_gate.sh" <feature>
```

| 检查项 | 命令 | 通过条件 |
|--------|------|----------|
| 验收点数量 | `grep -cE 'M-[0-9]{2}-F[0-9]{2}-A[0-9]{2}'` | > 0 |
| ID 唯一性 | `sort \| uniq -d` | = 0 |
| 状态冻结 | `grep -c 'FROZEN'` | = 总数 |
| 无占位符 | `grep -cE 'TODO|TBD|待补充'` | = 0 |

## 常见澄清场景

| 场景 | 澄清问题 |
|------|----------|
| "用户可以管理数据" | 管理=CRUD哪些操作？批量操作支持吗？ |
| "系统需要高效" | 高效的具体指标？响应时间？并发？ |
| "数据需要安全" | 安全具体指什么？加密？权限？审计？ |

## 结构化产物层（v3.25.2）

本阶段产物已结构化：AI 按 `schemas/clarification.schema.json`（样例 `examples/structured/clarification.sample.json`）填 `.devflow/<feature>/clarification.json`，再跑管线校验并确定性渲染 Markdown——**校验失败不渲染、不落盘、不进 Gate**；空集合必须 `zero_results` 显式声明。渲染格式与阶段 Gate 的机器解析契约逐字段兼容，模板保留为语义参考。


本阶段含多份结构化产物：

| kind | JSON | 渲染产物 |
|---|---|---|
| `clarification` | `.devflow/<feature>/clarification.json` | `docs/需求/<feature>-需求澄清.md` |
| `acceptance` | `.devflow/<feature>/acceptance.json` | `docs/需求/<feature>-验收点.md` |
| `constraints` | `.devflow/<feature>/constraints.json` | `docs/需求/<feature>-技术约束.md` |

```bash
python3 scripts/df_pipeline.py clarification --input .devflow/<feature>/clarification.json --out docs/需求/<feature>-需求澄清.md
python3 scripts/df_pipeline.py acceptance   --input .devflow/<feature>/acceptance.json   --out docs/需求/<feature>-验收点.md
python3 scripts/df_pipeline.py constraints  --input .devflow/<feature>/constraints.json  --out docs/需求/<feature>-技术约束.md
```
