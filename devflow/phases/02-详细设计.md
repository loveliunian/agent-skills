# Phase 2: 详细设计 (Detailed Design)

## 目标

基于PRD和技术选型结果，生成完整的详细设计文档，为后续编码提供明确指导。

**经验教训应用**：
- L-P2-001：跨模板视图必须独立文件，禁止硬链接
- L-P2-003：表结构对账必须在 P2 冻结前完成
- 详见 `concepts/lessons-learned.md`

## 输入

- PRD文档
- 技术选型报告
- 现有系统架构（如有）

## 设计内容

### 1. 系统架构设计

```
┌─────────────────────────────────────────────────────────┐
│                     前端层 (Frontend)                     │
│   Web App / Mobile App / Mini Program / API Consumer    │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│                    API网关层 (Gateway)                   │
│         认证、鉴权、限流、路由、日志                       │
└─────────────────────────────────────────────────────────┘
                            │
            ┌───────────────┼───────────────┐
            ▼               ▼               ▼
    ┌───────────┐   ┌───────────┐   ┌───────────┐
    │ Service A │   │ Service B │   │ Service N │
    │ (业务服务) │   │ (业务服务) │   │ (业务服务) │
    └───────────┘   └───────────┘   └───────────┘
            │               │               │
            └───────────────┼───────────────┘

│                      数据层 (Data)                        │
│     DB / Cache / Message Queue / Object Storage          │
└─────────────────────────────────────────────────────────┘
```

### 2. 模块设计

对每个核心模块，定义：

| 项目 | 内容 |
|------|------|
| **职责** | 模块负责什么 |
| **边界** | 输入、输出、内部状态 |
| **依赖** | 依赖的其他模块/服务 |
| **接口** | 对外暴露的API |

### 3. API设计

```yaml
API规范: OpenAPI 3.0
格式: REST / GraphQL / gRPC (按需选择)

示例:
POST /api/v1/users
Request:
  {
    "username": "string",
    "email": "string",
    "password": "string"
  }
Response:
  {
    "code": 0,
    "data": {
      "id": "long",
      "username": "string",
      "email": "string",
      "createdAt": "datetime"
    },
    "message": "success"
  }
```

### 4. 数据模型设计

#### 4.1 实体关系图 (ERD)

```
┌──────────────┐     ┌──────────────┐
│    User      │     │   Account    │
├──────────────┤     ├──────────────┤
│ id (PK)      │────<│ id (PK)      │
│ username     │     │ user_id (FK) │
│ email        │     │ balance       │
│ password     │     │ currency      │
└──────────────┘     └──────────────┘
```

#### 4.2 表结构

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_username (username),
    INDEX idx_email (email)
);
```

### 5. 流程设计

对核心业务流，绘制流程图：

```
开始 → 用户提交 → 参数校验 → 业务处理 → 数据持久化 → 返回结果 → 结束
              ↓           ↓           ↓
           校验失败    异常处理    失败回滚
              ↓           ↓           ↓
           返回错误    记录日志    返回错误
```

### 6. 非功能性设计

| 项目 | 设计要点 |
|------|----------|
| **性能** | 响应时间目标、并发处理能力 |
| **可用性** | SLA目标、容错机制 |
| **安全** | 认证方式、权限控制、数据加密 |
| **可扩展** | 水平扩展方案、模块化设计 |
| **可观测** | 日志规范、监控指标、告警规则 |

## Red Flags 🚩

以下情况必须停止并汇报：

| 红旗 | 问题 | 正确做法 |
|------|------|----------|
| 接口定义模糊 | "返回用户信息" | 必须定义完整字段 |
| 表结构缺失 | 没有索引设计 | 必须定义索引 |
| 依赖模糊 | "依赖其他模块" | 必须明确模块名 |
| 假设未验证 | "假设性能足够" | 必须量化指标 |
| 与选型矛盾 | 设计与技术选型不符 | 必须保持一致 |
| 遗漏异常场景 | 只考虑正常流程 | 必须覆盖异常 |

## 关键原则

1. **明确无歧义** - 每个设计点都要有明确的结论，不能留模糊地带
2. **说人话** - 全部产出文档的中文表达遵循 `concepts/中文文风规范.md`：主谓宾完整、结论自己站着、数字给口径、不把校验器/Gate 内部机制写进正文
3. **可落地** - 设计要考虑实现难度，不能纸上谈兵
4. **保持一致** - API命名、字段命名等要保持一致性
5. **考虑演进** - 设计要支持未来的扩展

## ⚠️ 详细设计强制约束（v3.9.4 新增）

### 1. 数据库关键字规避规则

> **强制要求**：所有表名、字段名必须规避目标数据库关键字（覆盖所有支持的数据库）

**各数据库关键字清单**：

| 数据库 | P0-极高风险关键字 | P1-高风险关键字 | P2-中风险关键字 |
|--------|------------------|----------------|----------------|
| **PostgreSQL** | `user`, `group`, `order`, `status`, `name`, `type`, `desc`, `level`, `comment` | `check`, `date`, `time`, `timestamp`, `boolean`, `integer`, `text`, `varchar`, `char` | `select`, `from`, `where`, `insert`, `update`, `delete`, `create`, `drop`, `alter` |
| **MySQL** | `user`, `group`, `order`, `status`, `name`, `type`, `desc`, `key`, `file` | `date`, `time`, `timestamp`, `text`, `table`, `index`, `condition` | `select`, `from`, `where`, `order`, `by`, `limit` |
| **Oracle** | `user`, `group`, `order`, `status`, `name`, `type`, `desc`, `level`, `comment` | `date`, `time`, `timestamp`, `boolean`, `integer`, `varchar2`, `clob`, `blob` | `select`, `from`, `where`, `table`, `index`, `sequence` |
| **KingBase** (人大金仓) | `user`, `group`, `order`, `status`, `name`, `type`, `desc`, `level`, `comment` | `date`, `time`, `timestamp`, `boolean`, `integer`, `text`, `varchar` | `select`, `from`, `where`, `insert`, `update`, `delete`, `create` |

**通用 P0 关键字（所有数据库必须规避）**：

```
user, username, group, order, status, name, type, desc, level, comment,
key, index, table, column, date, time, timestamp, primary, foreign, references,
default, unique, check, boolean, integer, text, varchar, char
```

**规避策略**：

| 策略 | 示例 | 适用场景 |
|------|------|----------|
| **前缀法** | `user` → `sys_user`，`order` → `biz_order` | 字段名 |
| **后缀法** | `status` → `status_cd`，`type` → `type_code` | 枚举类字段 |
| **下划线法** | `name` → `user_name`，`date` → `create_date` | 通用场景 |
| **完整词法** | `level` → `priority_level`，`comment` → `remark` | 语义明确 |

**设计检查点**：
```
分文档完成后，Agent 必须执行：
1. 检查所有表名、字段名是否命中上述关键字
2. 如目标多数据库：分别检查各数据库关键字
3. 如有冲突，立即修改设计文档后再继续
```

**验证 SQL（按数据库执行）**：

```sql
-- PostgreSQL
SELECT * FROM pg_get_keywords() WHERE reserved = true;

-- MySQL
SELECT * FROM information_schema.keywords WHERE reserved = true;

-- Oracle（查询数据字典）
SELECT * FROM v$reserved_words WHERE reserved = true;

-- KingBase（兼容 PostgreSQL）
SELECT * FROM pg_get_keywords() WHERE reserved = true;
```

### 2. 分文档状态同步规则

> **强制要求**：总分架构模式下，分文档完成后必须同步更新总文档状态

**同步时机与内容**：

| 阶段 | 总文档位置 | 同步内容 |
|------|------------|----------|
| 分文档创建 | §0.2 / §6 | 初始化状态为 `🔄`（进行中） |
| 分文档完成 | §0.2 / §6 / §7 | 状态改为 `✅`，更新验收点数 |
| 分文档变更 | §10 变更历史 | 记录变更内容和版本号 |

**设计检查点**：
```
分文档完成后，Agent 必须执行：
1. grep "⏳" docs/detailed-design/{feature}-design-summary.md
2. 如果仍有 ⏳，立即更新对应行的状态为 ✅
3. 输出同步后的 diff 证据
```

**反模式**：

| 禁止行为 | 正确做法 |
|----------|----------|
| ❌ 分文档完成但总文档状态没变 | ✅ 分文档完成后立即同步总文档 |
| ❌ 先写分文档后补总文档状态 | ✅ 创建时初始化，评审通过后更新为 ✅ |
| ❌ 部分同步 | ✅ 同步所有涉及该分文档的章节 |

## 结构化产物层（v3.17.0 · design.json）

> 借鉴 flow-node-panorama 的「结构化数据编译成文档」机制：AI 只填**语义层**（设计判断、
> 锚点、证据）；编号、计数、覆盖率、追溯矩阵、索引表、零结果话术由脚本派生（**确定性层**）。

| 产物 | 位置 | 说明 |
|------|------|------|
| `design.json` | `.devflow/<feature>/design.json` | 机器可读业务产物，契约见 `schemas/design.schema.json` |
| 详设文档 | `docs/detailed-design/<feature>-design.md` | 骨架中嵌入 `<!-- df:begin:KEY -->`/`<!-- df:end:KEY -->` 锚点块，由渲染器整体重写 |

**管线（单一失败关闭入口，禁止跳过校验直接渲染）**：

```bash
python3 "$SKILL_ROOT/scripts/df_pipeline.py" design \
  --input .devflow/<feature>/design.json \
  --doc docs/detailed-design/<feature>-design.md \
  --criteria docs/requirements/<feature>-acceptance-criteria.md \
  --gate bash "$SKILL_ROOT/scripts/s2_design_coverage_gate.sh" \
         docs/detailed-design/<feature>-design.md \
         docs/requirements/<feature>-acceptance-criteria.md --mode=monolith
```

**确定性层锚点块**（KEY 共 10 个，骨架缺块即渲染失败）：`summary`、`trace-matrix`、
`table-index`、`api-index`、`permission-matrix`、`rule-index`、`client-scope`、`zero-results`、
`ddr-index`、`ddr-matrix`。

**跨字段校验**（`df_validate.py --kind design`，s2 Gate §2c 必填强制）：

- 验收 ID 唯一 + 与 criteria 冻结集合全等；锚点引用闭环（page/api/data/rule 必须指向真实条目）；
- **接口概览 ↔ 详细定义一一对应**（v3.17.1）：每个 API 必填 `detail_anchor`（§3.2.N）+ `name`；
  monolith 模式对文档**双向对账**——概览声明的小节必须在文档中真实存在（拦「概览列了 N 个、
  详细定义只写了 M<N 个」），文档中多余小节同样拦截；
- **DDR ↔ 字段一一对应**（v3.17.1）：`decisions[]`（DDR-N：决策点/备选/选定/理由）+ 每个表字段
  必填 `ddr: [DDR-N]` 引用；双向闭环——字段引用的 DDR 必须存在（悬空拦截），DDR 必须被字段
  引用或声明 `unreferenced_reason` 全局豁免（孤儿拦截）；渲染器生成 `ddr-index` + `ddr-matrix`
  （字段×决策矩阵）；
- 孤儿条目拦截（收录却无人引用须 `unreferenced_reason`）；客户端/迁移声明自洽（not-applicable 与
  四方言偏离必须显式说明）；零结果双向闭环（空集合必须 `zero_results` 声明，声明必须指向
  真实空集合）；占位话术全文递归拦截。

**证据规范**：锚点是证据位——必须指向当前详设/PRD 真实章节；定位器（codegraph、历史
文档）只负责找位置，不是证据。空集合不声明 = 校验拦截。
