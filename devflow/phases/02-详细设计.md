# Phase 2: 详细设计 (Detailed Design)

## 目标

把冻结的 PRD 验收点和技术选型，转成可直接施工的契约：数据、接口、规则、权限、迁移、前端、实现交接与验证策略。
**设计"长什么样"由模板定义**；本阶段文件只定义：做什么、按什么顺序做、以什么判停。

**经验教训应用**：
- L-P2-001：跨模板视图必须独立文件，禁止硬链接
- L-P2-003：表结构对账必须在 P2 冻结前完成
- 详见 `concepts/lessons-learned.md`

## 输入

- `docs/需求/<feature>-需求澄清.md`、`<feature>-验收点.md`（P0 FROZEN）、`<feature>-技术约束.md`
- `docs/详细设计/<feature>-技术选型.md`（P1）与 7 份工程事实源（`_commons.md`、`_权限矩阵.md`、`_环境与账号.md`、`_菜单Seed索引.md`、`INDEX-*.md`）
- 现有代码库与现有测试（实现交接的基线事实源）

## 第 1 步：现有代码基线调查（先调查，后设计）

写任何设计结论前必须先调查并记录（产出即模板「实现交接」节，`<!-- anchor: implementation-handoff -->`）：

1. 定位入口与调用链：Controller/路由/事件入口 → Service → Repository → 表；
2. 查找可复用的同类实现：相似接口、相似页面、相似迁移脚本；
3. 查找现有工具与公共组件：分页、校验、导出、鉴权、缓存、消息；
4. 查明现有测试模式：命名、夹具、可运行命令；
5. 确定最小修改文件集合。

绿地项目在基线表写"新增"，证据列为计划新增路径；存量项目必须给出真实文件路径。
调查结论与设计意图冲突（如"复用 X"但 X 不存在）必须在 P2 内解决，不得带入 P3。

## 第 2 步：选择模板并声明身份

从 `templates/详细设计-模板.md`（路由器）选择模式：

| 模式 | 适用 | 模板 |
|------|------|------|
| 单体 | 简单功能、单模块 | `详细设计-完整版-模板.md` |
| 总分总 | 多模块、需全局视图 | `详细设计-总分总文档-模板.md` |
| 总分分 | 总文档下的模块分文档 | `详细设计-总分分文档-模板.md` |

产物必须声明精确的模板 ID 与版本：把模板中的 `{{template_version}}` 替换为该模板 frontmatter 的 version
（`s2` Gate 与模板逐字对账）。禁止用本阶段文件或旧版本模板里的示例骨架代替当前模板。

## 第 3 步：必须解决的设计问题（锚点为定位正本）

- **数据模型**（`<!-- anchor: data-model -->`）：ER、全字段表结构（五列，禁止"关键字段"式省略）、索引、关键字规避（`references/db-reserved-words.md`）、DDR 决策记录；
- **接口契约**（`<!-- anchor: api-contracts -->`）：概览↔详细定义一一对应、请求/响应双六列表、错误语义；
- **业务规则**（`<!-- anchor: business-rules -->`）：R 编号、WHEN 准伪代码与关键流程时序；
- **权限矩阵**：权限码、数据范围、按钮/菜单可达性；
- **前端契约**：页面清单、页面与接口映射、路由/状态/复用组件（`references/frontend-tech-stack.md`）；
- **迁移与种子**：脚本清单、初始数据、多方言一致性（适用时）；
- **技术约束逐条引用**：P0 冻结的每个 constraint_id 必须在详设中出现并给出落点；
- **验收追溯矩阵**（`<!-- anchor: acceptance-traceability -->`）：与验收点冻结集合全等，全部 COMPLETE；
- **组件复用与公共抽取**：复用优先级——项目现有能力 > 项目现有依赖 > JDK/框架标准能力 > 新增第三方依赖（必须写成 Design Decision）> 自研；≥2 消费方的能力必须抽取登记；
- **实现交接**（`<!-- anchor: implementation-handoff -->`）：现有实现基线、预计代码变更（ADD/MODIFY/DELETE）、不变量清单；
- **零结果显式声明**：不涉及的表/接口/资源必须 `zero_results` 声明——空集合也是证据。

## 关键原则

1. **明确无歧义**：每个设计点有结论，不留模糊地带；
2. **说人话**：中文表达遵循 `concepts/中文文风规范.md`，不把校验器/Gate 内部机制写进正文；
3. **可落地**：考虑实现难度与最小改动面；
4. **保持一致**：命名、口径、错误语义一致；
5. **演进约束**：优先满足当前冻结需求；仅当已有兼容性约束、明确扩展需求或至少两个实际消费者时才建立扩展点；禁止为假想需求引入抽象层或新增表、接口、中间件。

## 结构化产物层（v3.17.0 · design.json）

> AI 只填语义层（设计判断、锚点、证据）；编号、计数、覆盖率、追溯矩阵、索引表由脚本派生（确定性层）。

| 产物 | 位置 | 说明 |
|------|------|------|
| `design.json` | `.devflow/<feature>/design.json` | 机器可读业务产物，契约见 `schemas/design.schema.json` |
| 详设文档 | `docs/详细设计/<feature>-详细设计.md` | 骨架中嵌入 `<!-- df:begin:KEY -->`/`<!-- df:end:KEY -->` 锚点块，由渲染器整体重写 |

**管线（单一失败关闭入口，禁止跳过校验直接渲染）**：

```bash
python3 "$SKILL_ROOT/scripts/df_pipeline.py" design \
  --input .devflow/<feature>/design.json \
  --doc docs/详细设计/<feature>-详细设计.md \
  --criteria docs/需求/<feature>-验收点.md \
  --gate bash "$SKILL_ROOT/scripts/s2_design_coverage_gate.sh" \
         docs/详细设计/<feature>-详细设计.md \
         docs/需求/<feature>-验收点.md --mode=monolith
```

**确定性层锚点块**（KEY 共 10 个，骨架缺块即渲染失败）：`summary`、`trace-matrix`、
`table-index`、`api-index`、`permission-matrix`、`rule-index`、`client-scope`、`zero-results`、
`ddr-index`、`ddr-matrix`。

**跨字段校验**（`df_validate.py --kind design`，s2 Gate §2c 必填强制）：

- 验收 ID 唯一 + 与 criteria 冻结集合全等；锚点引用闭环（page/api/data/rule 必须指向真实条目）；
- **接口概览 ↔ 详细定义一一对应**：每个 API 必填 `detail_anchor`（§3.2.N）+ `name`；monolith 模式对文档
  双向对账（概览列了 N 个、详细定义只写 M<N 个即拦截，多余小节同样拦截）；
- **DDR ↔ 字段一一对应**：`decisions[]` + 每个表字段必填 `ddr: [DDR-N]` 双向闭环（悬空/孤儿拦截），
  渲染器生成 `ddr-index` + `ddr-matrix`（字段×决策矩阵）；
- 孤儿条目拦截（收录却无人引用须 `unreferenced_reason`）；客户端/迁移声明自洽（not-applicable 与
  多方言偏离必须显式说明）；零结果双向闭环——空集合必须 `zero_results` 声明，声明必须指向真实空集合；
  占位话术全文递归拦截。

**证据规范**：锚点是证据位——必须指向当前详设/PRD 真实章节；定位器（codegraph、历史文档）只负责
找位置，不是证据。

## 分文档状态同步（总分模式）

分文档创建即初始化总文档状态为 `🔄`；分文档完成后更新为 `✅` 并同步验收点数与变更历史。完成的分文档在
总文档仍有 `⏳` 即视为未完成——输出同步后的 diff 作为证据。

## Gate 检查

```bash
bash "$SKILL_ROOT/scripts/s2_design_coverage_gate.sh" docs/详细设计/<feature>-详细设计.md docs/需求/<feature>-验收点.md
bash "$SKILL_ROOT/checks/check-arch-pitfalls.sh" --category config
```

| 检查项 | 通过条件 |
|--------|----------|
| 字段级覆盖 = 100% | `s2_design_coverage_gate.sh` exit = 0 |
| 需求追溯 = P0 验收点 | 验收 ID 集合相等 |
| 语义锚点齐备 | data-model / api-contracts / business-rules / acceptance-traceability / implementation-handoff |
| 架构陷阱 = 0 | `check-arch-pitfalls.sh` exit = 0 |
| 结构化产物层对账 | `design.json` 存在时 §2c 校验必须通过（schema + 跨字段 + criteria 全等） |

## Gate 失败处理

Gate 非零即停止（铁律 8）：保存 checkpoint → 修复根因 → 重跑**同一 Gate**，通过前不得进入 P3；
禁止用放宽阈值、删追溯行、跳过 design.json 校验来"绕过"。

## 输出

- 详设文档：`docs/详细设计/<feature>-详细设计.md`（模板 ID + 版本已声明，语义锚点齐备）；
- 结构化层：`.devflow/<feature>/design.json`；
- 实现交接：详设内 `anchor: implementation-handoff` 节——供 `/plan` 生成执行契约、`/build` 开工前对账。
