# Phase 2: 详细设计 (Detailed Design)

## 目标

把冻结的 PRD 验收点和技术选型，转成可直接施工的契约：数据、接口、规则、权限、迁移、前端、实现交接与验证策略。
**设计"长什么样"由模板定义**；本阶段文件只定义：做什么、按什么顺序做、以什么判停。

**经验教训应用**：
- L-P2-001：跨模板视图必须独立文件，禁止硬链接
- L-P2-003：表结构对账必须在 P2 冻结前完成
- 详见 `concepts/lessons-learned.md`

## 输入

- `docs/需求/<feature>-需求澄清.md`、`<feature>-验收点.md`（P0 FROZEN）、`<feature>-技术约束.md`
- `docs/详细设计/<feature>-技术选型.md`（P1，含《详设文档结构决策》：monolith/total 与《脚手架重合度审计》裁剪/复用清单）与 7 份工程事实源（`_commons.md`、`_权限矩阵.md`、`_环境与账号.md`、`_菜单Seed索引.md`、`INDEX-*.md`）
- 现有代码库与现有测试（实现交接的基线事实源）
- 输入物料（若提供）：原型图/交互稿、设计规则、UI 规范——**设计硬约束**（铁律 19）

## 输入物料优先（铁律 19）

提供原型/设计规则/UI 规范时，详设的布局、组件选型、交互状态与文案口径必须**遵循物料**；
脚手架既有设计只作为实现载体参考，不得以其默认样式/交互/信息架构覆盖物料。冲突时 `STATUS=BLOCKED`
回用户裁决。物料为图片/链接时，须在详设落为可执行规格并锚定原物料路径；未提供物料方可采用
脚手架默认口径并显式声明。

## 脚手架裁剪承接（铁律 18）

P1「裁剪/复用清单」在详设的承接为硬要求：

- 「裁剪」项 → baseline `DELETE`/`MODIFY`（含菜单下线、前端页面移除、迁移清理的动作与目标路径）；
- 「复用」项 → baseline `REUSE`（真实文件路径 + 现有契约）；
- 「新建」项 → baseline `ADD`（所属模块与同类模式参照）；
- **禁止双实现并存**：详设不得为同一功能域同时保留脚手架旧实现与本次新实现的两套入口；
- 菜单 seed、路由注册、权限矩阵与裁剪清单三向一致（P2a/P4b 逐项核验）。

## 增量/修改点标记（change/extend 模式强制）

> **适用**：`--mode=change|extend` 或任何承接存量设计/代码的增量需求；`--mode=new`（绿地）不适用。
> **原则**：**新建不标记**——新建表/接口/页面/菜单/迁移脚本/错误码等属 obviously 的新交付物，在各章正文自然呈现，不加任何标记；仅当**触及既有产物**（存量表、既有接口、既有页面/公共组件、事实源文件、既有行为语义）时，必须以【标记】在落点处显式标注，使"本次改了什么"一眼可辨、可独立施工、可单独评审。

### 标记词汇（可按领域扩展，格式恒为【前缀-说明】）

| 标记 | 用途 | 必须给出的配套信息 |
|---|---|---|
| 【增量字段】 | 修改既有表：增列/改列并回填 | 承载迁移脚本（ALTER+回填语句口径）、回填值口径 |
| 【修改-行为】 | 既有接口/规则的行为增量 | 声明「接口签名不变」+ 新增处置内容与驱动关系 |
| 【追加登记】 | 修改既有事实源（_权限矩阵/_菜单Seed索引/INDEX-*） | 追加的行内容；已交付的注明 |
| 【扩展-公共层】 | 修改既有公共组件/工具行为 | 既有文件真实路径 + 行为扩展点 |

### 落点要求（三处同源，缺一即 P2a 退回）

1. **详设总表**：§0.1（或等价位置）给「增量/修改点标记」总表（标记/含义/本次落点三列），并在 §0 文档结构中登记该节；
2. **正文内联**：每个触及点所在章节（表结构标题或引导句/接口概览/页面清单/依赖项）以【标记】内联标注；
3. **实现交接**：施工清单分「新建（无标记，一句话清单）」与「增量/修改点（M-NN 逐行编号：标记/对象/修改内容/锚点）」两节——/plan、/build 只需盯 M-NN 改动面。

P2a 评审委员会按本节核对：change/extend 交付若缺增量/修改点标记（或标记了新建物），按评审发现（DF）记录并退回补正。

## 第 1 步：现有代码基线调查（先调查，后设计）

写任何设计结论前必须先调查并记录（产出即《实现交接》文档 `docs/详细设计/<feature>-实现交接.md`，`<!-- anchor: implementation-handoff -->`）：

1. 定位入口与调用链：Controller/路由/事件入口 → Service → Repository → 表；
2. 查找可复用的同类实现：相似接口、相似页面、相似迁移脚本；
3. 查找现有工具与公共组件：分页、校验、导出、鉴权、缓存、消息；
4. 查明现有测试模式：命名、夹具、可运行命令；
5. 确定最小修改文件集合。

绿地项目在基线表写"新增"，证据列为计划新增路径；存量项目必须给出真实文件路径。
调查结论与设计意图冲突（如"复用 X"但 X 不存在）必须在 P2 内解决，不得带入 P3。

**机器契约（v3.24.0/A02）**：基线调查结果必须登记进 design.json `baseline.entries[]`——
每条含稳定 ID（BL-N）、目标（文件或 文件#符号）、REUSE/MODIFY/ADD/DELETE 决策、现有契约
（REUSE/MODIFY 必填）、验证方式；Gate 在仓库内反查：**REUSE/MODIFY/DELETE 目标不存在即 FAIL**
（虚构 `MODIFY FooController#list` 直接拦截）；ADD 须声明所属模块与同类模式；数据库证据用
`baseline.db_evidence` 区分迁移脚本静态事实与目标库实际 schema，缺运行证据不得推断已部署。

## 第 2 步：按 P1 冻结结构取模板并声明身份

详设写单文档还是总分文档，**已在 P1 设计决策记录决策并冻结**（设计决策记录《详设文档结构决策》，
JSON `design_doc_structure.mode`，机检行 `design_doc_structure_mode=`）。本步只按冻结结果取模板，
不再做总分/单体决策、不写决策矩阵；认为结构不适用时回 P1 走变更。

| P1 冻结 mode | 模板 | Gate |
|------|------|------|
| `monolith`（单文档，默认） | `详细设计-完整版-模板.md` | `--mode=monolith` |
| `total` · 总文档 | `详细设计-总分总文档-模板.md` | `--mode=total` |
| `total` · 分文档 | `详细设计-总分分文档-模板.md` | `--mode=sub` |

s2 Gate 的 `--mode` 必须与 P1 冻结 mode 一致（错配即 FAIL）；总分模式的计划文档清单以 P1
`design_doc_structure.planned_docs` 为准，第 2 步后续据此冻结 design-package.json。

产物必须声明精确的模板 ID 与版本：把模板中的 `{{template_version}}` 替换为该模板 frontmatter 的 version
（`s2` Gate 与模板逐字对账）。禁止用本阶段文件或旧版本模板里的示例骨架代替当前模板。

## 第 3 步：必须解决的设计问题（锚点为定位正本）

- **数据模型**（`<!-- anchor: data-model -->`）：ER、全字段表结构（五列，禁止"关键字段"式省略）、索引、关键字规避（`references/db-reserved-words.md`，df_validate 对表名/字段名按 fail/warn 分层机检——fail 层命中即 FAIL）；
- **数据库设计决策（v3.27.15 · 移出详设）**：DDR 与迁移独立成文 `docs/详细设计/<feature>-数据库设计决策.md`（`anchor: design-decisions`；design.json `decisions[]`/`migrations` 为正本，经管线 `--db-doc` 渲染）；迁移节含场景判型、Flyway 四方言脚本、初始数据；
- **接口契约**（`<!-- anchor: api-contracts -->`）：概览↔详细定义一一对应、请求/响应双六列表、错误语义；
- **业务规则**（`<!-- anchor: business-rules -->`）：R 编号、WHEN 准伪代码与关键流程时序；
- **业务操作契约**（`<!-- anchor: business-operations -->`，v3.24.0/A01）：以业务命名操作全集
  （非 CRUD 枚举，如 删除→回收站→恢复→彻底删除 各自成操作），逐项覆盖触发者、输入、前置校验、
  源/目标状态（无状态显式 `stateless=true`）、执行顺序、事务/并发、用户可见结果、失败路径、
  关联对象处置、副作用与测试场景；冻结验收点的每项操作必须有落点（`business_operations[].acceptance_refs`
  并集 = 冻结验收集合，缺项即 Gate FAIL）；无数据/无 API/纯任务场景同样适用；
- **权限矩阵**：权限码、数据范围、按钮/菜单可达性；
- **权限/可见性语义边界（v3.27.6 · L-M01-012）**：明确「新建对象是否自动可见/自动授权」——管理员/内置角色对**创建后未授权对象**的可见性（全量旁路还是仅权限组绑定）、默认权限组绑定策略；禁止留给实现推断（M01 教训：R29 只定义合成口径未定义 admin 对新菜单语义，实现半套自创旁路致不一致缺陷）；
- **字段格式规范（v3.27.6 · L-M01-012）**：API 层时间字段一律类型化（LocalDateTime 等）走全局序列化约定；确需 String 承载的，字段表必须同时冻结输出格式（如 `yyyy-MM-dd HH:mm:ss`）——禁止只写 `string` 不写格式（M01 教训：5 处实现各自 ISO 格式化致前端显示混乱）；
- **前端契约**：页面清单（§7.1 唯一 UI 面清单：独立路由页面 + **全部弹窗/抽屉**，design.json `pages[]` 必填字段；**页面判定口径**=有独立路由可直达视图，页内区域不计页，PRD 称"XX页"但设计为页内区域的须写明判定理由；**完整性三向对账**=菜单 seed × client.journeys × UI 验收点，示例行数不代表规模）、**页面交互设计**（§7.2，逐交互单元写：布局/查询区（有/无）/列表（有/无）/表单（有/无）/调用接口/操作/业务规则/状态矩阵/降级 + **弹窗/抽屉表**——原 §7.3 映射表已并入（组件+接口锚点闭环 ↔`dialogs`）；操作触发弹窗/抽屉写「→ 弹窗/抽屉：{交互名}」；规格表按形态：有列表↔`table_columns`、有表单（含弹窗内表单）↔`form_controls`，混合都写；**链路**：规格表「链路」列合并写 `§x.y.z 字段 ←/→ 表.字段`（JSON 拆 api_field/source 提供即对账），操作表「关联」列合并 `§x.y.z · BOP-n · Rn`，接口表带涉及表/BOP——页面元素→接口→表→规则/操作全链闭环，悬空引用机检 FAIL）、路由/状态/复用组件（`references/frontend-tech-stack.md`）；配置类客户端另见 `docs/devflow-client.json` 冻结）、**测试锚点**：全部可交互控件必填 `test_anchor`——表单控件（`form_controls[]`）、操作按钮（`actions[]`：页面/工具栏/行操作/批量按钮正本）、弹窗/抽屉（`dialogs[]`）——命名公式 `<feature缩写>-p<页面序号>-<类型>-<名称slug>`（类型枚举 input/select/date/switch/btn/dialog/row），全文档唯一（df_validate 机检），实现层以 `data-testid` 属性承载，P5/P6e 测试定位符只允许引用冻结锚点；
- **迁移与种子**：脚本清单、初始数据、多方言一致性（适用时）；
- **技术约束逐条引用**：P0 冻结的每个 constraint_id 必须在详设中出现并给出落点；
- **验收追溯矩阵**（`<!-- anchor: acceptance-traceability -->`）：与验收点冻结集合全等，全部 COMPLETE；
- **组件复用与公共抽取**：复用优先级——项目现有能力 > 项目现有依赖 > JDK/框架标准能力 > 新增第三方依赖（必须写成 Design Decision）> 自研；≥2 消费方的能力必须抽取登记；

- **零结果显式声明**：不涉及的表/接口/资源必须 `zero_results` 声明——空集合也是证据。
- **锚点具体化（v3.26.10 · L-P2-004）**：每张表独立锚点 §2.2.N、每个接口 anchor=detail_anchor=§3.2.N、每个页面独立锚点 §7.1.N、业务操作锚点 §6.2.N；`#### 6.2.N` 操作小节必须挂在 `### §6.2 业务操作契约（BOP-1～BOP-N）` 父级标题下、`#### 7.2.N` 页组小节必须挂在 `### §7.2 页面交互设计` 父级标题下（N.M.K 缺 N.M 父级即层级断裂，df_validate L-HIER-1 拦截）；需求追溯矩阵（在 `<feature>-需求追溯.md`）页面/接口/数据三列必须引用上述具体锚点（写 §7.1/§3.1/§2.2 通用锚点即 L-P2-004 断链，df_validate 拦截）；§3.2 小节标题只写编号+名称（方法/路径/权限与功能说明合并放标题下首行 `> 说明：METHOD 路径｜权限：…｜功能：…`）；§7.2 页组覆盖 §7.1 全部页面并逐组列出调用接口。

## 关键原则

1. **明确无歧义**：每个设计点有结论，不留模糊地带；
2. **说人话**：中文表达遵循 `concepts/中文文风规范.md`，不把校验器/Gate 内部机制写进正文；
3. **可落地**：考虑实现难度与最小改动面；
4. **保持一致**：命名、口径、错误语义一致；
5. **演进约束**：优先满足当前冻结需求；仅当已有兼容性约束、明确扩展需求或至少两个实际消费者时才建立扩展点；禁止为假想需求引入抽象层或新增表、接口、中间件。

**跨字段校验**（`df_validate.py --kind design`，s2 Gate §2c 必填强制）：

- 验收 ID 唯一 + 与 criteria 冻结集合全等；锚点引用闭环（page/api/data/rule 必须指向真实条目）；
- **接口概览 ↔ 详细定义一一对应**：每个 API 必填 `detail_anchor`（§3.2.N）+ `name`；全模式对文档
  双向对账（概览列了 N 个、详细定义只写 M<N 个即拦截，多余小节同样拦截）；
- **业务操作覆盖闭环（A01）**：`business_operations[].acceptance_refs` 并集 = 冻结验收集合，
  悬空引用与覆盖缺口（漏"恢复""彻底删除"等）均拦截；有状态操作必须同时声明源/目标状态；
- **真实代码基线（A02）**：`baseline.entries[]` 的 REUSE/MODIFY/DELETE 目标在仓库内反查存在，
  ADD 须声明 `target_module`，每条带验证方式；
- **正文事实对账（A03/A04）**：`prd_anchor` 来源文件必须存在；嵌套锚点（request/response/journey.page）
  闭环；JSON 字段清单与正文表格首列一致、类型不冲突；锚点小节不得是空壳；
- **DDR ↔ 字段一一对应**：`decisions[]` + 每个表字段必填 `ddr: [DDR-N]` 双向闭环（悬空/孤儿拦截），
  渲染器把 `ddr-index` + `ddr-matrix`（字段×决策矩阵）写入数据库设计决策文档（`--db-doc`）；
- 孤儿条目拦截（收录却无人引用须 `unreferenced_reason`）；客户端/迁移声明自洽（`client.scope=not-applicable`
  必填理由；`migrations.applicable=false` 必填 `not_applicable_reason`、适用时 `dialects` 四方言齐全或写
  `dialect_exception`；`client.journeys[]` 逐条给页面锚点+证据形态，客户端范围与 P0 冻结 state 对账）；
  `constraints[]` 使用时与 P0 冻结约束集合闭环（s2 §2b 反查，重复由 df_validate 拦截）；
  **测试隔离策略必填（v3.28.14，m01-base 教训：跨类登录态污染致 P3 集成测试三轮返工）**：
  `test_isolation.applicable=true` 必填 `strategy`（隔离手段）+ 建议 `shared_state`（共享态清单与处置）与
  `cleanup`（try/finally 自清理、置空显式 `set(field, null)`——L-M01-015）；不适用必填
  `not_applicable_reason`——隔离在 P2 冻结，不留到 P3 才发现；
  零结果双向闭环——空集合必须 `zero_results` 声明，声明必须指向真实空集合；占位话术全文递归拦截
  （正文围栏外残留 `{xxx}` 花括号变量同样拦截）。

**证据规范**：锚点是证据位——必须指向当前详设/PRD 真实章节；定位器（codegraph、历史文档）只负责
找位置，不是证据。

## 分文档状态同步（总分模式）

分文档创建即初始化总文档状态为 `🔄`；分文档完成后更新为 `✅` 并同步验收点数与变更历史。完成的分文档在
总文档仍有 `⏳` 即视为未完成——输出同步后的 diff 作为证据。

## Gate 检查

```bash
bash "$SKILL_ROOT/scripts/s2_design_coverage_gate.sh" docs/详细设计/<feature>-详细设计.md docs/需求/<feature>-验收点.md --mode=<P1 冻结 mode: monolith|total|sub>
bash "$SKILL_ROOT/checks/check-arch-pitfalls.sh" --category config
# local-patch:design-quality v1 — 项目内容充分性 lint（存在即必跑；规则 docs/design-quality-rules.json）
[ -f scripts/check_design_doc_quality.py ] && python3 scripts/check_design_doc_quality.py --doc docs/详细设计/<feature>-详细设计.md
```

| 检查项 | 通过条件 |
|--------|----------|
| 字段级覆盖 = 100% | `s2_design_coverage_gate.sh` exit = 0 |
| 需求追溯 = P0 验收点 | 验收 ID 集合相等 |
| 语义锚点齐备 | data-model / api-contracts / business-rules / acceptance-traceability / implementation-handoff |
| 文档结构来源 P1 | 选型报告含详设文档结构决策（`design_doc_structure_mode=` 机检行）；s2 `--mode` 与其一致；详设不内嵌总分/单体决策矩阵 |
| 架构陷阱 = 0 | `check-arch-pitfalls.sh` exit = 0 |
| 结构化产物层对账 | `design.json` 存在时 §2c 校验必须通过（schema + 跨字段 + criteria 全等） |

## Gate 失败处理

Gate 非零即停止（铁律 8）：保存 checkpoint → 修复根因 → 重跑**同一 Gate**，通过前不得进入 P3；
禁止用放宽阈值、删追溯行、跳过 design.json 校验来"绕过"。

## 输出

- 详设文档：`docs/详细设计/<feature>-详细设计.md`（模板 ID + 版本已声明，语义锚点齐备）；
- 结构化层：`.devflow/<feature>/design.json`；
- 实现交接：详设内 `anchor: implementation-handoff` 节——供 `/plan` 生成执行契约、`/build` 开工前对账。
