# Phase 8: 监控配置 (Monitoring)

## 目标

- 配置全面的监控覆盖
- 设置合理的告警规则
- 建立监控大盘
- 确保问题能快速发现

---

## 监控四大黄金指标

| 指标 | 说明 | 关注点 |
|------|------|--------|
| **延迟** | 请求响应时间 | 平均、P50、P90、P99 |
| **流量** | 系统吞吐量 | QPS、并发数 |
| **错误** | 请求失败率 | 错误率、错误类型 |
| **饱和度** | 系统利用率 | CPU、内存、连接数 |

---

## 监控分层

```
┌─────────────────────────────────────┐
│           业务监控层                │
│  (业务指标、转化率、功能使用)       │
├─────────────────────────────────────┤
│           应用监控层                │
│  (接口响应、错误率、调用链)         │
├─────────────────────────────────────┤
│           中间件监控层              │
│  (数据库、缓存、消息队列)           │
├─────────────────────────────────────┤
│           基础设施监控层            │
│  (服务器、网络、存储)               │
└─────────────────────────────────────┘
```

## 必须监控的指标

### 应用层
| 指标 | 描述 | 告警阈值建议 |
|------|------|--------------|
| HTTP请求量 | 每秒请求数 | - |
| HTTP响应时间 | P50/P90/P99 | P99 > 1s |
| HTTP错误率 | 4xx/5xx比例 | > 1% |
| JVM堆内存 | 内存使用率 | > 80% |
| GC频率 | Full GC次数 | > 1次/天 |

### 中间件层
| 组件 | 指标 | 告警阈值 |
|------|------|----------|
| MySQL | 连接数、慢查询 | 连接 > 80%，慢查询 > 100/s |
| Redis | 内存使用、命中率 | 内存 > 80%，命中率 < 90% |
| Kafka | 消费延迟、堆积 | 堆积 > 10000 |

### 基础设施层
| 指标 | 描述 | 告警阈值 |
|------|------|----------|
| CPU使用率 | CPU使用百分比 | > 80% |
| 内存使用率 | 内存使用百分比 | > 85% |
| 磁盘使用率 | 磁盘空间使用率 | > 80% |
| 网络IO | 进/出带宽 | > 80% |

## 告警配置模板

```markdown
# 告警规则配置

## 服务可用性告警
| 告警名称 | 条件 | 级别 | 通知方式 |
|----------|------|------|----------|
| 服务宕机 | status != 1 | P0 | 电话+短信 |
| 健康检查失败 | health == false | P1 | 短信 |
| 错误率升高 | error_rate > 5% | P1 | 短信 |
| 响应时间异常 | p99 > 3s | P2 | 钉钉/邮件 |

## 资源告警
| 告警名称 | 条件 | 级别 | 通知方式 |
|----------|------|------|----------|
| CPU过高 | cpu > 80% | P2 | 钉钉 |
| 内存过高 | memory > 85% | P2 | 钉钉 |
| 磁盘将满 | disk > 80% | P1 | 短信 |

## 业务告警
| 告警名称 | 条件 | 级别 | 通知方式 |
|----------|------|------|----------|
| 订单失败率 | order_fail_rate > 5% | P1 | 短信 |
| 支付成功率 | pay_success < 95% | P0 | 电话+短信 |
```

## 应用经验教训

### L-MON-001: build-watchdog 必须留痕

**教训**：devflow 规范要求 P3 编码阶段每次写完代码自动触发 `build-watchdog.sh check`，但实施中未找到 build-watchdog 执行记录，无法证明"写完即编译"的持续验证，也无法追溯编译错误的修复历史。

**本阶段应用**（监控类比）：
- P8 监控配置必须有执行记录（证明监控真实部署）
- 监控告警测试必须留痕（证明告警通道可用）
- 监控配置变更必须记录（可追溯）

**预防措施**：
1. P8 监控配置产物必须保存到 `docs/发布/<feature>-监控配置.md`
2. 告警测试必须记录测试时间、测试结果、通知截图
3. 监控大盘链接必须保存（可访问验证）

**参考**：详见 `concepts/lessons-learned.md` L-MON-001

---

### L-MON-002: checkpoint-state 必须记录中断恢复点

**教训**：devflow 规范要求每次 Gate 跑完后 + 会话中断前执行 `checkpoint-state.sh`，但实施中只有 state.json 包含 6 个 checkpoint，缺少对应的执行日志，无法追溯每个 checkpoint 的触发时机与保存内容，会话中断后恢复时缺少上下文。

**本阶段应用**：
- P8 监控配置完成后必须执行 checkpoint-state.sh
- 记录当前监控配置状态（指标、告警、大盘）
- 确保后续阶段（P9/P10）可恢复上下文

**预防措施**：
1. P8 Gate 完成后自动触发 checkpoint-state.sh
2. checkpoint 日志必须保存到 `.devflow/<feature>/checkpoints/<id>.log`
3. 每次 checkpoint 记录当前阶段、待办事项、阻塞原因

**参考**：详见 `concepts/lessons-learned.md` L-MON-002

---

### L-MON-003: orphans-detector 必须定期执行

**教训**：devflow 规范要求任何 P 阶段完成后执行 `checkpoint-state.sh orphans` 检测孤岛产物，但实施中未找到孤岛检测报告，无法证明 docs/ 和代码之间没有孤岛产物，可能存在未被引用的文档或代码。

**本阶段应用**：
- P8 监控配置完成后执行 orphans-detector
- 检测是否有配置了但未使用的监控指标
- 检测是否有配置了但从未触发的告警规则

**预防措施**：
1. P8 Gate 完成后执行 `checkpoint-state.sh orphans`
2. 孤岛检测报告保存到 `.devflow/<feature>/orphans-report.txt`
3. 清理或标注未使用的监控配置

**参考**：详见 `concepts/lessons-learned.md` L-MON-003
