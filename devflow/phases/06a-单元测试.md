# Phase 6a: 单测补齐

> 报告产物：`docs/测试/<feature>-单元测试报告.md`（历史英文名 `*-unit-report.md` 继续可被 Gate 解析，新产物用中文名）。

## 目标

补充单元测试，确保核心业务逻辑的测试覆盖率 ≥ 80%。

---

## 实施步骤

### Step 1: 分析当前覆盖率

```bash
# 生成覆盖率报告
mvn test jacoco:report / npm test -- --coverage

# 查看覆盖率
open target/site/jacoco/index.html
```

### Step 2: 识别未覆盖代码

从覆盖率报告中识别：
- 未测试的类
- 未测试的方法
- 未覆盖的分支

### Step 3: 补充测试用例

按优先级补充：

```
优先级:
1. 核心业务逻辑类
2. 复杂算法类  
3. 边界条件处理
4. 异常处理逻辑
5. 工具类
```

### Step 4: 验证覆盖率

补充后重新运行覆盖率，确保达标。

## 测试代码模板

### Java JUnit 5 + Mockito

```java
@ExtendWith(MockitoExtension.class)
class XxxServiceTest {

    @Mock
    private XxxRepository repository;
    
    @Mock
    private YyyService yyyService;
    
    @InjectMocks
    private XxxService service;
    
    @Test
    @DisplayName("正常流程 - 创建用户成功")
    void createUser_Success() {
        // Given
        CreateUserRequest request = CreateUserRequest.builder()
            .username("testuser")
            .email("test@example.com")
            .password("Password123!")
            .build();
            
        when(repository.existsByUsername("testuser")).thenReturn(false);
        when(repository.save(any(User.class))).thenAnswer(inv -> {
            User user = inv.getArgument(0);
            user.setId(1L);
            return user;
        });
        
        // When
        User result = service.createUser(request);
        
        // Then
        assertNotNull(result);
        assertEquals(1L, result.getId());
        assertEquals("testuser", result.getUsername());
        
        verify(repository).existsByUsername("testuser");
        verify(repository).save(any(User.class));
    }
    
    @Test
    @DisplayName("异常流程 - 用户名已存在")
    void createUser_UsernameExists_ThrowsException() {
        // Given
        CreateUserRequest request = CreateUserRequest.builder()
            .username("existing")
            .email("test@example.com")
            .password("Password123!")
            .build();
            
        when(repository.existsByUsername("existing")).thenReturn(true);
        
        // When & Then
        BusinessException exception = assertThrows(
            BusinessException.class,
            () -> service.createUser(request)
        );
        
        assertEquals("USER_USERNAME_EXISTS", exception.getCode());
        verify(repository, never()).save(any());
    }
    
    @Test
    @DisplayName("边界条件 - 用户名为空")
    void createUser_NullUsername_ThrowsException() {
        // Given
        CreateUserRequest request = CreateUserRequest.builder()
            .username(null)
            .email("test@example.com")
            .password("Password123!")
            .build();
            
        // When & Then
        assertThrows(BusinessException.class,
            () -> service.createUser(request));
    }
    
    @ParameterizedTest
    @CsvSource({
        "a, false",           // 太短
        "ab, false",          // 太短
        "abcdefghijklmnop, false", // 太长
        "validuser, true"     // 正常
    })
    @DisplayName("参数化测试 - 用户名长度验证")
    void validateUsername_Length(String username, boolean expected) {
        boolean result = service.validateUsername(username);
        assertEquals(expected, result);
    }
}
```

### JavaScript/TypeScript Jest

```typescript
describe('UserService', () => {
  let userService: UserService;
  let mockRepository: jest.Mocked<UserRepository>;
  let mockEventBus: jest.Mocked<EventBus>;
  
  beforeEach(() => {
    mockRepository = {
      findByUsername: jest.fn(),
      save: jest.fn(),
    } as any;
    
    mockEventBus = {
      emit: jest.fn(),
    } as any;
    
    userService = new UserService(mockRepository, mockEventBus);
  });
  
  describe('createUser', () => {
    it('should create user successfully', async () => {
      // Given
      const input: CreateUserInput = {
        username: 'testuser',
        email: 'test@example.com',
        password: 'Password123!',
      };
      
      mockRepository.findByUsername.mockResolvedValue(null);
      mockRepository.save.mockResolvedValue({
        id: 1,
        ...input,
      });
      
      // When
      const result = await userService.createUser(input);
      
      // Then
      expect(result).toMatchObject({
        id: 1,
        username: 'testuser',
      });
      expect(mockEventBus.emit).toHaveBeenCalledWith('user.created', { userId: 1 });
    });
    
    it('should throw error when username exists', async () => {
      // Given
      mockRepository.findByUsername.mockResolvedValue({ id: 1, username: 'existing' });
      
      // When & Then
      await expect(
        userService.createUser({
          username: 'existing',
          email: 'test@example.com',
          password: 'Password123!',
        })
      ).rejects.toThrow(UserAlreadyExistsError);
    });
  });
});
```

## Red Flags 🚩

以下情况必须停止并汇报：

| 红旗 | 问题 | 正确做法 |
|------|------|----------|
| 测试覆盖率不足 | "80%太高了" | 必须达标 |
| 测试相互依赖 | 顺序执行才能过 | 必须独立 |
| 测试永远通过 | 无实际断言 | 必须验证结果 |
| Mock所有依赖 | 无真实测试 | 必须测真实逻辑 |
| 测试不运行 | "CI会跑的" | 必须本地验证 |

---

## 常见问题处理

| 问题 | 解决方案 |
|------|----------|
| 私有方法测试 | 考虑重构为独立类，或通过公共方法间接测试 |
| 依赖外部服务 | Mock外部服务 |
| 依赖数据库 | 使用内存数据库(H2/SQLite)或Mock |
| 测试太慢 | 使用@MockitoExtension并行化 |
| 测试不稳定 | 解决测试间的状态泄漏 |

---

## 关键原则

1. **可读性** - 测试代码也要像生产代码一样整洁
2. **独立性** - 每个测试独立运行，不依赖其他测试
3. **可维护性** - 测试数据使用工厂方法创建
4. **快速反馈** - 单元测试必须快速执行

## 应用经验教训

### L-P6-001: 真实容器 E2E 必须在 P6 执行

**教训**：P6 测试执行阶段强制要求真实容器 E2E（19 项验证全通过），拦截了 P3 MockMvc 无法发现的问题（Schema 漂移、静态资源 500、探活 fail-open）。

**本阶段应用**：
- P6a 单元测试虽然可以使用 Mock，但必须配合 P6c E2E 测试（真实容器）
- 不能只跑单元测试就声称"测试通过"
- MockMvc 单测无法覆盖真实容器的启动逻辑、资源加载、健康检查等

**预防措施**：
1. P6a 单元测试 + P6c E2E 测试必须都通过
2. E2E 冒烟清单必须包含：启动日志、health 端点、静态资源、业务 API、认证/授权
3. 测试基建与生产 schema 同源（禁止维护独立的 `test-schema.sql`）

**参考**：详见 `concepts/lessons-learned.md` L-P6-001

### L-P6-002: 密钥/加密契约必须两端各有单测（前端半边不可省）

**教训**：M01 登录 RSA 契约（TC-AUTH-001）只有后端半边有测试（RsaCipherServiceTest），前端 `parsePublicKeyPem` DER 解析零覆盖——外层 SEQUENCE/BIT STRING 被整体跳过导致**浏览器登录必崩**，而后端测试、API 探针全部绿灯（探针用 Python 独立实现加密，绕过了前端）。人工首验才暴露。

**本阶段应用**：
- 涉及加解密/签名/摘要等密钥契约的模块，契约两端（前端解析+加密 × 后端解密）必须各有单测，禁止只测后端就宣称契约已覆盖
- 前端单测必须用真实注入密钥（如 `.env` 的开发公钥）走解析→加密往返断言，不得用 mock key

**预防措施**：
1. P2 详设冻结密钥契约时，同时冻结两端测试责任方
2. P6a 检查密钥契约的前端半边测试文件存在且实跑通过

**参考**：详见 `concepts/lessons-learned.md` L-M01-011
