# Phase 5: 测试用例生成

## 目标

基于 PRD 生成全面的功能、边界、异常与客户端旅程测试。客户端分支由冻结平台决定：PC Web 使用浏览器自动化，小程序使用开发者工具/模拟器，APP 使用模拟器或真机自动化。

---

## 测试用例分类

### 1. 功能测试 (Functional Tests)

| 类型 | 说明 | 示例 |
|------|------|------|
| 正向测试 | 正常输入，预期成功 | 正确用户名密码登录成功 |
| 反向测试 | 异常输入，预期失败 | 错误密码登录失败 |

### 2. 边界测试 (Boundary Tests)

| 类型 | 说明 | 示例 |
|------|------|------|
| 边界值 | 刚好在边界上的值 | 用户名长度=最小/最大 |
| 等价类 | 同类数据的代表值 | 整数范围取边界值 |
| 特殊值 | 空值、null、特殊字符 | 空字符串、SQL注入 |

### 3. 异常测试 (Error Tests)

| 类型 | 说明 | 示例 |
|------|------|------|
| 参数校验 | 无效参数处理 | 非法邮箱格式 |
| 业务异常 | 违反业务规则 | 余额不足扣款 |
| 系统异常 | 系统故障处理 | 服务不可用、网络断开 |

### 4. 客户端旅程测试用例

先读取 `devflow-client.json` 并运行 `client-adapter.sh test <platform> <client-root> --strict`。每个平台都必须产出 `docs/测试用例/<feature>-客户端旅程.md`，记录可执行文件、环境、步骤、断言和证据路径。

| 平台 | 自动化层级 | 运行证据 |
|---|---|---|
| PC Web | Playwright 或项目冻结的真实浏览器工具 | browser report、截图、网络断言 |
| 微信小程序 | 微信开发者工具 CLI/模拟器 | 工具版本、预览/模拟器结果、截图 |
| APP | Android/iOS 模拟器或真机框架 | 设备、构建号、旅程结果、截图/日志 |

#### PC Web 分支：Playwright E2E

> 仅当冻结平台为 `pc-web` 时使用本节。小程序和 APP 不得用 Playwright 报告替代其平台旅程证据。

#### Playwright E2E 测试结构

```yaml

```

#### 测试用例文档"前置条件"中登录凭证的可追溯性要求

> **目的**：杜绝"盲猜密码 / 瞎试密码 / 写错密码"导致的 E2E 100% SKIP 黑洞。
>
> **背景**：历史项目测试报告曾以"盲猜常见密码均 401"充当审计结论（见 examples/xyls/domain-checklist.md）——这是审计错误。正确凭证在代码 seed 中是确定的。

测试用例文档（含 E2E 用例文档）的"前置条件"一节中，涉及登录的，必须用以下**三列表**代替纯文字描述：

| 项 | 值 | 代码来源（铁证） |
|---|----|---------------|
| 用户名 | 从seed解析的实际用户名 | `backend/<service>/src/main/resources/db/migration/{h2,postgresql,oracle,kingbase}/<service>/V*.sql` 中 seed 脚本（行号定位） |
| 密码 | 从seed注释/安全测试配置确认的实际值；报告中脱敏 | 同上 + 初始化器注释或受控环境变量 |
| 客户端测试 helper | `ADMIN_USERNAME` / `ADMIN_PASSWORD` 常量 | 项目冻结的客户端测试 helper（行号定位） |
| 环境变量覆盖 | `E2E_ADMIN_USERNAME` / `E2E_ADMIN_PASSWORD` | 同上 |
| 权限 | 权限组编码（如 `governance:*:view`） | seed + `V*__seed_admin_permissions.sql` |

**禁止做法**：
- ❌ "已用 admin 账号登录系统"（没写密码 / 没写代码出处）
- ❌ 写错的密码如 `admin123`（除非 seed 真的是这个值）
- ❌ 在测试报告里写"尝试 admin/admin123 / admin888 / 12345678 等"作为凭据恢复尝试

**正确做法**：
- ✅ 「用户名与密码来自明确 seed/初始化器路径；执行报告只记录来源和脱敏值」

#### Playwright 测试用例编写规范

1. **命名规范**
   - 文件名：使用中文功能名称，如 `frontend/e2e/组织架构.spec.ts`、`frontend/e2e/权限管理.spec.ts`
   - 测试函数：`test('[用例编号] [场景描述]', async ({ page }) => { ... })`

2. **测试结构**
   ```typescript
   import { test, expect } from '@playwright/test';

   test.describe('【功能名称】', () => {
     let adminPage: Page;

     test.beforeEach(async ({ page }) => {
       // 前置登录
       await page.goto('/login');
       await page.fill('[data-testid=username]', ADMIN_USERNAME);
       await page.fill('[data-testid=password]', ADMIN_PASSWORD);
       await page.click('[data-testid=login-btn]');
       await expect(page).toHaveURL(/\/home/);
     });

     test('[用例编号] [场景描述]', async ({ page }) => {
       // 1. 导航到目标页面
       await page.click('text=基础能力');
       await page.click('text=组织架构');

       // 2. 执行操作
       await page.click('button:has-text("新增单位")');

       // 3. 填写表单
       await page.fill('[placeholder="组织编码"]', 'ORG-E2E-001');
       await page.fill('[placeholder="组织名称"]', 'E2E测试单位');

       // 4. 提交
       await page.click('button:has-text("确定")');

       // 5. 验证
       await expect(page.locator('text=新增成功')).toBeVisible();
     });
   });
   ```

3. **验证方式**
   - **snapshot 检查**：使用 `page.snapshot()` 捕获页面状态
   - **network 请求断言**：监听并断言 API 请求/响应
   - **screenshot 截图**：失败时自动截图保存证据
   - **元素存在性**：`expect(locator).toBeVisible()` / `toHaveCount()`
   - **URL 断言**：`await expect(page).toHaveURL(/\/expected/)`

4. **常用工具函数**

   ```typescript
   // frontend/e2e/helpers.ts — v2.3 必须用 helper 常量，禁止硬编码密码
   import { ADMIN_USERNAME, ADMIN_PASSWORD } from './helpers'; // 来自受控环境/seed解析

   export async function loginAsAdmin(page: Page) {
     await page.goto('/login');
     await page.fill('[placeholder="用户名"]', ADMIN_USERNAME);
     await page.fill('[placeholder="密码"]', ADMIN_PASSWORD);
     await page.click('button:has-text("登录")');
     await expect(page).toHaveURL(/\/home/);
   }

   export async function waitForApiResponse(page: Page, urlPattern: string) {
     return page.waitForResponse(resp => resp.url().includes(urlPattern));
   }
   ```

   > ⚠️ **凭证可追溯性铁律**：
   > - 测试脚本中禁止硬编码任何真实密码或猜测值。
   > - 必须用 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 常量（来自 `frontend/e2e/helpers.ts`）。
   > - 如需覆盖密码（如 admin 密码被改），通过环境变量 `E2E_ADMIN_USERNAME` / `E2E_ADMIN_PASSWORD` 传入。
   > - 密码取值的**唯一可信来源**：代码 seed 脚本（`db/migration/<方言>/<service>/V*__seed_admin_user.sql`）和 `init/BuiltinDataInitializer.java` Java 注释。
   > - 审计/执行阶段**禁止反复猜测常见密码**（admin / admin123 / admin888 / 12345678 等）作为"凭据恢复"尝试。

5. **环境配置**

   ```typescript
   // frontend/e2e/global-setup.ts
   import { chromium, FullConfig } from '@playwright/test';

   export default async function globalSetup(config: FullConfig) {
     const browser = await chromium.launch();
     const page = await browser.newPage();

     // 检查后端服务是否就绪
     const gatewayHealth = await page.goto('http://localhost:8080/actuator/health');
     if (!gatewayHealth.ok()) {
       throw new Error('Gateway service is not ready');
     }

     await browser.close();
   }
   ```

6. **测试环境变量**

   | 变量名 | 默认值 | 说明 |
   |--------|--------|------|
   | E2E_ADMIN_USERNAME | 无默认值 | 从seed解析或CI密钥注入 |
   | E2E_ADMIN_PASSWORD | 无默认值 | 从受控环境注入，禁止写入文档 |
   | E2E_ADMIN_USER_ID | 无默认值 | 从seed解析 |

7. **执行命令**

   ```bash
   # 安装浏览器
   npx playwright install chromium

   # 运行所有 E2E 测试
   npm run e2e

   # 运行单个测试文件
   npm run e2e -- 组织架构.spec.ts

   # 运行特定用例
   npm run e2e -- --grep "TC-ORG-001"
   ```

## 测试用例生成流程

### Step 1: 分析PRD

从PRD中提取：
- 功能点列表
- 业务规则
- 输入约束
- 预期输出

### Step 2: 识别测试场景

```
PRD功能点 → 业务流程 → 测试场景
    ↓
┌─────────────────────────────────┐
│ 1. 用户注册                      │
│    → 填写表单 → 提交 → 验证邮箱   │
│    ↓                            │
│    场景:                        │
│    - 正常注册                   │
│    - 用户名已存在               │
│    - 邮箱格式错误               │
│    - 密码强度不足               │
│    - ...                        │
└─────────────────────────────────┘
```

### Step 3: 编写测试用例

每个测试用例包含（API 测试 + 浏览器自动化测试）：

```markdown
### TC-USER-001: 正常用户注册

**用例类型**: 功能测试 - 正向
**优先级**: P0

**前置条件**:
- 系统正常运行
- 测试邮箱可用
- 无同名用户

**测试数据**（凭据禁止硬编码，一律来自环境变量 / seed fact source）:
- 用户名: `${TEST_USER_NAME}`（来源: env: TEST_USER_NAME）
- 邮箱: test001@example.com
- 密码: `${TEST_USER_PASSWORD}`（来源: env: TEST_USER_PASSWORD；CI 由 seed/config fact source 注入）

**测试步骤**:
1. 打开注册页面
2. 输入用户名: ${TEST_USER_NAME}
3. 输入邮箱: test001@example.com
4. 输入密码: ${TEST_USER_PASSWORD}
5. 确认密码: ${TEST_USER_PASSWORD}
6. 点击注册按钮

**预期结果**:
| 步骤 | 预期 |
|------|------|
| 1 | 显示注册表单 |
| 5 | 表单验证通过 |
| 6 | 显示注册成功提示 |
| 6 | 收到验证邮件 |
| 6 | 自动跳转到登录页 |
```

### 优先级定义

| 优先级 | 定义 | 执行时机 |
|--------|------|----------|

| P2 | 一般功能，优雅降级 | 定期执行 |

## Red Flags

以下情况必须停止并汇报：

| 红旗 | 问题 | 正确做法 |
|------|------|----------|
| 用例无法执行 | "测试界面正常" | 必须可执行 |
| 覆盖不全 | 只测正常流程 | 必须覆盖边界/异常 |
| 无预期结果 | "看看会发生什么" | 必须有明确预期 |
| 用例间有依赖 | 后面的用例依赖前面 | 用例必须独立 |
| 优先级混乱 | 全部是P0 | 按实际影响分级 |
| **缺少E2E测试** | "有API测试就够了" | **前端页面必须编写Playwright E2E** |

## 常见问题处理

| 问题 | 解决方案 |
|------|----------|
| PRD描述模糊 | 联系产品确认需求 |
| 场景太多 | 按优先级筛选，先做P0 |
| 边界难确定 | 与产品确认业务规则 |
| 异常场景不全 | 参考常见异常列表 |
| 前端页面无测试 | **必须编写Playwright E2E测试** |

---

## 关键原则

1. **覆盖全面** - 正向、反向、边界、异常、E2E都要覆盖
2. **可执行** - 用例要能实际执行，不是纸上谈兵
3. **可追踪** - 每个用例要能追溯到PRD需求
4. **独立** - 用例之间无依赖，可并行执行
5. **E2E优先** - 前端页面功能**必须**编写Playwright浏览器自动化测试

## Gate 检查

| 检查项 | 通过条件 |
