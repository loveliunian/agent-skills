# Release Integrity and Independent Review Attestation Design

## Goal

Make devflow's release evidence resistant to local self-attestation, mutable manifest history, unsafe test-only hash injection, and incomplete copy synchronization. A P2a approval must prove that an authority outside the workflow process observed the assigned reviewer identity and lifecycle.

## Scope

- Strict, externally signed P2a reviewer events.
- Removal of the production skill-tree hash cache bypass.
- An immutable legacy-manifest root anchored by the next release tree.
- Idempotent published-version hardening tests.
- Copy synchronization hygiene and release rollback correction.
- Official Codex `agents/openai.yaml` metadata shape.

## Strict reviewer attestation

`review-receipt.sh` remains responsible for local evidence layout and SHA binding, but no longer treats a caller-supplied `agent_id` as proof of a separate reviewer.

Each `begin` and `complete` transition requires a signed event envelope generated by an external dispatcher or CI attester. The envelope has a canonical JSON payload containing the feature, review session, role, platform-issued agent identity, input/output SHA, event kind, timestamp, and nonce; its detached signature is verified by `openssl` against `REVIEW_ATTESTATION_PUBKEY`.

The skill does not contain a private key and does not provide a local signing fallback. If the public key, signed event, or verification tool is absent, P2a is `BLOCKED`. Tests use an ephemeral test-only keypair and a simulated external attester; production credentials and private keys never enter the skill tree or project artifacts.

## Manifest integrity root

The mutable `references/manifest/CHAIN.json` is not a trust root. The next release adds `references/manifest-root.json`, outside the excluded manifest directory. It contains a canonical, complete hash inventory of every legacy manifest through the prior release and the expected ledger digest. Because this root is included in the next release tree and its immutable manifest, altering a legacy manifest and rewriting `CHAIN.json` changes a protected artifact and fails the current manifest check.

Manifest verification also requires an exact equality between manifest files and ledger entries, unique monotonically increasing versions, a verified parent manifest SHA, and a chain head matching the current release.

## Release and sync behavior

`gate-skill-tree.sh` must always compute the real tree hash. Test acceleration belongs in fixture setup rather than production gate behavior.

`sync-copies.sh` excludes `tests/logs/` in every rsync and portable apply/delete path. `release.sh` acquires an exclusive release lock, marks a B3 copy recheck failure rollback-eligible, and reports real-copy recovery separately from atomic source-manifest rollback.

## Codex metadata

`agents/openai.yaml` is reduced to the documented `interface`, `policy`, and `dependencies` structure. Shell and permission statements remain skill documentation, not an unenforceable metadata security boundary.

## Verification

Regression tests must demonstrate all of the following:

1. A published-version test rerun does not try to regenerate its existing manifest.
2. Injected `RUN_TESTS_ACTIVE` and `DEVFLOW_SKILL_TREE_SHA` values cannot change the returned hash.
3. Unsigned or caller-forged reviewer events are rejected; externally signed begin and complete events pass only when their fields match the receipt and current artifacts.
4. Tampering a legacy manifest and rewriting `CHAIN.json` still fails due to `manifest-root.json`; extra or duplicate manifest records fail.
5. `tests/logs/` never reaches a real copy during synchronization.
6. A B3 copy verification failure triggers source-manifest rollback and leaves an explicit recovery record for any already-updated real copies.

## Compatibility

This is deliberately fail-closed. Existing P2a review sessions without externally signed events cannot be upgraded in place and must be rerun. The release version increments from v3.21.1 to v3.21.2; no existing manifest is overwritten.
