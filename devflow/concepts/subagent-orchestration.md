# 子代理编排策略（Subagent Orchestration）

> **定位**：`/devflow` 全链编排的执行模式决策表。Gate 契约（schema/脚本）不因编排方式改变——
> 子代理产出仍须通过同一套 Gate；本文件只回答「谁来做、怎么做才不返工」。

---

## 1. 默认编排策略（按阶段）

| 阶段 | 模式 | 理由（实测依据） |
|---|---|---|
| P0 / P0b | 主会话单线 | 契约密集：验收点 ID、枚举、三字段检查的校验-修复循环强耦合，拆分反而传递错误清单 |
| P1 | 主会话单线 | 7 份事实源 + design-conventions 与 Gate schema 逐字段对齐，同上 |
| P2 | 主会话单线 | **单一正本原子链**：design.json → 生成器 → 三份文档 → 后处理 → 双 Gate，中途换手必引入不一致 |
| P2a / P3b | **独立上下文子代理（必选）** | 认知独立：同一上下文换角色帽子≠真独立。收据签名只提供过程独立（防篡改/补签），不提供认知独立（防盲区） |
| P3 | **并行子代理 ×2（backend/frontend）** | 两端仅靠 API 契约（详设 §3.2 + INDEX-接口）耦合，无共享状态；实测单线 ~85min，并行预估省 ~40% |
| P4 / P4b | 主会话单线 | PRD-vs-Code 对账依赖「设计↔代码↔验收点」三方精确一致性，拆分丢上下文 |
| P5 | 主会话单线 | 用例由生成器从正本派生，无并行空间 |
| P6 | 可并行 ×5 | unit/integration/client/load/staging 五命令相互独立（注意：CLIENT 依赖前端 dev server、STAGING 依赖后端容器，起服务的前置动作须先行） |
| P7~P10 | 主会话单线 | 收据链审计跨阶段一致性；串行成本低（合计 <1h） |

---

## 2. 三条单线理由（何时**不**用子代理）

1. **契约对齐循环**：schema 枚举/锚点正则/表头关键词的校验-修复循环，失败知识在当前上下文；
   子代理每轮都要重学契约，往返传递错误清单比直接修慢（实测 design.json 15+ 轮迭代全部在单线内收敛）。
2. **单一正本原子链**：正本 JSON → 渲染 → 后处理 → Gate 是原子操作序列，执行者必须持有整链上下文。
3. **收据链一致性**：P7 起的 receipt chain audit 跨阶段核验版本与哈希，编排器全程在场最不易产生版本漂移。

---

## 3. 子代理任务书契约（spawn 时必含六要素）

子代理不共享编排器上下文。任务书缺一项，产出即不可信或需返工：

1. **输入正本路径**（design.json / 详设 / 事实源文件），明示「契约以文件为准，禁止凭记忆重构」；
2. **产出物路径 + 验收命令**：子代理必须自行运行对应 Gate/测试并附真实退出码与输出摘要；
3. **边界声明**：允许改哪些文件、禁止改哪些（如：禁止修改 Gate 脚本/schema/已冻结正本）；
4. **回传格式**：结构化结果（产出清单 + 退出码 + 偏差说明），不是自由文本叙述；
5. **评审类任务附加**：DF 五字段契约 + AW≥3 + 零发现须附核查证据（同 P2a 深度契约）；
6. **收据边界**：评审收据由编排器两阶段签发（begin 于产出前 / complete 于定稿后），
   子代理只产出 findings 本体，**不得自行签发收据**。

---

## 4. 独立评审子代理流程（P2a / P3b）

```text
编排器（主会话）
  1. 生成评审密钥对（review-attest-init.sh keygen）
  2. begin-all（六角色收据，此时评审产出尚不存在）
  3. spawn 独立子代理 ×N：
       输入 = 详设 + 验收点 + 评审模板 + 深度契约（不含编排器对设计的辩护性上下文）
       输出 = findings/aw/zero-df 结构化 JSON
  4. 编排器汇总 → 渲染聚合报告（冻结）
  5. complete-all（绑定冻结报告 SHA）
  6. p2a_design_review_gate / p3b_code_review_gate
```

要点：子代理的输入**刻意不含**编排器的实现过程叙述，只给正本文件——
评审者看到的世界应与实现者无关，这正是「独立」的实际含义。

## 5. 反模式（实测踩过）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 契约对齐循环派子代理 | 每轮重学契约，往返传递错误清单 | 主会话单线收敛，教训沉淀到复盘 |
| 单一正本原子链中途换手 | 双正本不一致，Gate 互斥失败 | 单线持有整链，或用生成器脚本作为交接物 |
| 评审与实现同上下文换帽子 | 认知盲区共享，发现率下降 | 独立子代理 + 只喂正本（§4） |
| 子代理自行签发收据 | 过程独立保证失效 | 编排器两阶段签发（§3.6） |
| 并行子代理共享可变证据文件 | 收据 SHA 绑定互相打断（实测：P6-final 证据被后续运行扰动 2 次） | 证据文件按子代理分目录；终验命令最后统一执行 |

## 6. 实测基线（m01-base，单线全链）

| 指标 | 值 |
|---|---|
| 总耗时 | 6h40m（21:15→03:58，含全部构建/安装/压测） |
| 最耗时 | P6-final 90min、P3 85min、P2 70min |
| 契约对齐占比 | ~25%（枚举/类型/列序/锚点） |
| 并行化预估 | P3 并行省 ~40min；契约循环不可并行 |

**P6 修复循环（v3.28.12）**：m01-base 实测每轮修复都全量重跑五类（登录死锁一轮
全量 mvn 51 用例 + playwright）。修复循环改用 `scripts/p6-iterate.sh <feature>
<kind> [--filter <类名>]` 只重跑失败套件（框架感知拼接 mvn -Dtest / playwright
--grep 等；产物落 `.devflow/<feature>/iterations/`，只读 test-evidence.env）——
**P6-final 门禁仍全量真实重执行五类命令**（反自报契约不变），收敛后照常走终验。
**环境预热**：P5 开始即后台跑 `scripts/p6-prewarm.sh <feature> --backend-cmd <cmd>
[--frontend-cmd <cmd>]`（幂等，健康绿则跳过），后端/前端在测试设计期间预热，
消化 L-PROC-005 的 E2E 冷启动超时预算。

后续项目可对照本基线评估编排收益；偏离 ±50% 以上时先查契约对齐方式是否退化。
