# 详设评审流程规范 (Design Review Process)

> 本文档定义了从 PRD 到详设的评审路径、角色定义、评审机制和循环修复流程。

---

## 1. 核心目标

| 目标 | 说明 |
|------|------|
| **质量保障** | 通过多角色、多维度评审，确保详设无重大遗漏 |
| **问题前置** | 将问题发现提前到编码前，降低修复成本 |
| **知识沉淀** | 评审过程沉淀的规则反哺模板和 Gate 脚本 |

---

## 2. 角色定义

### 2.1 评审委员会组成

```
┌─────────────────────────────────────────────────────────────────┐
│                    详设评审委员会 (5人)                          │
├─────────────┬─────────────┬─────────────┬─────────────┬────────┤
│ 业务专家    │ 架构师      │ DBA         │ 开发工程师    │ BPM专家│
│ (业务视角)  │ (架构视角)  │ (数据视角)  │ (实现视角)  │(流程视角│
└─────────────┴─────────────┴─────────────┴─────────────┴────────┘
```

### 2.2 角色职责

| 角色 | 关注领域 | 评审重点 |
|------|----------|----------|
| **业务专家** | 业务逻辑、业务规则、术语口径 | 模块规划、业务流程、原子服务划分 |
| **架构师** | 系统架构、技术选型、模块边界 | 模块独立性、接口契约、扩展性 |
| **DBA** | 数据模型、索引设计、数据迁移 | 表结构规范性、历史数据映射、老系统对接 |
| **开发工程师** | 代码实现、异常处理、性能 | 数据逻辑、事务边界、并发安全 |
| **BPM专家** | 流程编排、状态机、节点设计 | 流程完整性、节点设计、异常分支 |

### 2.3 角色准入标准

| 角色 | 最低要求 |
|------|----------|
| 业务专家 | 3年+ 业务经验，熟悉至少2个老系统 |
| 架构师 | 通过架构评审认证，熟悉微服务架构 |
| DBA | 2年+ 数据库设计经验，熟悉4种数据库方言 |
| 开发工程师 | 3年+ 开发经验，熟悉领域驱动设计 |
| BPM专家 | 2年+ BPM流程设计经验，熟悉流程引擎 |

## 3. 评审路径

### 3.1 流程概览

```
┌──────────────────────────────────────────────────────────────────────────┐
│                          PRD → 详设评审路径                               │
└──────────────────────────────────────────────────────────────────────────┘

PRD冻结
    │
    ▼
┌─────────────────┐
│ P0b PRD评审      │  ←── 业务/技术/测试/安全多Agent讨论
└────────┬────────┘
         │ 通过
         ▼
┌─────────────────┐
│ P2 详细设计      │  ←── 生成详设文档
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│                     评审循环 (最多3轮)                              │
│  ┌───────────┐    ┌───────────┐    ┌───────────┐    ┌────────┐  │
│  │ 第1轮评审  │───▶│ 修复完善  │───▶│ 第2轮评审  │───▶│  ...   │  │
│  └───────────┘    └───────────┘    └───────────┘    └────────┘  │
└─────────────────────────────────────────────────────────────────┘
         │ 通过
         ▼
┌─────────────────┐
│ P3 编码阶段      │
└─────────────────┘
```

### 3.2 评审模式

#### 模式一：委员会评审（正式）

适用于：P0/P1 功能、跨模块功能、新老系统对接；P2a 正式评审统一使用 canonical 五角色

```
1. spawn 5个评审子Agent
2. 各Agent独立评审：先执行主责探针（六类深挖探针），再按实际发现输出 DF/SF——DF 数量不设下限，零发现必须有 ZERO-DF 核查证据（已核查清单+§锚点）；AW ≥3 且每条以"结果:"收尾
3. 汇总问题（按严重性分类）
4. 讨论修订严重性
5. 生成修复任务
6. 修复 → 审核 → 合稿
7. 复核Gate
```

#### 模式二：专项评审（轻量）

适用于：仅 `/small-change` 或明确不进入 P2a 的局部修改；简单 CRUD 进入 P2a 时仍使用 canonical 五角色，但按适用性标记专项检查 N-A

```
1. spawn 2-3个专项评审子Agent（不签发 P2a Gate）
2. 聚焦专项领域评审
3. 问题修复
4. 复核通过
```

## 4. 评审执行

### 4.1 第一步：spawn 评审子Agent

```markdown
spawn 5个评审子Agent，组成详设评审委员会

角色：
1. 架构师（architecture-reviewer）
2. 后端专家（backend-reviewer）
3. 前端专家（frontend-reviewer）
4. 测试开发（test-reviewer）
5. DBA（dba-reviewer）

任务：
对 {详设文档路径} 进行评审
```

### 4.2 第二步：独立评审

每位评审专家必须先执行适用的主责探针（见 `concepts/review-depth-methodology.md` §3 探针主责矩阵），再按 DF 或 ZERO-DF 契约输出；不以固定问题数量作为通过条件：

```markdown
## {角色名} 评审报告

### 评审范围
- 文档路径：{详设文档}
- 评审时间：{timestamp}
- 评审原则：客观公正、从严从紧、找茬挑毛病；未跑主责探针不得下结论

### 探针执行记录（六类，主责必做）
| 探针 | 执行情况 | 结论/产出位置 |

### 对抗场景走查（委员会合计 ≥3 条，每条以"结果:"收尾）
- AW-{n} 场景：…｜走查路径：…｜结果：{发现 DF-xx / 无问题，证据：§x.y}

### 深层发现 DF（按实际发现；零发现必须附 ZERO-DF 核查证据；五字段缺一无效）

#### DF-{nn} {标题}
- 归属评委：{本角色}
- 文档位置：§{x.y}
- 触发场景：
- 影响链：
- 根因类别：
- 完善建议：
- 验证方式：
- 严重性：P0/P1/P2

### 表层发现 SF（≤5 条）
- SF-{nn} {标题}（§位置 + 一句话建议）
```

### 4.3 严重性分级标准

> 仅适用于 DF；P3 级"锦上添花"类意见归入 SF（表层发现，不计配额不阻塞）。

| 级别 | 定义 | 示例 | 处理要求 |
|------|------|------|----------|
| **P0** | 阻碍性缺陷，无法进入下一阶段 | 数据模型缺失核心字段、接口契约与PRD严重不符 | **必须修复** |
| **P1** | 重大缺陷，影响核心功能 | 业务规则遗漏、分页逻辑错误 | **必须修复** |
| **P2** | 一般缺陷，不影响主流程 | 字段命名不规范、注释缺失 | **建议修复** |

### 4.4 第三步：问题汇总与讨论

```markdown
## 问题汇总报告

### 汇总统计

| 严重性 | 业务专家 | 架构师 | DBA | 开发工程师 | BPM专家 | 合计 |
|--------|----------|--------|-----|----------|---------|------|
| DF-P0  | 2        | 1      | 0   | 1        | 0       | 4    |
| DF-P1  | 5        | 3      | 2   | 4        | 2       | 16   |
| DF-P2  | 8        | 5      | 6   | 7        | 4       | 30   |
| SF 归档 | 10       | 8      | 5   | 6        | 7       | 36（不计配额） |

### 修订后问题列表

> 基于当事人回避原则，对评委提出的问题进行讨论

| # | 原问题 | 原严重性 | 修订后严重性 | 修订理由 | 归属评委 |
|---|--------|----------|--------------|----------|----------|
| 1 | ...    | P1       | P2           | 非核心功能 | 业务专家 |
```

### 4.5 第四步：修复循环

```
┌─────────────────────────────────────────────────────────────────┐
│                     修复-审核-合稿循环                           │
└─────────────────────────────────────────────────────────────────┘

  ┌──────────────┐
  │ 修复子Agent  │  ←── 基于问题列表、原文、建议进行修复
  └──────┬───────┘
         │ 修复后
         ▼
  ┌──────────────┐
  │ 审核子Agent  │  ←── 验证修复是否正确、完整
  └──────┬───────┘
         │ 审核通过
         ▼
  ┌──────────────┐
  │ 合稿子Agent  │  ←── 合并修复内容，生成最终版本
  └──────┬───────┘
         │ 合稿完成
         ▼
      ┌──────┐
      │ 复核 │
      └──────┘
```

### 4.6 第五步：Gate 检查

```markdown
## 评审Gate

| 条件 | 要求 | 当前状态 |
|------|------|----------|
| DF-P0/P1 数 | = 0 | ❌ 20 → ✅ 0 |
| DF/ZERO-DF 证据 | 每角色有 DF 或 ZERO-DF 核查证据 | ✅ 满足 |
| AW 走查 | ≥3 条且有结果收尾 | ✅ 3 条 |
| 六类探针记录 | 全部已执行 | ✅ 6/6 |

通过条件：DF-P0=P1=0 且每角色有 DF/ZERO-DF 核查证据且探针记录齐全

循环次数：1/3
```

## 5. 循环机制

### 5.1 循环终止条件

| 条件 | 说明 |
|------|------|
| **通过** | DF-P0=0 且 DF-P1=0 且每角色有 DF/ZERO-DF 核查证据（AW≥3）且探针记录齐全 |
| **最大轮次** | 最多3轮评审循环 |
| **升级处理** | 3轮未通过 → 人工介入决策 |

### 5.2 循环流程图

```
                    开始评审
                       │
                       ▼
                 ┌───────────┐
                 │ 第N轮评审  │
                 └─────┬─────┘
                       │
                       ▼
                 ┌───────────┐
                 │ Gate检查  │
                 └─────┬─────┘
                       │
           ┌───────────┴───────────┐
           │                       │
      Gate通过                 Gate未通过
           │                       │
           ▼                       ▼
    ┌─────────────┐         ┌─────────────┐
    │ 进入下一阶段 │         │ N < 3 ?     │
    └─────────────┘         └──────┬──────┘
                                   │
                    ┌──────────────┴──────────────┐
                    │                             │
               N < 3                         N >= 3
                    │                             │
                    ▼                             ▼
            ┌─────────────┐               ┌─────────────┐
            │ 修复→审核   │               │ 人工介入    │
            │ →合稿      │               │ 决策        │
            └──────┬──────┘               └─────────────┘
                   │ 修复完成
                   ▼
             ┌───────────┐
             │ 第N+1轮   │
             │ 评审      │
             └───────────┘
```

## 9. 铁律

1. **评审独立性**：每位评委独立评审，不得相互讨论后再输出
2. **按实际发现**（v3.16.26，替代旧"DF≥10/每角色≥3"配额）：DF 数量不设下限、不凑数；每角色必须有实际 DF 或 ZERO-DF 核查证据（已核查清单+§锚点证据）；DF 五字段缺一无效；SF>DF 仅 WARN——凑数灌水比零发现更恶劣
3. **严重性公正**：P0/P1由全体评委讨论确认，避免个人主观放大
4. **修复可追溯**：所有问题必须追踪到修复commit
5. **Gate强制**：DF-P0/P1=0 且每角色有 DF/ZERO-DF 核查证据（AW≥3、探针记录齐全）才能进入编码；独立评审收据（review-receipt.sh）必须通过验证
6. **循环上限**：3轮未通过必须人工介入
