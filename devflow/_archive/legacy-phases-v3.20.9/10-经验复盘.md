- 总结项目经验与教训

```markdown

**上次 New-Findings**:
1. ✅ 已应用: P2a 五角色评审在编码前拦截 43 个缺陷

   - 效果: 拦截 12 个 P1 缺陷

2. ❌ 未应用: 权限码需在 P0b 对账
   - 原因: P0 gate 脚本尚未更新

- 行动项: 将权限码对账加入 P0 checklist
```

### 2. New-Findings: 本次新发现

**目的**：记录本次项目中发现的新问题、新经验，供下次项目参考。

```markdown
## New-Findings: 本次新发现

### NF-001: P2b Demo 签收不可形式化

**发现阶段**: P2b → P3  
**问题描述**: 业务方"看了一眼"就签收 Demo，编码后发现交互流程不符合实际业务  
**影响**: 返工 3 天  
**根因**: Demo 签收流于形式，未实际操作验证  

**下次改进**:
1. 签收前必须实际操作 Demo
2. 记录"已操作场景清单"
3. 签收时间 ≥ Demo 交付时间 + 1 天
4. P2b gate 增加签收时间检查

**适用场景**: 所有涉及前端交互的项目

---

### NF-002: PRD-vs-Code Gate 必须透传模板模式

**发现阶段**: P4b  
**问题描述**: 小程序多租户项目，PRD 只描述模板逻辑，但 P4b 对账脚本只找到 1 个模板实现，报告"实现不完整"  
**影响**: P4b gate 误报，需要人工介入  
**根因**: Gate 脚本未识别模板模式  

**下次改进**:
1. PRD 中明确标注"模板模式"或"多租户模式"
2. P4b gate 自动识别模板模式
3. 模板项目对账只验证模板逻辑，不验证实例数量

**适用场景**: 模板项目、多租户项目、小程序矩阵

---

### NF-003: 真实容器 E2E 必须在 P6 执行

**发现阶段**: P6 → P7  
**问题描述**: MockMvc 全绿，但真实 Docker 容器启动时 Spring Context 初始化失败  
**影响**: 部署前夕发现问题，延期 1 天  
**根因**: 测试环境与生产环境不一致（MockMvc vs 真实容器）  

**下次改进**:
1. P6 阶段必须在真实容器中执行 E2E 测试
2. 测试环境使用与生产一致的容器镜像
3. 容器启动失败 = P6 gate 阻断

**适用场景**: 所有容器化部署的项目

---

### NF-004: 详设覆盖率 100% 是必要的

**发现阶段**: P2 → P3  
**问题描述**: 详设覆盖率只有 85%，编码时发现 15% 的字段没有定义，需要反复回到设计阶段补充  
**影响**: 编码效率低，反复切换上下文  
**根因**: 认为"大部分写清楚就可以了"  

**下次改进**:
1. P2 gate 必须检查覆盖率 = 100%
2. s2_design_coverage_gate.sh 输出详细缺失清单
3. 不通过不进入 P3

**适用场景**: 所有项目

---

### NF-005: 监控大盘必须在部署前配置

**发现阶段**: P7 → P8  
**问题描述**: 部署完成后才开始配置监控，期间服务出现性能问题但无法及时发现  
**影响**: 用户投诉响应慢，但无监控数据定位问题  
**根因**: 监控配置作为部署后的"补充工作"  

**下次改进**:
1. 监控配置前置到 P6 阶段（测试时就验证监控）
2. P7 部署 gate 增加"监控大盘已配置"检查
3. 部署前必须能看到监控指标

**适用场景**: 所有生产服务
```

## Feedback Queue 机制

### 什么是 Feedback Queue？

**定义**: 项目级工具改进建议队列，记录在 `.devflow/<feature>/feedback/` 目录。

**目的**:
1. 项目不能擅自修改全局 skill（铁律 9）
2. 但项目发现的工具问题需要记录和反馈
3. Skill 维护者定期从各项目 feedback queue 中提取共性问题

### Feedback 格式

```markdown
# FB-20260915-001: s0_acceptance_gate.sh 缺少权限码对账

## 基本信息
- 反馈类型: 工具改进
- 优先级: P1
- 项目: 治理服务 v2
- 发现阶段: P2a
- 提交时间: 2026-09-15
- 提交人: Agent-治理详设-v2

## 问题描述
P0 gate 脚本 `s0_acceptance_gate.sh` 未检查权限码与权限矩阵（`docs/detailed-design/_权限矩阵.md`）一致性。

权限码双口径问题在 P2a 前端评审才发现，应该在 P0 或 P0b 就拦截。

## 影响范围
- 影响阶段: P0, P0b
- 影响项目: 所有涉及权限管理的项目

## 建议改进

### 方案 1: 在 s0_acceptance_gate.sh 增加检查项

```bash
# 检查权限码与权限矩阵一致性
echo "✓ 检查权限码对账..."
PERMISSION_MATRIX="docs/detailed-design/_权限矩阵.md"
if [ -f "$PERMISSION_MATRIX" ]; then
  # 提取 PRD 中的权限码
  PRD_PERMS=$(grep -oP "权限码[:：]\s*\K[a-z:_]+" "$PRD_FILE" | sort -u)
  
  # 提取权限矩阵中的权限码
  MATRIX_PERMS=$(grep -oP "\| \K[a-z:_]+(?= \|)" "$PERMISSION_MATRIX" | sort -u)
  
  # 对比差异
  DIFF=$(comm -3 <(echo "$PRD_PERMS") <(echo "$MATRIX_PERMS"))
  
  if [ -n "$DIFF" ]; then
    echo "❌ 权限码双口径不一致"
    echo "$DIFF"
    exit 1
  fi
fi
```

### 方案 2: 在 P0b PRD 评审增加探针

在 `phases/00b-PRD评审.md` 中增加"权限事实源一致性"探针。

## 决策
- 决策: `defer`
- 理由: 需要修改全局 skill，建议随 devflow v3.21 交付
- 临时方案: 在项目 checklist 中手动增加检查项

## 跟踪
- skill 版本: devflow v3.21.1
- 目标版本: devflow v3.21
- 跟踪 Issue: (待创建)
```

### Feedback 决策类型

| 决策 | 说明 | 适用场景 |
|------|------|---------|
| `defer` | 延后处理，等待 skill 更新 | 需要修改全局 skill |
| `accept` | 立即接受，本项目实施 | 项目特有配置 |
| `reject` | 拒绝，不是问题 | 误报或不合理建议 |
| `escalate` | 升级，紧急修复 | 阻塞性问题 |

## 经验教训应用

### L-RETRO-001: P10 教训必须写入项目本地 feedback queue

**问题**: 不能擅自修改全局 skill（铁律 9）

**解决方案**:
1. 工具改进建议记录为 FB（feedback）
2. 决策为 `defer`，等待 skill 更新
3. Skill 维护者定期从各项目 feedback 中提取共性问题

### L-RETRO-002: 复盘必须包含 Prior-Gap 与 New-Findings

**问题**: 复盘不只是总结本次项目，更是为下次项目提供前车之鉴

**解决方案**:
1. Prior-Gap: 检查上次项目的 New-Findings 是否应用
2. New-Findings: 记录本次项目的新发现
3. 每次项目启动前（P0）读取上次项目的 New-Findings

---

## 反模式

❌ **复盘只是走过场**：写几句总结就完事，没有实质内容  
❌ **不记录 Prior-Gap**：每次项目都重复踩坑  
❌ **New-Findings 空泛**：写"要加强测试"这种无用建议  
❌ **不建立 Feedback Queue**：发现工具问题但不记录  
❌ **复盘后无行动项**：复盘完了就忘了，下次还是老样子  
❌ **只批评不表扬**：只记录问题，不记录亮点  
❌ **不计算 ROI**：不知道评审投入是否值得
