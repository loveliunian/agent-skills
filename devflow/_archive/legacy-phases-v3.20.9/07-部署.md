# Phase 7: 部署（Deployment）

## 目标

- 将经过验证的代码安全部署到目标环境
- 确保部署过程可追溯、可回滚
- 验证部署后服务健康状态
- 建立部署记录和应急预案

## 进入条件

- [ ] P6 测试全部通过（单元/集成/E2E/压测）
- [ ] P0 缺陷 = 0
- [ ] 代码覆盖率 ≥ 80%
- [ ] E2E 通过率 ≥ 95%
- [ ] 性能指标达标（P95 < 阈值）
- [ ] 安全审计通过
- [ ] 变更审批通过（生产环境）

---

## 部署环境

### 环境分层

| 环境 | 用途 | 数据 | 审批要求 |
|------|------|------|---------|
| **开发环境** (dev) | 日常开发测试 | Mock 数据 | 无 |
| **测试环境** (test) | 功能测试、集成测试 | 测试数据 | 开发负责人 |
| **预发环境** (staging) | 生产验证、压测 | 脱敏生产数据 | 技术负责人 |
| **生产环境** (prod) | 正式对外服务 | 真实数据 | 变更委员会 |

### 环境隔离要求

```bash
# 1. 配置隔离
backend/src/main/resources/
├── application.yml                  # 公共配置
├── application-dev.yml             # 开发环境
├── application-test.yml            # 测试环境
├── application-staging.yml         # 预发环境
└── application-prod.yml            # 生产环境

# 2. 数据库隔离
dev_db      → localhost:3306
test_db     → test-db.internal:3306
staging_db  → staging-db.internal:3306
prod_db     → prod-db.internal:3306 (只读副本用于测试)

# 3. 凭证隔离
dev:     明文配置（仅限本地）
test:    环境变量
staging: Vault / K8s Secret
prod:    Vault / K8s Secret + 加密
```

## 部署策略

### 1. 蓝绿部署（推荐用于生产）

**原理**: 同时维护两套环境（蓝/绿），切换流量

```
┌─────────────┐
│   负载均衡   │
│  (Nginx/LB) │
└──────┬──────┘
       │
   ┌───┴────┐
   │        │
┌──▼──┐  ┌──▼──┐
│ 蓝环境 │  │ 绿环境 │
│ v1.0  │  │ v1.1  │  ← 部署新版本
└──────┘  └──────┘
              │
           流量切换
              ▼
┌──────┐  ┌──────┐
│ 蓝环境 │  │ 绿环境 │  ← 100% 流量
│ v1.0  │  │ v1.1  │
└──────┘  └──────┘
```

**优点**:
- 切换快速（秒级）
- 可快速回滚
- 零停机时间

**缺点**:
- 需要双倍资源
- 数据库迁移需要兼容两个版本

**适用场景**:
- 生产环境首次部署
- 重大版本升级
- 需要快速回滚的场景

**部署步骤**:
```bash
# 1. 当前蓝环境提供服务（v1.0）
# 2. 在绿环境部署新版本（v1.1）
# 3. 在绿环境执行健康检查
# 4. 切换负载均衡到绿环境
# 5. 监控绿环境运行状态
# 6. 确认无问题后，蓝环境保持待命（回滚备用）
```

### 2. 灰度发布（推荐用于迭代更新）

**原理**: 逐步将流量从旧版本切换到新版本

```
阶段 1: 5% 流量          阶段 2: 50% 流量         阶段 3: 100% 流量
┌──────────┐            ┌──────────┐            ┌──────────┐
│ v1.0 95% │            │ v1.0 50% │            │ v1.1 100%│
│ v1.1  5% │ → 监控 →   │ v1.1 50% │ → 监控 →   │          │
└──────────┘            └──────────┘            └──────────┘
```

**优点**:
- 风险可控（问题影响面小）
- 可观察用户反馈
- 可 A/B 测试

**缺点**:
- 部署周期较长
- 需要流量管理能力

**适用场景**:
- 日常迭代更新
- 高风险功能上线
- 需要 A/B 测试的功能

**流量控制方式**:
```java
// 方式 1: 基于用户 ID 哈希
int bucket = userId % 100;
if (bucket < 5) {
    // 5% 用户使用新版本
    return newFeature();
} else {
    return oldFeature();
}

// 方式 2: 基于地区
if (region.equals("beijing")) {
    return newFeature(); // 北京地区先灰度
}

// 方式 3: 基于白名单
if (whitelistUsers.contains(userId)) {
    return newFeature(); // 白名单用户先体验
}
```

### 3. 滚动发布（推荐用于多实例服务）

**原理**: 逐个实例替换，保持部分实例持续服务

```
Step 1: 3 个实例服务中
┌────┐ ┌────┐ ┌────┐
│v1.0│ │v1.0│ │v1.0│
└────┘ └────┘ └────┘

Step 2: 替换第 1 个
┌────┐ ┌────┐ ┌────┐
│v1.1│ │v1.0│ │v1.0│
└────┘ └────┘ └────┘

Step 3: 替换第 2 个
┌────┐ ┌────┐ ┌────┐
│v1.1│ │v1.1│ │v1.0│
└────┘ └────┘ └────┘

Step 4: 替换第 3 个
┌────┐ ┌────┐ ┌────┐
│v1.1│ │v1.1│ │v1.1│
└────┘ └────┘ └────┘
```

**优点**:
- 不需要额外资源
- 自动化程度高（K8s 原生支持）

**缺点**:
- 部署时间较长
- 新旧版本会同时存在

**K8s 滚动更新配置**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 最多额外启动 1 个实例
      maxUnavailable: 1  # 最多 1 个实例不可用
  template:
    spec:
      containers:
      - name: app
        image: my-service:v1.1
        readinessProbe:  # 健康检查
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
```

### 4. 金丝雀发布（Canary Deployment）

**原理**: 部署少量新版本实例，验证通过后全量发布

```
Phase 1: 部署 1 个金丝雀实例
┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
│ v1.0 │  │ v1.0 │  │ v1.0 │  │ v1.1 │ ← Canary
└──────┘  └──────┘  └──────┘  └──────┘
                                  │
                            观察指标 24h
                                  │
Phase 2: 全量发布                  ▼
┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
│ v1.1 │  │ v1.1 │  │ v1.1 │  │ v1.1 │
└──────┘  └──────┘  └──────┘  └──────┘
```

**适用场景**:
- 基础设施变更（如 JDK 升级）
- 依赖库大版本升级
- 性能优化验证


## 部署检查清单

### 部署前检查 (Pre-deployment)

```bash
#!/bin/bash
# scripts/deploy/pre-deployment-check.sh

set -euo pipefail

ENV=$1
VERSION=$2

echo "部署前检查: $ENV - $VERSION"
echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"

# 1. 版本号检查
echo "✓ 检查版本号格式..."
if ! [[ $VERSION =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]; then
  echo "❌ 版本号格式错误: $VERSION (期望 vX.Y.Z)"
  exit 1
fi

# 2. Git 标签检查
echo "✓ 检查 Git 标签..."
if ! git tag | grep -q "^${VERSION}$"; then
  echo "❌ Git 标签不存在: $VERSION"
  exit 1
fi

# 3. 测试通过检查
echo "✓ 检查测试状态..."
TEST_REPORT="docs/test/final-test-report.md"
if ! grep -q "所有测试通过" "$TEST_REPORT"; then
  echo "❌ 测试未全部通过"
  exit 1
fi

# 4. 代码覆盖率检查
echo "✓ 检查代码覆盖率..."
COVERAGE=$(grep -oP "总覆盖率.*\K[0-9]+" "$TEST_REPORT" || echo "0")
if [ "$COVERAGE" -lt 80 ]; then
  echo "❌ 代码覆盖率不足: ${COVERAGE}% (要求 ≥80%)"
  exit 1
fi

# 5. 安全扫描检查
echo "✓ 检查安全扫描..."
SECURITY_REPORT="docs/review/security-audit-report.md"
if grep -q "P0\|高危" "$SECURITY_REPORT"; then
  echo "❌ 存在高危安全问题"
  exit 1
fi

# 6. 配置文件检查
echo "✓ 检查配置文件..."
CONFIG_FILE="backend/src/main/resources/application-${ENV}.yml"
if [ ! -f "$CONFIG_FILE" ]; then
  echo "❌ 配置文件不存在: $CONFIG_FILE"
  exit 1
fi

# 7. 数据库连接检查
echo "✓ 检查数据库连接..."
DB_HOST=$(grep "url:" "$CONFIG_FILE" | grep -oP "//\K[^:/]+")
if ! nc -z "$DB_HOST" 3306; then
  echo "❌ 数据库连接失败: $DB_HOST"
  exit 1
fi

# 8. 依赖服务检查
echo "✓ 检查依赖服务..."
# Redis
REDIS_HOST=$(grep "redis.host" "$CONFIG_FILE" | grep -oP ": \K.*")
if ! redis-cli -h "$REDIS_HOST" ping > /dev/null 2>&1; then
  echo "❌ Redis 连接失败: $REDIS_HOST"
  exit 1
fi

# 9. 磁盘空间检查
echo "✓ 检查磁盘空间..."
DISK_USAGE=$(df -h / | tail -1 | awk '{print $5}' | sed 's/%//')
if [ "$DISK_USAGE" -gt 85 ]; then
  echo "❌ 磁盘空间不足: ${DISK_USAGE}% (要求 <85%)"
  exit 1
fi

# 10. 变更审批检查（生产环境）
if [ "$ENV" = "prod" ]; then
  echo "✓ 检查变更审批..."
  APPROVAL_FILE="docs/deploy/${VERSION}-approval.txt"
  if [ ! -f "$APPROVAL_FILE" ]; then
    echo "❌ 缺少变更审批文件"
    exit 1
  fi
fi

echo ""
echo "✅ 所有检查通过，可以部署"
exit 0
```

### 健康检查 (Health Check)

```bash
#!/bin/bash
# scripts/deploy/health-check.sh

set -euo pipefail

ENV=$1
VERSION=$2
MAX_RETRIES=30
RETRY_INTERVAL=10

echo "健康检查: $ENV - $VERSION"
echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"

# 获取服务地址
case $ENV in
  dev)
    BASE_URL="http://localhost:8080"
    ;;
  test)
    BASE_URL="http://test.internal:8080"
    ;;
  staging)
    BASE_URL="http://staging.internal:8080"
    ;;
  prod)
    BASE_URL="http://api.example.com"
    ;;
esac

# 1. 基础健康检查
echo "1️⃣  基础健康检查..."
for i in $(seq 1 $MAX_RETRIES); do
  if curl -f "${BASE_URL}/health" > /dev/null 2>&1; then
    echo "✅ 服务健康检查通过"
    break
  else
    echo "⏳ 等待服务启动... ($i/$MAX_RETRIES)"
    sleep $RETRY_INTERVAL
  fi
  
  if [ $i -eq $MAX_RETRIES ]; then
    echo "❌ 服务启动超时"
    exit 1
  fi
done

# 2. 版本检查
echo "2️⃣  版本检查..."
ACTUAL_VERSION=$(curl -s "${BASE_URL}/version" | jq -r '.version')
if [ "$ACTUAL_VERSION" != "$VERSION" ]; then
  echo "❌ 版本不匹配: 期望 $VERSION, 实际 $ACTUAL_VERSION"
  exit 1
fi
echo "✅ 版本正确: $ACTUAL_VERSION"

# 3. 数据库连接检查
echo "3️⃣  数据库连接检查..."
DB_STATUS=$(curl -s "${BASE_URL}/health/db" | jq -r '.status')
if [ "$DB_STATUS" != "UP" ]; then
  echo "❌ 数据库连接失败"
  exit 1
fi
echo "✅ 数据库连接正常"

# 4. Redis 连接检查
echo "4️⃣  Redis 连接检查..."
REDIS_STATUS=$(curl -s "${BASE_URL}/health/redis" | jq -r '.status')
if [ "$REDIS_STATUS" != "UP" ]; then
  echo "❌ Redis 连接失败"
  exit 1
fi
echo "✅ Redis 连接正常"

# 5. 关键接口冒烟测试
echo "5️⃣  关键接口冒烟测试..."
# 用户列表接口
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "${BASE_URL}/api/users?page=1&size=10")
if [ "$HTTP_CODE" != "200" ]; then
  echo "❌ 用户列表接口失败: HTTP $HTTP_CODE"
  exit 1
fi
echo "✅ 关键接口正常"

# 6. 性能指标检查
echo "6️⃣  性能指标检查..."
RESPONSE_TIME=$(curl -s -o /dev/null -w "%{time_total}" "${BASE_URL}/api/users?page=1&size=10")
RESPONSE_MS=$(echo "$RESPONSE_TIME * 1000" | bc | cut -d'.' -f1)
if [ "$RESPONSE_MS" -gt 1000 ]; then
  echo "⚠️  响应时间较慢: ${RESPONSE_MS}ms (期望 <1000ms)"
else
  echo "✅ 响应时间正常: ${RESPONSE_MS}ms"
fi

echo ""
echo "✅ 所有健康检查通过"
exit 0
```

## 数据库迁移

### Flyway 迁移脚本

```sql
-- V1.1.0__add_user_status.sql
-- 描述: 为用户表增加状态字段
-- 作者: 张三
-- 日期: 2026-09-15

-- 1. 增加字段（兼容旧版本）
ALTER TABLE t_user 
ADD COLUMN status VARCHAR(20) DEFAULT 'active' 
COMMENT '用户状态: active-活跃, inactive-停用, deleted-已删除';

-- 2. 为现有数据设置默认值
UPDATE t_user SET status = 'active' WHERE status IS NULL;

-- 3. 创建索引
CREATE INDEX idx_user_status ON t_user(status);

-- 4. 回滚脚本（记录在注释中，实际回滚用 undo 文件）
-- ALTER TABLE t_user DROP COLUMN status;
-- DROP INDEX idx_user_status ON t_user;
```

### 迁移最佳实践

1. **向后兼容**: 新版本代码必须兼容旧数据库结构
2. **分步迁移**: 
   - 第一次部署: 增加字段（nullable）
   - 数据迁移: 填充数据
   - 第二次部署: 字段改为 NOT NULL
3. **准备回滚**: 每个迁移脚本都有对应的回滚脚本
4. **先测试后生产**: staging 环境验证后再生产执行

## 回滚预案

### 回滚决策矩阵

| 问题严重程度 | 影响范围 | 回滚决策 | 执行时间 |
|------------|---------|---------|---------|
| P0 - 服务不可用 | 全部用户 | 立即回滚 | 5 分钟内 |
| P1 - 核心功能异常 | >50% 用户 | 立即回滚 | 15 分钟内 |
| P2 - 部分功能异常 | <50% 用户 | 评估后决定 | 30 分钟内 |
| P3 - 体验问题 | 少量用户 | 修复后发布 | 不回滚 |

### 快速回滚脚本

```bash
#!/bin/bash
# scripts/deploy/rollback.sh

set -euo pipefail

CURRENT_VERSION=$1
PREVIOUS_VERSION=$2

echo "回滚: $CURRENT_VERSION → $PREVIOUS_VERSION"
echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"

# 1. 确认回滚
read -p "确认回滚到 $PREVIOUS_VERSION? (yes/no): " CONFIRM
if [ "$CONFIRM" != "yes" ]; then
  echo "取消回滚"
  exit 1
fi

# 2. 蓝绿部署回滚（切换流量）
echo "1️⃣  切换流量到旧版本..."
kubectl patch service my-service -p "{\"spec\":{\"selector\":{\"version\":\"${PREVIOUS_VERSION}\"}}}"

# 3. 验证回滚
echo "2️⃣  验证回滚..."
sleep 10
bash scripts/deploy/health-check.sh prod "$PREVIOUS_VERSION"

# 4. 清理失败版本
echo "3️⃣  清理失败版本..."
kubectl delete deployment "my-service-${CURRENT_VERSION}"

# 5. 记录回滚
echo "4️⃣  记录回滚..."
cat >> docs/deploy/rollback-history.md << EOF
## 回滚记录: $(date +"%Y-%m-%d %H:%M:%S")
- 失败版本: $CURRENT_VERSION
- 回滚到: $PREVIOUS_VERSION
- 原因: [待补充]
- 操作人: [待补充]
EOF

echo ""
echo "✅ 回滚完成"
```

## 反模式

❌ **跳过测试直接部署**：认为"小改动不需要测试"，结果生产故障  
❌ **手动部署无记录**：SSH 登录服务器手动操作，无法追溯  
❌ **未准备回滚预案**：部署出问题后手忙脚乱不知如何回滚  
❌ **数据库迁移不可逆**：删除字段后无法回滚  
❌ **未验证健康检查**：部署完成后未检查服务状态就切换流量  
❌ **生产环境直接测试**：把生产当测试环境，发现问题再回滚  
❌ **凌晨部署无人值守**：凌晨自动部署，出问题无人处理
