# Phase 5: 测试策略（Test Strategy）

## 目标

- 制定全面的测试策略
- 定义各层级测试覆盖范围和目标
- 规划测试用例和测试数据
- 确保测试可追溯到需求

## 进入条件

- [ ] P4 PRD 验证已完成（功能验证通过）
- [ ] P4b PRD-代码对账已完成（实现完整性 100%）
- [ ] 代码已完成并通过基本冒烟测试
- [ ] 所有 P0 缺陷已修复

---

## 测试金字塔

```
         /\
        /  \  E2E 测试 (5%)
       /────\  集成测试 (15%)
      /──────\  单元测试 (80%)
     /────────\
```

**原则**：
- 单元测试为主（快速、稳定、可重复）
- 集成测试为辅（验证模块协作）
- E2E 测试为核心场景（模拟真实用户）

## 测试分层策略

### 1. 单元测试（Unit Test）

**目标覆盖率**: ≥ 80%

**测试范围**:
- 所有 Service 层业务逻辑
- 所有工具类（Utils）
- 所有数据转换（Converter/Mapper）
- 复杂的算法和计算逻辑

**不测试内容**:
- 简单的 POJO（getter/setter）
- 框架代码（Spring 容器、JPA）
- 第三方库

**示例**:
```java
@Test
void testCreateUser_Success() {
    // Given
    UserCreateRequest request = new UserCreateRequest();
    request.setName("张三");
    request.setEmail("zhangsan@example.com");
    
    when(userRepository.existsByEmail(anyString())).thenReturn(false);
    when(userRepository.save(any())).thenAnswer(i -> i.getArgument(0));
    
    // When
    UserDTO result = userService.createUser(request);
    
    // Then
    assertEquals("张三", result.getName());
    assertEquals("zhangsan@example.com", result.getEmail());
    verify(userRepository).save(any(User.class));
}

@Test
void testCreateUser_EmailExists_ThrowsException() {
    // Given
    UserCreateRequest request = new UserCreateRequest();
    request.setEmail("existing@example.com");
    
    when(userRepository.existsByEmail("existing@example.com")).thenReturn(true);
    
    // When & Then
    assertThrows(BusinessException.class, () -> {
        userService.createUser(request);
    });
}
```

### 2. 集成测试（Integration Test）

**目标覆盖率**: ≥ 60%（核心接口）

**测试范围**:
- Controller → Service → Repository 完整链路
- 数据库读写（使用测试数据库）
- 事务和并发控制
- 权限拦截器

**技术选型**:
- Spring Boot: `@SpringBootTest` + `@AutoConfigureMockMvc`
- 数据库: H2 内存数据库或 Testcontainers
- 断言: MockMvc + JsonPath

**示例**:
```java
@SpringBootTest
@AutoConfigureMockMvc
@Transactional
class UserControllerIntegrationTest {
    
    @Autowired
    private MockMvc mockMvc;
    
    @Test
    void testCreateUser_Integration() throws Exception {
        String requestBody = """
            {
                "name": "张三",
                "email": "zhangsan@example.com",
                "role": "USER"
            }
            """;
        
        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content(requestBody))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("张三"))
            .andExpect(jsonPath("$.email").value("zhangsan@example.com"));
        
        // 验证数据库
        User user = userRepository.findByEmail("zhangsan@example.com").orElseThrow();
        assertEquals("张三", user.getName());
    }
}
```

### 3. 端到端测试（E2E Test）

**目标覆盖率**: ≥ 95%（核心业务流程）

**测试范围**:
- 完整的用户场景（前端 + 后端 + 数据库）
- 跨模块的业务流程
- 关键的异常场景

**技术选型**:
- 后端: REST Assured / Spring RestTemplate
- 前端: Playwright / Selenium / Cypress
- 环境: 真实容器（Docker）

**核心场景示例**:
```markdown
## E2E-001: 用户注册到登录完整流程

### 前置条件
- 数据库清空
- 服务已启动

### 测试步骤
1. 用户访问注册页面
2. 填写用户信息（姓名/邮箱/密码）
3. 点击"注册"按钮
4. 系统发送验证邮件
5. 用户点击邮件中的验证链接
6. 用户使用注册的账号登录
7. 验证登录成功，进入首页

### 预期结果
- 注册成功，数据库新增用户记录
- 验证邮件发送成功
- 验证链接点击后，用户状态变为"已激活"
- 登录成功，返回 JWT token
- 首页显示用户信息
```

### 4. 性能测试（Performance Test）

**目标**:
- 接口响应时间 P95 < 500ms
- 接口响应时间 P99 < 1s
- 并发支持 500 QPS
- 错误率 < 0.1%

**测试工具**: JMeter / Gatling / wrk

**测试场景**:
```markdown
## 性能测试场景

### PT-001: 用户列表查询压测
- 并发用户: 100
- 持续时间: 5 分钟
- 请求参数: 分页查询（page=1, size=20）
- 预期 TPS: ≥ 500
- 预期响应时间: P95 < 500ms

### PT-002: 用户创建压测
- 并发用户: 50
- 持续时间: 3 分钟
- 请求参数: 随机用户信息
- 预期 TPS: ≥ 200
- 预期响应时间: P95 < 800ms

### PT-003: 混合场景压测
- 并发用户: 200
- 场景比例: 查询 70%, 创建 20%, 更新 10%
- 持续时间: 10 分钟
- 预期系统稳定运行，无内存泄漏
```

### 5. 安全测试（Security Test）

**测试范围**:
- SQL 注入
- XSS 跨站脚本
- CSRF 跨站请求伪造
- 权限绕过
- 敏感信息泄露

**测试工具**: OWASP ZAP / Burp Suite

**测试清单**:
```markdown
## 安全测试清单

### SEC-001: SQL 注入测试
- [ ] 在所有输入参数中注入 SQL 语句
- [ ] 验证系统是否使用参数化查询
- [ ] 验证是否有 SQL 错误信息泄露

### SEC-002: XSS 测试
- [ ] 在所有文本输入中注入脚本
- [ ] 验证输出是否进行 HTML 转义
- [ ] 验证富文本编辑器是否过滤危险标签

### SEC-003: 权限测试
- [ ] 普通用户尝试访问管理员接口
- [ ] 未登录用户尝试访问需要认证的接口
- [ ] 用户 A 尝试操作用户 B 的数据

### SEC-004: 敏感信息测试
- [ ] 验证密码是否加密存储
- [ ] 验证日志中是否有敏感信息
- [ ] 验证接口返回是否包含敏感字段
```

## 测试数据策略

### 1. 测试数据准备

**原则**:
- 数据独立：每个测试用例有独立的测试数据
- 数据清理：测试结束后清理数据（@Transactional 回滚）
- 数据真实：模拟真实业务场景的数据

**测试数据分类**:
```java
// 1. 基础数据（Master Data）
@Sql("/data/master-data.sql")  // 角色、权限、配置项等

// 2. 场景数据（Scenario Data）
@Sql("/data/user-management-scenario.sql")  // 特定场景的用户数据

// 3. 边界数据（Boundary Data）
User userWithMaxLengthName = new User();
userWithMaxLengthName.setName("A".repeat(100));  // 最大长度

// 4. 异常数据（Invalid Data）
User userWithInvalidEmail = new User();
userWithInvalidEmail.setEmail("invalid-email");  // 非法邮箱
```

### 2. 测试数据工厂

```java
public class TestDataFactory {
    
    private static final AtomicInteger counter = new AtomicInteger(0);
    
    public static User createUser() {
        int id = counter.incrementAndGet();
        User user = new User();
        user.setName("测试用户" + id);
        user.setEmail("test" + id + "@example.com");
        user.setStatus(UserStatus.ACTIVE);
        return user;
    }
    
    public static User createUser(Consumer<User> customizer) {
        User user = createUser();
        customizer.accept(user);
        return user;
    }
}

// 使用示例
@Test
void testCreateUser() {
    User user = TestDataFactory.createUser(u -> {
        u.setName("张三");
        u.setRole(Role.ADMIN);
    });
    // ...
}
```

## 反模式

❌ **无测试策略直接写用例**：边写边想，导致覆盖不全  
❌ **覆盖率目标过低**：只追求"跑通"，不追求质量  
❌ **只测正常流程**：忽略异常场景和边界条件  
❌ **测试数据不独立**：用例之间相互影响，不稳定  
❌ **需求追溯缺失**：写了很多用例，但不知道覆盖了哪些需求  
❌ **E2E 测试过多**：金字塔倒置，导致测试慢且不稳定  
❌ **性能测试缺失**：上线后才发现性能问题
