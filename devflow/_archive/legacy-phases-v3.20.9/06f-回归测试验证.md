# Phase 6f: 回归测试验证（Regression Testing）

## 目标

- 验证新功能不影响已有功能
- 确保修复的 bug 不再复现
- 验证重构后功能保持一致
- 建立回归测试基线

## 进入条件

- [ ] P6a-P6e 所有测试已完成
- [ ] 有明确的回归范围（新功能影响哪些已有功能）
- [ ] 上一版本的测试基线存在

---

## 回归测试场景

### 1. 新功能引入后的回归

**场景**: 新增"批量删除用户"功能后，验证原有的"单个删除"功能

**回归范围**:
- 用户列表查询
- 单个用户删除
- 用户详情页面
- 权限控制

**测试策略**: 执行上一版本的全量测试用例

---

### 2. Bug 修复后的回归

**场景**: 修复"分页查询最后一页数据重复"bug 后

**回归范围**:
- 分页查询第一页、中间页、最后一页
- 空列表查询
- 排序 + 分页
- 筛选 + 分页

**测试策略**: 执行 bug 相关的测试用例 + 相邻功能测试用例

---

### 3. 重构后的回归

**场景**: 重构用户服务层代码，将 UserService 拆分为 UserQueryService 和 UserCommandService

**回归范围**:
- 所有用户相关接口
- 用户权限验证
- 用户数据一致性

**测试策略**: 执行用户模块的全量测试用例

---

### 4. 依赖升级后的回归

**场景**: Spring Boot 从 2.7 升级到 3.2

**回归范围**:
- 全部功能
- 重点关注启动、配置、数据库连接

**测试策略**: 冒烟测试（核心流程）+ 重点模块全量测试

---

## 回归测试策略

### 1. 全量回归（Full Regression）

**适用场景**:
- 重大版本发布
- 核心框架升级
- 大规模重构

**执行内容**: 执行所有测试用例（单元 + 集成 + E2E）

**时间成本**: 高（数小时）

---

### 2. 选择性回归（Selective Regression）

**适用场景**:
- 小版本迭代
- 局部功能修改
- Bug 修复

**执行内容**: 
- 变更影响分析（Impact Analysis）
- 执行受影响模块的测试用例
- 执行高风险用例

**时间成本**: 中（数十分钟）

---

### 3. 冒烟回归（Smoke Regression）

**适用场景**:
- 快速验证
- 部署前快速检查
- 每日构建

**执行内容**: 执行核心业务流程（P0 用例）

**时间成本**: 低（数分钟）

---

## 变更影响分析

### 1. 代码级影响分析

**工具**: Git diff + 静态分析

```bash
#!/bin/bash
# scripts/impact-analysis.sh

# 获取变更的文件
CHANGED_FILES=$(git diff --name-only HEAD~1 HEAD)

echo "变更文件："
echo "$CHANGED_FILES"

# 分析影响范围
echo ""
echo "影响分析："

for file in $CHANGED_FILES; do
  # 查找调用该文件的代码
  if [[ $file == *.java ]]; then
    CLASS_NAME=$(basename "$file" .java)
    echo "查找 $CLASS_NAME 的调用者..."
    grep -r "$CLASS_NAME" backend/src --include="*.java" | \
      grep -v "^$file:" | \
      cut -d: -f1 | \
      sort -u
  fi
done
```

---

### 2. 功能级影响分析

**方法**: 根据需求追溯矩阵分析

```markdown
## 变更影响分析

### 变更内容
- 新增功能：批量删除用户
- 修改代码：UserService.deleteUser(), UserController.deleteUser()

### 直接影响
- 用户删除接口（DELETE /api/users/{id}）
- 用户列表页面（删除按钮）

### 间接影响
- 用户详情页面（删除按钮）
- 角色管理（用户被删除后角色关联）
- 权限验证（删除权限）

### 回归范围
- [ ] 用户删除（单个）
- [ ] 用户删除（批量）
- [ ] 用户详情页删除
- [ ] 角色-用户关联验证
- [ ] 权限验证
```

---

### 3. 基于风险的回归

**高风险区域**（必须回归）:
- 核心业务流程（登录、下单、支付）
- 高频使用功能
- 历史上 bug 多的模块
- 复杂的算法和逻辑

**低风险区域**（可选回归）:
- 独立的辅助功能
- 静态页面
- 配置页面

### 3. CI/CD 集成

```yaml
# .github/workflows/regression.yml
name: Regression Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  smoke-regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Start services
        run: docker-compose -f docker-compose.test.yml up -d
      
      - name: Run smoke regression
        run: npx playwright test --project=p0-critical
      
      - name: Upload report
        if: always()
        uses: actions/upload-artifact@v3
        with:
          name: regression-report
          path: playwright-report/

  full-regression:
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Start services
        run: docker-compose -f docker-compose.test.yml up -d
      
      - name: Run full regression
        run: npx playwright test
      
      - name: Upload report
        if: always()
        uses: actions/upload-artifact@v3
        with:
          name: full-regression-report
          path: playwright-report/
```

## 回归测试基线

### 1. 建立基线

**定义**: 某个稳定版本的测试结果，作为后续回归对比的标准

**建立时机**:
- 首次发布
- 重大版本发布
- 大规模重构后

**基线内容**:
```markdown
## 回归测试基线 v1.0.0

### 测试环境
- 版本: v1.0.0
- 日期: 2026-09-15
- 提交: abc123

### 测试结果
- P0 用例: 15 个，通过 15 个（100%）
- P1 用例: 45 个，通过 45 个（100%）
- P2 用例: 30 个，通过 28 个（93%）

### 已知问题
- P2-001: 用户导出功能在 IE 11 不可用（不修复）
- P2-002: 图表在 4K 屏幕下显示模糊（待优化）

### 性能基线
- 用户列表查询: P95 = 180ms
- 用户创建: P95 = 250ms
- 登录: P95 = 120ms
```

---

### 2. 基线对比

**对比内容**:
- 通过率变化
- 新增失败用例
- 性能退化

**示例**:
```markdown
## 回归测试对比报告 v1.1.0 vs v1.0.0

### 通过率对比
| 套件 | v1.0.0 | v1.1.0 | 变化 |
|------|--------|--------|------|
| P0 | 100% | 100% | ✅ 持平 |
| P1 | 100% | 98% | ❌ -2% |
| P2 | 93% | 93% | ✅ 持平 |

### 新增失败用例
- P1-012: 用户删除后角色关联未清理 ❌
- P1-023: 批量删除权限验证缺失 ❌

### 性能对比
| 接口 | v1.0.0 | v1.1.0 | 变化 |
|------|--------|--------|------|
| 用户列表查询 | 180ms | 185ms | ⚠️ +5ms |
| 用户创建 | 250ms | 480ms | ❌ +230ms |
| 登录 | 120ms | 115ms | ✅ -5ms |

### 回归结论
- ❌ 不通过：2 个 P1 缺陷，1 个性能退化
- 建议：修复 P1-012 和 P1-023，优化用户创建性能
```

## 视觉回归测试

### 1. 截图对比

**工具**: Playwright / Percy / Chromatic

**示例**:
```javascript
// tests/regression/visual.spec.js
import { test, expect } from '@playwright/test';

test('首页视觉回归', async ({ page }) => {
  await page.goto('http://localhost:3000');
  
  // 等待页面加载完成
  await page.waitForLoadState('networkidle');
  
  // 截图对比
  await expect(page).toHaveScreenshot('homepage.png');
});

test('用户列表视觉回归', async ({ page }) => {
  await page.goto('http://localhost:3000/users');
  await page.waitForLoadState('networkidle');
  
  // 对比特定元素
  const table = page.locator('table');
  await expect(table).toHaveScreenshot('user-table.png');
});
```

**配置**:
```javascript
// playwright.config.js
export default {
  expect: {
    toHaveScreenshot: {
      maxDiffPixels: 100,  // 最大允许 100 像素差异
      threshold: 0.2,      // 20% 容差
    },
  },
};
```

### 2. 视觉回归服务

**Percy 集成**:

### 3. 失败用例分析
```markdown
## 失败用例

### REG-001: 用户删除后角色关联未清理

**用例**: 删除用户后，角色-用户关联表未清理  
**优先级**: P1  
**回归类型**: 新功能引入的 bug  
**重现步骤**:
1. 创建用户并分配角色
2. 批量删除用户
3. 查询角色-用户关联表

**预期**: 关联记录被删除  
**实际**: 关联记录仍存在  
**根因**: UserService.batchDelete() 缺少级联删除逻辑  
**修复**: 增加级联删除  

---

### REG-002: 批量删除权限验证缺失

**用例**: 普通用户可以批量删除用户  
**优先级**: P0（安全问题）  
**回归类型**: 新功能权限缺失  
**重现步骤**:
1. 普通用户登录
2. 调用批量删除接口
3. 删除成功

**预期**: 返回 403 权限不足  
**实际**: 删除成功  
**根因**: UserController.batchDelete() 未添加 @PreAuthorize  
**修复**: 增加权限验证注解  
```

## 反模式

❌ **不做回归测试**：认为"改得少，不会影响其他功能"  
❌ **只测试变更代码**：忽略间接影响  
❌ **手工回归测试**：耗时且不稳定  
❌ **没有测试基线**：无法判断是新 bug 还是老问题  
❌ **回归测试太慢**：导致无人执行  
❌ **失败用例不分析**：不知道是代码问题还是测试用例过时  
❌ **视觉回归太严格**：1px 差异导致失败
