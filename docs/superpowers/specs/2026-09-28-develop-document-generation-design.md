# Develop 文档生成精度升级设计

**状态：** 待用户审阅
**目标版本：** develop 1.1.0
**范围：** `develop/` 的文档生成与详设校验链路

## 目标

在保留 develop 现有命令和 `02-详细设计.json` 正本的基础上，借鉴 DevFlow 文档生成链路的精度：模板、Schema、基线和产物可追溯；Markdown 可确定性重建；单文档与总分文档都能按冻结验收集合对账；Gate 能用正例和反例证明校验有效。

本次升级只覆盖 develop 的文档生成、完整性校验和回归门禁。它不迁入 DevFlow 的 P0–P10 交付流程，也不从详设自动生成业务代码。

## 现状与设计依据

当前 `develop/脚本/develop.py` 已经实现：

- 从文档清单载入模板并生成文档骨架与详设 JSON。
- 用 `详设数据结构.json` 校验必填字段、类型和未知字段。
- 将冻结验收点作为覆盖分母，检查覆盖集合相等、对象引用闭环、重复 ID、孤立对象理由和空集合理由。
- 从 JSON 确定性渲染完整 Markdown，并在 `check-design` 中比较 Markdown 与预期输出。

DevFlow 当前详设生成链路进一步提供：

- 文档、模板、Schema 的版本和角色契约。
- `validate → render → gate` 的失败关闭顺序。
- 有定位锚点的渲染块，允许生成内容与人工说明共存。
- 总分设计包登记各文档及其验收点子集，并对账冻结分母。
- 将输入和生成产物的 SHA256 纳入收据，证明 Gate 检查的是哪一版内容。

本设计把这些生成机制移植到 develop 的职责边界内，沿用现有 JSON 字段模型和 `init`、`render-design`、`check`、`check-design` 命令。

## 方案

### 1. 版本化文档契约

扩展 `develop/契约/文档清单.json`，使每个文档登记稳定的 `id`、目标路径、模板 ID、模板版本、Schema（如适用）、文档角色和章节/锚点。详设契约登记 `schema_version`、模板身份和渲染目标。`develop.py init` 在创建文件时写入被选模板的准确 ID 与版本；未知模板变量、版本不匹配、模板缺失或锚点契约不完整均报错退出。

模板版本由受版本控制的清单维护。Gate 校验文档声明与所选模板一致，并校验模板实际内容指纹；不能只接受文档中任意填写的版本字符串。

### 2. 锚点块确定性渲染

把详设 Markdown 分成生成块和说明正文。生成块使用配对标记，例如：

```markdown
<!-- develop:begin:tables -->
<!-- develop:end:tables -->
```

每个 JSON 驱动的块在模板中必须恰好出现一次。渲染器只替换已登记的生成块，保留块外的架构图、方案理由和人工说明；缺块、重复块、未配对、嵌套或未知块均失败关闭。所有业务字段和清单仍以 JSON 为准，块外内容不得复制出第二份相互矛盾的结构化契约。

`check-design` 以 JSON、模板和文档清单重新计算各生成块并比对文档现状。任何手改生成块或模板漂移都要求重新渲染和复核。

### 3. 单文档与总分文档包

单文档继续使用现有 `02-详细设计.json` 与 `02-详细设计.md`。新增可选 `design-package.json`，登记总文档、分文档的稳定 ID、路径、模板角色、模块/对象归属和验收点子集。每份分文档按对象类型列出其拥有的对象 ID；所有设计对象必须至少归属一份分文档，引用的对象 ID 必须存在。共享对象须显式登记为共享，并在渲染时保持相同定义。总分包中的文档路径不得重复；所有声明的文档必须存在；各分文档验收点集合的并集必须与冻结验收点集合完全相等。交叉模块对象可被显式引用，但不得因此漏掉任何验收点或产生未登记文档。

未提供设计包时，默认使用现有单文档模式。已有项目无需仅为升级而改目录或重命名文件。

### 4. 基线、模板与产物指纹

`render-design` 校验完成后生成可复核的设计生成收据，记录：

- 详设 JSON、冻结验收点清单、Schema、模板和文档清单的 SHA256。
- 生成的 Markdown 文件及其 SHA256。
- 工具版本、模板 ID/版本、文档包模式和执行结果。

Gate 重新计算这些指纹，并确认收据对应当前输入和输出。验收点清单或设计 JSON 在评审后发生变化时，原收据失效，必须重新渲染、校验和评审。收据只证明校验过的文件身份与流程结果，不证明业务判断本身正确。

### 5. 校验阶段与失败语义

统一顺序为：

1. 校验清单、Schema、模板身份和模板锚点。
2. 校验 JSON 结构、固定基线、对象 ID 唯一性、引用闭环、字段引用及零结果声明。
3. 对账覆盖集合和设计包文档集合。
4. 确定性渲染 Markdown。
5. 检查生成内容与文档一致，检查占位符和未决项状态。
6. 产出收据；任一步骤非零都不得签发 PASS 收据。

零结果必须逐类写原因；对象为空和声称零结果相互矛盾时失败。未决业务规则、缺少事实来源或需要人为决策的字段仍须显式标记，不能被结构校验转换成“设计完成”。

### 6. 回归门禁

新增文档生成测试集，至少包含：完整单文档正例、完整总分包正例，以及缺字段、未知字段、重复 ID、验收点漏项/多项、悬空引用、正反向引用不一致、字段引用不存在、零结果缺理由、对象与零结果矛盾、模板版本错误、锚点缺失/重复/不配对、手改渲染块、输入或产物哈希过期、设计包路径重复和验收点并集不完整等反例。

回归结果必须由真实进程退出码判断；只检查输出文本中是否包含“PASS”不构成通过。失败用例须证明 Gate 非零并指出对应路径或 ID。

## 数据流

```text
冻结验收点 + 详设 JSON + 文档清单/Schema/模板 + 可选设计包
                         │
                         ▼
              校验结构、基线与引用
                         │ PASS
                         ▼
              替换模板中的生成锚点块
                         │
                         ▼
       一致性检查 + 指纹收据 + 文档生成 Gate
```

JSON 是结构化设计对象和追溯关系的唯一正本；模板是展示布局与写作提示的权威来源；Markdown 是可阅读、可评审的渲染结果。块外说明用于表达原因、架构和取舍，不代替表、接口、规则或覆盖矩阵。

## 文件职责

- `develop/SKILL.md`：说明何时进入文档流程、命令顺序、阻断条件和人工评审边界。
- `develop/契约/文档清单.json`：登记文档、模板、Schema、版本和锚点契约。
- `develop/契约/详设数据结构.json`：约束设计对象字段和结构。
- `develop/契约/设计包数据结构.json`：约束总分文档包及对象归属（新增）。
- `develop/模板/02-详细设计.json`：初始化结构化正本。
- `develop/模板/02-详细设计.md`：详设章节布局、模板身份和生成块锚点。
- `develop/脚本/develop.py`：现有 CLI 的校验、生成和一致性入口；若新增逻辑使单文件难以维护，可拆为内部模块，但 CLI 行为保持兼容。
- `develop/tests/`：完整正例、反例夹具和真实退出码回归（新增）。

## 兼容与迁移

- 保持 `develop.py init`、`render-design`、`check`、`check-design` 现有命令名和退出码语义。
- 单文档模式继续作为默认模式；总分模式由显式设计包启用。
- 继续从现有冻结验收点 Markdown 表格读取 ID 和需求映射；校验解析出的集合非空、ID 唯一、表结构有效，并把完整文件哈希写入收据。
- 升级时为现有模板分配确定的 ID 和版本；迁移现有详设模板时，以当前 JSON 字段渲染生成块，保留经确认的块外说明。
- 对已有验收清单继续使用当前 Markdown 文件作为冻结输入，并记录内容哈希；本次不新增第二份验收 JSON 正本，避免引入双写来源。
- 只修改 `develop/` 和本设计文档。保留已有 `README.md`、`sync.sh` 与其他工作区内容。

## 精度边界

结构校验、集合对账、引用闭环、确定性渲染和指纹收据可以证明文档没有结构性遗漏或生成漂移。它们无法单独证明规则符合真实业务、技术方案可运行或场景判断正确。放行仍需有来源依据的逐项评审；评审应核对 PRD/现状事实、正常与异常流程、权限和数据边界。后续开发测试再验证设计是否能在目标代码和运行环境中兑现。

## 验收标准

1. 现有单文档输入可以按登记的模板 ID/版本完成初始化、渲染和检查。
2. JSON 中的每个设计对象和覆盖行都能从正确锚点块渲染；重复生成得到字节一致的生成块。
3. 块外人工说明在渲染后保留；手改生成块、锚点异常或模板身份不符被 Gate 拒绝。
4. 冻结验收点集合与 coverage 集合严格相等；对象引用双向一致；未知、悬空、重复和无理由对象均被拒绝。
5. 空对象集合只有在存在明确零结果理由时通过；非空对象集合声明同类零结果时失败。
6. 总分设计包中的文件登记唯一、文件齐全，分文档验收点并集严格覆盖冻结集合；遗漏、未登记文件或错误路径被拒绝。
7. 输入、模板、Schema、清单或生成产物变化后，旧收据不能通过。
8. 正例和所列关键反例都有自动化回归，Gate 按真实退出码判定。
9. 生成文档保留详尽详设标准要求的逐表字段、逐接口字段、规则、流程、页面交互、质量决定和逐验收点追溯，不用摘要或样例替代全量清单。
