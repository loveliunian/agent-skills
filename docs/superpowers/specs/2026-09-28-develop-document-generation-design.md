# Develop 文档生成精度升级设计

**状态：** 待用户审阅
**目标版本：** develop 1.1.0
**范围：** `develop/` 的 PRD 需求抽取、验收基线冻结和详设生成链路

## 目标

在保留 develop 的使用入口基础上，先保证 PRD 中的需求、约束和未决项能完整进入稳定的验收基线，再保证每个冻结验收点都落到详设对象并能确定性渲染。模板/Schema/基线可追溯、总分文档对账和生成收据仍属于目标，但排在 PRD→验收点→详设的完整性闭环之后。

本次升级只覆盖 develop 的文档生成、完整性校验和回归门禁。它不迁入 DevFlow 的 P0–P10 交付流程，也不从详设自动生成业务代码。

## 现状与设计依据

当前 `develop/脚本/develop.py` 已经实现：

- 从文档清单载入模板并生成文档骨架与详设 JSON。
- 用 `详设数据结构.json` 校验必填字段、类型和未知字段。
- 将冻结验收点 Markdown 表格作为覆盖分母，检查覆盖集合相等、对象引用闭环、重复 ID、孤立对象理由和空集合理由。
- 从 JSON 确定性渲染完整 Markdown，并在 `check-design` 中比较 Markdown 与预期输出。

当前缺口在 PRD 输入侧：没有可审计的源内容盘点与需求分类正本；PRD 需求到原子验收点的映射目前主要靠人工维护 Markdown 表；设计阶段只能证明自己覆盖了该表里已出现的验收点，不能证明表本身完整代表了 PRD。

DevFlow 当前详设生成链路进一步提供：

- 文档、模板、Schema 的版本和角色契约。
- `validate → render → gate` 的失败关闭顺序。
- 有定位锚点的渲染块，允许生成内容与人工说明共存。
- 总分设计包登记各文档及其验收点子集，并对账冻结分母。
- 将输入和生成产物的 SHA256 纳入收据，证明 Gate 检查的是哪一版内容。

本设计只把生成与验证机制建设在 develop。PRD Markdown 保留为原始需求来源；结构化需求清单记录 PRD 全量提取；现有原子验收 Markdown 继续作为人工冻结的验收基线；详设 JSON 是设计对象正本。DevFlow 仅是只读参照，不修改 DevFlow 文件。

## 方案

### 0. PRD 源内容盘点与需求提取（第一优先级）

为清单登记的主 PRD Markdown 增加确定性源内容清单：按标题、段落、列表项、表格表头/数据行切分为可定位的 source unit，表格数据行同时保留对应列名，围栏代码、引用块、HTML 和无法结构化解析的块以原文及行号保留为 code/opaque source unit 并附审阅提示；扫描器不能因 PRD 的展示格式拒绝或丢弃内容。记录稳定 ID、原文、起止行和 PRD 文件 SHA256。显式链接的图片/原型/附件也生成 asset source unit；本流程只记录本地文件指纹，不抓取远端资源或自动 OCR。缺失、远端或不可读的附件须保持未解决并阻断冻结，直到有来源证据的人工转录/说明被登记。未链接的其他需求文档不会自动发现，须先合并到主 PRD。每个 source unit 必须且只能被分类为需求、约束、假设、范围外、风险、背景/说明或未决问题；不能静默遗漏。扫描器负责枚举 Markdown 内容，不负责推断业务语义。

AI 从完整 source unit 清单提取结构化需求 JSON：每条需求有稳定 ID、原文引用、规范化陈述、是否强制、角色/触发/结果（适用时）、关联实体/操作/约束、状态和待澄清项。需求和验收点 ID 保持项目既有格式，不强制 `REQ-` 或 `AC-` 前缀。一个 source unit 含多个可独立验证行为时必须拆分成多条需求并共同引用来源；纯背景、重复项或不形成验收行为的条目须明确分类和理由。

要求独立复核：第二遍从原始 PRD 和 source unit 清单重新核对结构化需求，记录新增、缺失、语义变化和重复候选。任何差异都须逐项裁决并留依据；不能用平均稳定性分数抵消一个未处理的关键漏项。台账必须记录提取者和不同的复核者 ID、复核完成状态、所审 PRD 哈希、来源单元数量、结论和证据；该记录是流程凭据，不能单独证明语义正确。机器门禁检查 source unit 全覆盖、引用真实、资产已阅读、差异已裁决；所有强制需求必须已确认，任何仍待确认的强制需求阻断验收冻结与详设。结构化清单的完整性不能由同一份清单自证，必须保留 PRD 哈希和独立复核结论。

### 0.1 原子验收点冻结

保留现有 `02-原子验收点清单.md` 作为人工评审和冻结的验收基线，增强解析校验并记录完整文件 SHA256。每个已确认且可验证的需求必须关联一个或多个验收点；被判定为背景/范围外/不单独验收的需求需有显式理由。存在未澄清的强制行为、未裁决的提取差异或未映射的需求时，不得冻结。

保留当前验收点稳定 ID；冻结后任何 ID 集合、文本、来源或映射变化都形成新基线版本并要求重新评审。现阶段不另建一份验收点 JSON 正本，避免 Markdown 与 JSON 双写。

### 1. 版本化文档契约

扩展 `develop/契约/文档清单.json`，使每个文档登记稳定的 `id`、目标路径、模板 ID、模板版本、Schema（如适用）、文档角色和章节/锚点。详设契约登记 `schema_version`、模板身份和渲染目标。`develop.py init` 在创建文件时写入被选模板的准确 ID 与版本；未知模板变量、版本不匹配、模板缺失或锚点契约不完整均报错退出。

模板版本由受版本控制的清单维护。Gate 校验文档声明与所选模板一致，并校验模板实际内容指纹；不能只接受文档中任意填写的版本字符串。

### 2. 锚点块确定性渲染

把详设 Markdown 分成生成块和说明正文。生成块使用配对标记，例如：

```markdown
<!-- develop:begin:tables -->
<!-- develop:end:tables -->
```

每个 JSON 驱动的块在模板中必须恰好出现一次。渲染器只替换已登记的生成块，保留块外的架构图、方案理由和人工说明；缺块、重复块、未配对、嵌套或未知块均失败关闭。所有业务字段和清单仍以 JSON 为准，块外内容不得复制出第二份相互矛盾的结构化契约。

`check-design` 以 JSON、模板和文档清单重新计算各生成块并比对文档现状。任何手改生成块或模板漂移都要求重新渲染和复核。

所有通过 `init` 或 `render-design` 生成的 Markdown 文档均在渲染时为 H2 及以下章节添加层级编号（`1`、`1.1`、`1.1.1`）；H1 文档标题不编号。编号不写入 JSON 正本、文档清单或模板章节名；章节校验先去掉编号再与清单对账。编号生成须幂等，并跳过围栏代码块中的 Markdown 示例。

JSON 中的类型化对象引用保持稳定 ID。渲染器生成按对象类型隔离的稳定锚点，将接口、规则、流程、页面、表/字段及验收覆盖中的引用转成 Markdown 链接。总详设内使用文内锚点；分文档模式优先链接到本篇已归属对象，否则使用相对文档路径链接到其子文档所有者。设计校验先验证引用 ID 和文档归属，再生成链接；章节编号或对象顺序变化不要求手工更新引用。

### 3. 单文档与总分文档包

每个项目显式选择 `single` 或 `total_subdocuments` 模式，并在 `mode_reason` 记录决策依据。该结构决策在详设开始前冻结，依据模块/服务拆分、跨域依赖、独立演进需要和团队并行方式；模块数量仅为权衡输入而非硬阈值。默认 `single` 只渲染一份完整详设；`total_subdocuments` 同时渲染总详设和模块分详设，并要求先列好文档计划。用统一的详设输出配置记录模式、总文档路径和（分包模式下）子文档路径与对象归属。两种模式均允许调用方设置总文档路径，故可生成 `m01-base-详细设计.md`；所有输出路径须保持在项目目录内、唯一且登记在收据中。单文档模式不要求人为重复录入总文档对象/验收集合，渲染器从详设正本和冻结验收基线推导；分包模式要求显式列出对象归属和验收点子集。

分包模式中，文档配置登记总文档、分文档的稳定 ID、路径、模板身份、模块/对象归属和验收点子集。总文档渲染系统级决策、全量对象与验收索引；表字段、接口字段、规则/流程细节及页面交互在其所有者子文档展开，索引从总文档直接链接到所有者。对象归属覆盖所有内置类型与通用领域对象；约束、假设和范围外事项作为全局上下文保留。所有设计对象必须至少归属一份分文档，引用的对象 ID 必须存在。共享对象须显式登记为共享，并在渲染时保持相同定义。总文档验收集合必须等于冻结集合；所有子文档验收点集合的并集必须与冻结验收点集合完全相等。分文档的验收覆盖行所引用的设计对象必须归属该文档；功能域可作为跨文档共享上下文，对象所引用的验收点需列入其所属文档。文档路径不得重复（按大小写/Unicode 等价形式检查）；所有声明的文档必须生成且纳入收据。文档使用文档清单登记的模板 ID/版本。

### 3.1 全量详设结构

详设正本除现有功能域、表字段、接口字段、业务规则、流程、页面、质量决定、领域对象和验收追溯外，提供可独立校验及分包归属的术语表、权限矩阵、架构/ER/时序/状态图、内部与外部依赖、复用组件/服务决策。每项都使用稳定 ID，适用时记录 PRD 来源、需求、验收点和类型化设计引用；没有直接验收点映射的条目写明理由。Markdown 模板按固定章节渲染全量清单，摘要只作导航，不能替代对象清单。项目特有对象仍用通用 `domain_objects`，不为单个 PRD 改核心类型。

未提供设计包时，默认使用现有单文档模式。已有项目无需仅为升级而改目录或重命名文件。

### 4. 基线、模板与产物指纹

`render-design` 校验完成后生成可复核的设计生成收据，记录：

- 详设 JSON、冻结验收点清单、Schema、模板和文档清单的 SHA256。
- 生成的 Markdown 文件及其 SHA256。
- 工具版本、模板 ID/版本、文档包模式和执行结果。

Gate 重新计算这些指纹，并确认收据对应当前输入和输出。验收点清单或设计 JSON 在评审后发生变化时，原收据失效，必须重新渲染、校验和评审。收据只证明校验过的文件身份与流程结果，不证明业务判断本身正确。

### 5. 校验阶段与失败语义

统一顺序为：

1. 校验 PRD 指纹和 source unit 盘点；每个源单元有分类与原文位置。
2. 校验需求 JSON、独立复核差异和未决问题；差异均有裁决，需求/约束/范围边界可追溯。
3. 校验原子验收 Markdown：需求覆盖集合完整、验收点原子且可观察、来源真实、ID 唯一，再冻结基线。
4. 校验详设 JSON：每个冻结验收点有设计落点和验证方式，需求、表字段、接口字段、规则、流程、页面及质量决定的引用闭环。
5. 对账设计包文档集合（启用总分模式时）。
6. 确定性渲染详设 Markdown 的生成锚点块。
7. 检查生成内容与文档一致，检查占位符和未决项状态。
8. 产出指纹收据；任一步骤非零都不得签发 PASS 收据。

零结果必须逐类写原因；对象为空和声称零结果相互矛盾时失败。未决业务规则、缺少事实来源或需要人为决策的字段仍须显式标记，不能被结构校验转换成“设计完成”。

### 6. 回归门禁

新增文档生成测试集，至少包含：完整单文档正例、完整总分包正例，以及缺字段、未知字段、重复 ID、验收点漏项/多项、悬空引用、正反向引用不一致、字段引用不存在、零结果缺理由、对象与零结果矛盾、模板版本错误、锚点缺失/重复/不配对、手改渲染块、输入或产物哈希过期、设计包路径重复和验收点并集不完整等反例。

回归结果必须由真实进程退出码判断；只检查输出文本中是否包含“PASS”不构成通过。失败用例须证明 Gate 非零并指出对应路径或 ID。

## 数据流

```text
PRD 原文 ──> source unit 盘点 ──> 结构化需求清单 ──> 独立复核与差异裁决
                                                     │
                                                     ▼
                          原子验收点 Markdown 冻结 ──> 详设 JSON
                                                     │
                           文档清单/Schema/模板 ────┤
                                                     ▼
                       完整性/追溯校验 ──> 锚点块渲染 ──> 指纹收据与 Gate
```

PRD 是业务原文来源；source unit 清单证明扫描范围；结构化需求 JSON 记录抽取结论；原子验收 Markdown 是经评审冻结的分母；详设 JSON 是设计对象和追溯关系的正本。模板是展示布局与写作提示的权威来源；需求清单和详设 Markdown 是可阅读、可评审的视图，验收 Markdown 是人工确认的冻结记录。块外说明用于表达原因、架构和取舍，不代替结构化条目。

- 对已有验收清单继续使用当前 Markdown 文件作为冻结输入，并记录内容哈希；本次不新增第二份验收 JSON 正本，避免引入双写来源。
- 只修改 `develop/` 和本设计文档。保留已有 `README.md`、`sync.sh` 与其他工作区内容。

## 精度边界

结构校验、集合对账、引用闭环、确定性渲染和指纹收据可以证明文档没有结构性遗漏或生成漂移。它们无法单独证明规则符合真实业务、技术方案可运行或场景判断正确。放行仍需有来源依据的逐项评审；评审应核对 PRD/现状事实、正常与异常流程、权限和数据边界。后续开发测试再验证设计是否能在目标代码和运行环境中兑现。

## 验收标准

1. 现有单文档输入可以按登记的模板 ID/版本完成初始化、渲染和检查。
2. PRD 每个 source unit 都有唯一分类，需求条目都有真实 PRD 来源；扫描范围和源哈希可复核。
3. 独立复核能发现需求遗漏、重名/重复项和语义变化；差异未裁决或未决强制需求存在时不能冻结。
4. 每个冻结的可验证需求均映射到至少一个原子验收点；每个验收点可单独判定且含来源、前置条件、操作、结果和验证方式。
5. 详设覆盖集与冻结验收集严格相等；对象引用双向一致；字段来源和不存在的引用被识别。
6. JSON 中的每个设计对象和覆盖行都能从正确锚点块渲染；重复生成得到字节一致的生成块。
7. 块外人工说明在渲染后保留；手改生成块、锚点异常或模板身份不符被 Gate 拒绝。
8. 空对象集合只有在存在明确零结果理由时通过；非空对象集合声明同类零结果时失败。
9. 总分设计包中的文件登记唯一、文件齐全，分文档验收点并集严格覆盖冻结集合；遗漏、未登记文件或错误路径被拒绝。
10. 输入、模板、Schema、清单或生成产物变化后，旧收据不能通过。
11. PRD 抽取、验收冻结、详设校验、单文档/总分渲染均有真实正例和关键反例回归，Gate 按真实退出码判定。
12. 生成文档保留详尽详设标准要求的逐表字段、逐接口字段、规则、流程、页面交互、质量决定和逐验收点追溯，不用摘要或样例替代全量清单。
