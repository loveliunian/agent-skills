## 2. 架构分层与依赖方向

以下两种形态共用的部分:

- Controller 只做参数校验与编排,业务逻辑在 Service,数据访问在 Repository/Mapper [测试]
- 依赖方向单向:Controller → Service → Repository,禁止反向与跨层 [测试]
- 业务模块/服务之间禁止循环依赖(包级切片判环) [测试]
- 公共代码下沉 common/shared 模块;common 只依赖自身与基础库,不依赖任何业务模块 [测试]
- 跨业务边界的写操作必须有明确一致性策略:<同事务/最终一致+补偿,按详设保留一项> [约定]

形态专属部分(按上面的架构形态保留对应一条,删除另一条):

- 【单体】新建工程默认 **Maven 多模块布局**:`common`(响应体/异常/工具,只放真跨域的,禁养肥) + 每业务域一个 module(`controller+service+mapper+entity` 同域同模块) + `app` 启动壳(Application/Flyway/配置);既有单模块工程不强制回溯改造。并行开发各 feature 只编自己模块(`mvn -pl <module> -am test`),共享构建面竞态随之消失 [测试]
- 【单体】跨业务模块只能调用对方对外暴露的 Service 接口包,禁止直引 `<其他模块>.internal..` / `..repository..` / `..mapper..` [测试]
- 【微服务】服务间调用只走 Feign/声明式客户端,禁止直接引用其他服务的 internal/entity/mapper 包 [测试]
- 强制规则对应的测试见 specs/guard-tests-setup.md;规则与测试类的对照关系见该文档"规则↔守卫对照"一节

## 3. 接口契约

- 先契约后实现:每个 feature 的接口先写 OpenAPI 3.0 契约,实现以契约为准 [评审]
- 契约文件与 feature spec 同目录(`specs/<F编号>-<短名>/`),脚本做结构校验 [评审]
- 统一响应结构:`{ code, message, data }`;code=0 成功,非 0 按 `specs/constitution.md` 错误码分段 <详设交代分段规则,否则待定(Q00x)> [约定]
- 分页请求统一参数:`pageNum/pageSize`;分页响应统一结构:`{ total, list }` [约定]
- 破坏性契约变更(删字段、改类型、改语义)必须在 spec 修订记录登记并通知前端 [评审]
- 时间字段传输格式统一 ISO 8601 或 `yyyy-MM-dd HH:mm:ss` <二选一,详设定> [约定]

## 4. 命名与代码风格

后端(阿里巴巴《Java 开发手册》强制项基线):

- POJO 类中布尔类型属性禁止加 is 前缀 [评审]
- Service 接口以 Service 结尾,实现以 Impl 结尾;DAO/Mapper 以 Mapper 结尾 [评审]
- 事务注解必须写 `@Transactional(rollbackFor = Exception.class)` [评审]
- 禁止使用过时(@Deprecated)API;禁止在循环中做远程调用/SQL 查询 [评审]
- 异常必须处理或向上抛出并带上下文,禁止空 catch [评审]
- 日志用占位符 `log.info("xx {}", var)`,禁止字符串拼接;禁止 System.out [评审]

数据库:

- 表名/字段名小写下划线;布尔字段 is_ 前缀;时间字段 create_time/update_time [约定]
- 每表必备:id(主键)、create_time、update_time、<按需 del_flag> [约定]
- 默认不建物理外键,关联靠应用层与索引 <以详设为准> [约定]
- 变更脚本放 <目录约定>,含回滚说明 [评审]

前端:

- 组件 PascalCase,组合式函数 useXxx,常量 UPPER_SNAKE_CASE [评审]
- props 必写类型与默认值;禁止 v-for 与 v-if 同标签并用 [评审]
- 接口调用统一收敛到 src/api 目录,组件内禁止直写 fetch/axios [评审]

## 5. AI 实现规则

- 一次只实现一个 feature,严格按该 feature spec 任务清单的 T 编号顺序
- 不修改 spec 未覆盖的既有代码;确需改动时停下说明并等用户确认
- 完成判据:守卫测试通过 + 该 feature 单测通过 + spec 验收标准逐条自验
- spec 与实现出现偏差时,偏差写回 spec 修订记录,保持规范为真源
- 提交粒度:一个 T 一条 commit,message 格式 `<F编号> T<n>: <做了什么>`
- 实现中遇到 spec 未覆盖的决策点:登记新 Q。**未开启委托模式**(无 `specs/_work/gate-delegation.json`)时停下询问;开启委托模式时按其配置自裁,但每次自裁必须追加 `specs/_work/gate-decisions.md` 留痕,五类红线事项(高阻塞 Q、spec 与详设/现有代码矛盾、3 轮不收敛、守卫挡路且实现没错、无权拍板事项)仍一律停

## 7. 测试策略

测试分五层,每层有独立分母,缺一层即体系不完整;分母声明与实际执行的差集由守门引擎对账:

- L1 静态守卫(ESLint/vue-tsc/ArchUnit):分母=守卫清单,全绿 [测试]
- L2 单元测试:行覆盖率分层阈值——核心业务 Service 不低于 <90%,Controller/配置类不低于 <70%,生成代码按需 exclude>;spec 每条业务规则 R 必须有自动化验证落点(单测/接口用例/Playwright 触达其一),规则覆盖要求 100%,行覆盖率不追满分 [测试]
- L3 接口全量测试:分母=spec apis[] 全集+每条 errorCodes;用例落 `specs/_work/api-tests/<F编号>/`,豁免逐条登记 _exempt.md;deliver 与收尾两道对账差集即红 [测试]
- L4 场景链路测试:分母=验收 A 全集;脚本落 `specs/_work/local-tests/<F编号>/`,只写跨接口业务链路,接口级行为归 L3 不重复;收尾前全量重跑全绿,归档 <tests/e2e 或按项目约定> [测试]
- L5 浏览器冒烟:分母=页面清单×主链+前端相关 R 触达对账;Playwright,冒烟红按测试失败处理 [测试]
- **NFR 定责**:spec 每条非功能约束(nfrs)必须三选一指认验证方式,登记到守卫方案——`自动化`(归 L2/L3,如覆盖率)/ `专项工具`(如压测,写明"本批不执行,需时另立任务")/ `评审`(默认,交付确认时人工核对 target);未指认视为缺口 [评审]
- 覆盖率命令(如 `mvn -q verify`)与守卫命令必须登记到 specs/guard-tests-setup.md 的"命令落点"表,实现阶段以该表为准;未登记不认 [测试]
- 覆盖率阈值调整需修订本条并记录到"修订记录",禁止为过门禁临时调低阈值 [评审]
