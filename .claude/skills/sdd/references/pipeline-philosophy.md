# SDD 流水线的编排思想(思想说明,非操作指导)

> 本文件不是操作手册——操作性内容在 references/step1~5 与 scripts。这里只记录管线设计背后的思维方式,供理解与演进时对齐。源自 2026-09-18 ORG-USR 首次全流程实战(10 feature,9h 纯工作时长)后的复盘。

## 一句话

**质量用门禁保证,顺序用数据驱动,并行用契约隔离,异常用红线兜底。** 四件事分属四个机制,不要让任何一个机制越界去干另一件的活。

## 1. 质量与速度是正交的

提速的手段只有一种:消除"等待"。绝不能是"跳过检查"。事件驱动派发改变的是**何时开始**,不改变**怎样才算完**——deliver 闸、独立评审、全量回归在并行模式下与串行模式一字不差。凡是发现"为了并行而放宽判据"的设计,一律是错的。

## 2. 顺序是数据,不是日程

"哪个 feature 先做"不该由人排日程,也不该由批量批次隐含,而是由依赖图数据(feature-list 的 deps)+ 就绪探测器(ready)在每次交付事件后重新计算。推论:

- 批次是派发的产物,不是计划的对象。计划里只有依赖边,没有"第几批"
- 交付一个节点 → 下游立即解锁 → 立即派发。等待只来自数据依赖,不来自流程

## 3. 并行的最小充分条件是"契约隔离",不是"信任"

两个代理能不能同时工作,不看它们多聪明,看三份契约是否齐:

- **物理边界**(worktree / 文件所有权清单 / 独占迁移号)——让踩踏不可能发生
- **协作约定**(共享文件只追加、测试环境各自独立)——让必要的交汇有秩序
- **语义边界**(spec 已裁决的口径,如物理删除特例)——让两个代理对同一规则的理解不会分叉

软隔离(约定+自觉)在没有版本控制的目录里是事故温床(实测:并行撕裂致编译两度打断、误报循环十余轮)。**能用 worktree 就用 worktree;用不了,契约清单必须白纸黑字进派发提示词。**

## 4. 状态只有一份真源,且机器可读

流程推进不靠记忆、不靠聊天记录、不靠人肉判断,靠一个可被脚本随时 interrogate 的状态源(feature-list deps + 各 spec status + Q 登记簿)。`state` 回答"整体到哪了",`ready` 回答"现在能干谁"。任何"我觉得差不多了"都是流程异味。

## 5. 人停在裁决点,不停在信息点上

人的介入是稀缺资源,只花在两类地方:

- **裁决**:互斥口径三选一(如唯一索引×逻辑删除)、详设缺口、红线事项(高阻塞 Q、3 轮不收敛)
- **验收**:确认关口与最终使用

信息同步、状态查询、例行派发全部自动化。委托模式(gate-delegation)是把"确认关口"也交给 AI 的授权机制;授权后 AI 仍须把每个自裁落档(gate-decisions),做到"人不点头,但人可追溯"。

## 6. 事故是资产:每次偏离都要问四问

spec 哪里没写清?上下文缺什么?哪道校验没拦住?哪个手工步骤在重复?——回答落到五类资产(手册/引擎/代理定义/守卫/方法论)的**具体条目**,禁止"要加强"。本次实战的例子:三次「唯一索引×逻辑删除」500 → 三表对账硬规则 + DDL 互斥守卫;一次前端契约断链 → vue-tsc + 浏览器冒烟;一次并行撕裂 → 事件驱动派发 + 契约隔离。**缺陷的终点应当是机制,不是记忆。**

## 7. 效率的极限是依赖图,不是人力

最终决定总时长的是关键路径上的依赖边(共享核心表、真实上下游)。流程优化的全部空间在:压缩关键路径上每个节点的耗时(更好的代理、更准的守卫),以及把非关键路径节点从关键路径上摘下来并行。剩下的串行段是数据本质,接受它。
