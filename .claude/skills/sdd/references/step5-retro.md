# 第⑤步 复盘(收尾检查全绿后)

**这是流程复盘,不是代码评审**——代码的毛病自查和测试抓过了,这里找流程的毛病:spec 为什么没写清、校验为什么没拦住、哪类手工步骤在重复。

## 输入

specs 目录、本批 F 编号(不给就读 feature-list.json 取本批已交付的)、本批 git 范围(可选)。

## 步骤

1. **收集材料**:每个 F 的 spec.json、impl/review/local-test 日志、open-questions 相关 Q(谁登记何时关闭)、命令流水、git log
2. **找偏离**:对照"计划 vs 实际",每条记:计划(引 R/A)、实际(引代码/日志/Q)、原因、类型(更好方案|计划假设有误|遗漏场景|走捷径欠债|其他)。Q、评审清单、测试红单、手工绕过的步骤、重复命令都算偏离来源
3. **分好坏+追根因**:好偏离(spec 假设了不存在的东西/发现更优方案)→计划能力要提升;坏偏离(无视约束/另起炉灶/走捷径/误解需求)→四问:spec 哪里没写清?上下文缺什么?哪道校验没拦住?哪个手工步骤在重复?
4. **打对齐分**:1~10(10=完全按计划;7~9 有偏离但正当;4~6 好坏混杂;1~3 严重跑偏)
5. **归纳模式给建议**:跨 feature 找重复模式(不看孤例),每条落到五类资产之一:
   | 资产 | 建议形态 |
   |---|---|
   | 本 skill 阶段手册 | 手册补一条硬规则/自查项 |
   | 守门引擎 sdd.py / 状态机 sdd_state.py | 加一道检查/state 输出加一个字段 |
   | 代理定义 | spec-implementer / spec-reviewer / local-tester 规则补条 |
   | 守卫测试 | ArchUnit / ESLint 新增守卫类 |
   | 系统分析方法论 | 仅当问题在分析方法本身 |
   每条必须附具体改法(改哪个文件加什么),禁止"要加强""要重视"。
6. **落盘呈报**:写 `<specs>/_work/retro-logs/<日期>-<批次>-retro.md`;呈报对齐分+好坏偏离条数+建议清单

## 纪律

1. 只提不改:建议经用户逐条确认后才动流程文档
2. 要具体:不说"spec 不清",说"spec 没写鉴权模式,导致 F003 登记 2 个 Q"
3. 看模式不看孤例;4. 证据引编号(R/A/Q 或路径),可回查
