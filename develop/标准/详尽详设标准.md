# 详尽详设标准

用户要求“完整/详尽详设”，或需求跨多个数据对象、接口、业务流程和页面时，按本标准编写。目标是让开发和测试能逐项落地；小型变更不必套用完整体量。

PRD 盘点与验收冻结先于详设。运行 `scan-prd <directory>` 建立 PRD 来源单元清单；填写需求台账和验收 Markdown 草稿；完成独立语义复核并关闭差异；将验收 Markdown 标记为“已冻结”；再运行 `check-prd <directory>` 核对来源清单、需求台账、已记录的复核/差异处置和冻结验收点。`check-prd` 是结构与引用门禁，不能证明复核者独立或语义解释正确。

除主 PRD 外，约束、澄清、领域评审、技术选型、API 契约、数据库方言/迁移和实现基线等补充 Markdown，须登记在 `01-需求来源配置.json`，并在需求台账中逐来源单元分类和引用。源码及 SQL 不能只登记目录名；先整理成带精确文件/符号/行号定位的 `implementation_baseline` Markdown，再纳入来源配置。仅为兼容性对照而整理的旧详设摘录，可使用 `legacy_design_reference`；它只能标记为比较参考，不能充当 PRD 规范或独立需求依据。`scan-prd` 不会递归发现未登记的文档或源码。已有旧格式验收清单可通过 `import-acceptance` 转为 develop 草稿；导入会保留原始 AC ID、描述、验证方式和 PRD 锚点，同时标记“待复核”，不能直接当作已冻结基线。转换占位文本（例如“旧版清单未单独列出”“复核时确认”“待业务补充”）必须替换成具体前置条件、操作和可观察结果；校验器会拒绝这些占位文本，即使文档状态被手动改成“已冻结”。

结构化填写以项目目录中的 `03-详细设计.json` 为正本；输出模式和 Markdown 路径由 `03-详设输出.json` 定义，Markdown 由契约模板渲染生成。把所有表、字段、接口、权限矩阵、规则、流程、架构/ER/时序/状态图、页面、依赖与补偿、复用决策、质量决定、项目领域对象和验收点映射完整填入 JSON。项目特有模型（如外部集成、配置键、受管资源、作业或策略）使用 `domain_objects`，通过 `kind` 标记类型、`attributes` 保存本领域字段，使用 `typed_refs`、需求/来源/验收引用闭环；不应为单个 PRD 改核心类型。冻结验收 Markdown 后，按 `python3 /path/to/develop/脚本/develop.py render-design <directory>`、再 `python3 /path/to/develop/脚本/develop.py check-design <directory>` 的顺序渲染并核对详设。不要分别手改 JSON 和 Markdown。

`模板/03-详细设计.json` 提供完整对象级填写骨架；`示例/03-详细设计-输出示例.md` 对照展示每类对象渲染后的表格、小节和链接；`示例/03-详设输出-总分示例.json` 演示总文档、模块分文档、对象归属和验收点分配。JSON 骨架中的 `{{...}}` 是必须替换的填写提示，未清除时校验会拒绝生成。示例中的虚构项目、ID、路径、指标和规则只用于看结构，不可作为真实需求或设计依据。
所有生成的 Markdown 以 `#` 作为不编号的文档标题，从 `##` 起自动生成 `1`、`1.1`、`1.1.1` 层级编号；章节编号属于显示格式，不写进 JSON 正本、模板或文档清单中的章节名。手工添加的详设章节也会在 `render-design` 时统一编号。
`01-产品需求.md` 是用户提供的输入源文档，不要求匹配 develop 的 PRD 模板标题或章节编号；`scan-prd`/`check-prd` 负责扫描并核验其内容指纹。编号与固定章节契约适用于 develop 生成的其他文档，包括冻结验收清单；旧验收导入会在输出时补章节编号。

JSON 中的交叉引用只填写类型明确的稳定对象 ID。渲染时会为对象生成稳定锚点，并将 API、规则、流程、页面、数据字段和覆盖表中的引用转换为本篇或分文档链接；不要存章节编号或手写锚点。对象移动或章节顺序变化时，链接仍通过 ID 定位到当前归属文档和编号。

## 输出模式

每个详设任务都在 `03-详设输出.json` 中明确选一种模式：

- `single`：适合一个紧密内聚的功能模块。输出一份完整详设，所有对象和冻结验收点均在该文档中；无需手工重复维护对象归属清单。
- `total_subdocuments`：适合跨多个模块、领域或独立交付团队的需求。输出总详设和分详设；总文档给全量概览、对象目录与验收追溯，各分文档承载所属对象的完整契约。每份子文档必须登记模块/功能域、对象归属和验收点子集。

模式决策在填写详设前完成并冻结，`mode_reason` 记录本项目依据。综合模块/服务拆分、跨域依赖、单模块复杂度及团队并行方式判断；模块数量仅作权衡输入，不作硬阈值。总分模式先列出总文档和所有模块分文档路径，再开始详设。架构或需求范围改变时先更新模式决策、文档计划和对象归属。

两个模式都由同一份 `03-详细设计.json` 正本渲染。`total.path` 可按项目命名（例如 `m01-base-详细设计.md`）；所有输出使用项目内相对路径，不得逃逸项目目录。分包模式的分文档验收点并集必须与冻结集合完全相等，每个设计对象至少归属一份子文档。多个子文档重复归属同一对象时，在 `shared_object_refs` 显式登记。每份子文档的验收覆盖引用到的对象也必须归属该文档。功能域、约束、假设和范围外事项作为全局上下文保留。所有输出使用清单登记的详设模板 ID/版本，渲染收据绑定模式、配置、基线和全部输出文件哈希。

初始化时可直接声明模式和总文档路径：

```bash
python3 /path/to/develop/脚本/develop.py init /path/to/project --name "M01 基础模块" --design-mode single --design-mode-reason "单模块，单份详设可以完整承载对象与验收追溯" --design-output docs/详细设计/m01-base-详细设计.md
```

总分模式将 `--design-mode` 设为 `total_subdocuments`，随后在 `03-详设输出.json` 中列全总文档和分文档路径、模块归属、设计对象归属及验收点子集。一个对象跨分文档共享时，显式写入 `shared_object_refs`。默认总文档包含全量设计对象与验收追溯；分文档只渲染各自归属对象，跨文档引用自动转为相对链接。

详设校验要求原子验收点清单已冻结，且清单版本、验收点总数、验收点 ID 集合与详设 JSON 完全一致。验收点 ID 沿用 PRD 的稳定格式，不强制 `AC-` 前缀。

## 输入基线

开始前确认并标注来源与版本：

- PRD 来源单元清单（对文档清单登记的主 PRD Markdown 及其显式链接的图片/原型/附件，逐章节/表格/项目记录稳定位置和版本；`scan-prd` 不递归发现未链接的其他文档，范围内的补充文档须合并到主 PRD 后再扫描；缺少可读内容的附件保持未解决并阻止冻结）。
- 详设 JSON `baseline` 必须将冻结验收清单路径/版本/SHA 与 `01-PRD来源清单.json` 的 `source_set_sha256`、`units` 数量绑定；两项来源集字段成对填写，校验时必须与当前清单完全一致。新建详设模板始终包含这两个字段。旧 JSON 若两者都缺失，可按 `LEGACY_UNBOUND` 兼容读取，收据和 `check-design` 必须明确显示“来源集未绑定”，不得标成来源已验证；要取得 `VERIFIED` 状态，须迁移补齐匹配的来源集 SHA 与单元数量。
- PRD 中的围栏代码/图、引用块、HTML 或非标准块须作为带原文和行号的来源单元保留；无法结构化解析的表格作为 opaque source unit 保留并标记审阅提示。每个来源单元仍须分类并纳入独立复核，解析器不得静默丢弃内容。
- 来源分类与需求追溯必须覆盖功能说明、业务规则、实体/字段、校验、操作、权限、流程、UI、质量属性、约束、假设、非目标、风险和开放问题。只有纯背景内容可以标为 `context`，并说明理由；每个需求类来源单元须被至少一条结构化需求引用。评审材料中的每项决议、遗漏和边界发现都须与 PRD 及验收点核对，不能因为有一份评审报告就默认全部合并，也不能只登记少数显眼差异。
- 标题、表头、关联依据和上下游引用等结构/关系来源应标为有理由的 `context`，不能继承邻近内容类别；混合边界、异常和验收章节必须按行按项区分。一个功能块关联多个 REQ 时，按块内显式需求映射与该来源单元语义建立引用，不能将全部 REQ 机械复制到块内每一条，也不能把被提及的依赖 REQ 当作本单元直接覆盖。
- 结构化需求台账，至少包含稳定需求 ID、PRD 原文或可定位来源、规范化需求、强制性、约束/依赖及确认状态。
- 由独立复核者逐来源单元核对 PRD 与需求台账的记录；复核记录必须绑定 PRD SHA、登记来源集 SHA 和来源单元数量，补充来源发生变化就必须重新复核。每个提取差异均有明确处置、理由及复核结果。处置为“待确认”时差异仍未关闭，不能冻结或进入详设。需求 ID 和验收点 ID 保留项目原有稳定格式，不强制 `REQ-`/`AC-` 前缀。
- 对主 PRD 中标注待确认、后续澄清/评审中已有决定的内容，保留原始证据并将现行决定写入需求陈述/约束和差异处置；验收映射应引用受影响的需求。记录了 `review_deltas` 不等于关闭差异，逐项证据、明确决定和独立复核状态全部满足后才能冻结。
- 验收覆盖表中的“覆盖结论/待澄清项”不得保留“待独立复核”“待业务补充”等标记再声明冻结；覆盖关系和逐点语义必须分别核对，组级 ID 对照正确不代表每条 AC 都原子、可执行或结果明确。
- 逐行复核场景映射时，必须比对来源行的前置状态、触发动作和预期结果；只有结果语义一致才可关联 AC。一个来源行拆成多个 AC 时，映射中列出全部拆分点；来自其他章节、决议或实现基线的补充 AC 必须标真实来源，不得伪挂到邻近的 §7.1 场景。
- 一条 AC 只描述一个初始状态和一个可判定结果。成功/拒绝、确认/取消、提交/不提交、有效/无效输入及不同用户状态分别建点；不能把两个独立请求塞进同一 AC 后只断言其中一个结果。导入旧点已拆分时，旧 ID 必须明确为“仅迁移追溯、不可执行”，不得伪装成新的可执行覆盖。
- 前置条件、操作和结果必须足以让开发与测试复现：写明角色和权限、隔离数据及关键字段值、对象关系、初始状态、按钮/API 操作、可观察的页面/响应/持久化变化与清理方式。禁止“准备相关数据”“按步骤执行并检查结果”等泛化模板句。时钟、定时任务、故障注入、短信或加密依赖必须指出可控入口和确定性 fixture。fixture 代码尚未实现时，可把其 test-only 入口、隔离数据、注入点、结果与清理步骤写进 AC 并标记“待实现测试夹具”；不得声称它已存在或已运行。只有业务结果/边界缺少来源，或无法提出可确定且不引入新业务语义的 fixture 步骤时，才列为未决并阻止冻结。
- 对 PRD 中有明确列结构的验收场景表，须在“PRD验收场景映射”表中逐 source unit 关联一个或多个 AC ID，并验证不存在漏映射、悬空 AC/REQ 或不一致的需求归属；将场景摘要到 FUN 或 REQ 的组级映射不能代替逐场景追溯。映射说明为“候选待复核”或“未映射”时不得冻结。
- 验收草稿可以新增/修改点数，同时保留上一冻结版本的 version/count 作为历史基线；只有 freeze gate 才要求清单版本、冻结版本、声明点数和冻结点数一致并将状态改为“已冻结”。
- 已确认的 PRD 与验收 Markdown（冻结版本、验收点总数）。验收 Markdown 中全部原子验收点构成详设覆盖率的完整分母。
- 技术、业务、安全、客户端和兼容约束。
- 项目现状：已有数据表、接口、页面/组件、权限模型、依赖和编码约定。
- 必要的原型、UI 规范、外部接口和数据库方言事实。

事实来源冲突或输入缺失时，列为待确认项并说明影响范围。未解决的强制需求或任何尚未关闭的提取差异（包括已有“待确认”处置的差异）都会阻止验收 Markdown 冻结，也阻止进入详设。只有有依据的已关闭处置才允许继续。不得为了填满模板而臆造表、字段、接口、页面、权限、错误码、性能指标或实现基线。

## 逐项展开要求

### 范围与方案

- 写清功能域、目标、本次范围、Non-Goals、假设和技术约束。
- 说明模块边界、依赖方向和关键方案选择及理由。
- 可给出数量摘要和导航索引，但数量必须能从正文清单复核。

### 术语、权限和架构图

- 术语表逐项定义项目内有歧义或跨团队复用的概念，并标注来源。
- 权限矩阵按角色/主体、资源、操作、权限码和数据范围列全，链接到页面、接口和业务规则；同一权限码应有单一事实源。
- ER、系统架构、时序、状态和关键决策图使用可维护的源码，逐图登记稳定 ID、图类型、引用对象和来源；图中对象必须能与字段/接口/流程契约对账。

### 表与数据

- 每张表单独列名、用途、关系、主键、外键、唯一约束和索引。
- 每个字段列名称、类型/长度、可空/必填、默认值、约束、业务含义和来源；不只写“关键字段”。
- 说明枚举、状态变化、逻辑删除、版本/并发、时间语义及数据生命周期中适用的部分。
- 对非显然的字段类型/长度、索引、唯一键、删除语义和迁移方案写决策理由；适用时说明 DDL、回填、兼容和数据库方言影响。
- 表关系复杂时提供 ER 图；图与字段表保持一致。

### 接口

- 提供全量接口索引：稳定 ID、方法、路径、用途、权限、请求/响应字段数量或详设位置。
- 每个端点单独成节，注明认证授权、功能、输入输出、关联业务规则和验收点。
- 请求字段逐项注明类型/格式、必填条件、校验、来源和敏感信息处理；响应字段逐项注明类型/格式、是否恒出、取值规则、来源和脱敏。
- 写清成功/失败语义、错误码、幂等、事务、并发、超时和降级要求；不适用项说明理由。
- 一个端点不能借用另一个端点的字段定义；示例报文不能替代字段契约。

### 权限、规则与关键流程

- 权限模型适用时，分别对账页面、操作、接口及数据范围；权限码使用一个明确事实源。
- 业务规则使用稳定 ID，逐条写适用对象、条件、结果、错误语义、来源需求和验收点。
- 关键流程逐个写触发者、触发条件、前置校验、处理步骤、状态迁移、事务/并发/幂等、结果、失败/回滚/重试路径。
- 跨服务、异步、状态迁移或失败补偿较复杂时提供时序图/状态图，并保留完整文字说明。

### 前端页面与交互

- 列出全部顶级页面、路由、组件、权限，以及业务相关弹窗/抽屉和挂载页面。
- 逐页说明布局/区域、控件、校验、按钮/行操作、调用接口、规则和数据映射。
- 覆盖加载、空数据、提交中、成功、失败、禁用和权限不足等适用状态。
- 对需要自动化定位的交互使用稳定测试锚点，并关联验收点/测试用例。

### 横向质量与设计决定

- 按实际风险说明安全、异常、性能/容量、兼容、日志/审计、外部依赖、配置、恢复和降级。
- 有明确指标时写数值、口径和测量条件；没有依据时标为待确认，不编造目标。
- 优先复用现有组件和标准能力；新增依赖、公共组件或架构扩展记录选择项、理由、影响和替代方案。
- 迁移、种子数据、外部集成、计划任务或受管资源适用时，列清责任、失败处理和验证办法。
- 依赖登记内部/外部方向、契约或版本、责任方、超时/失败语义、降级/补偿路径及影响对象。
- 复用决策逐项说明复用对象、接入方式、扩展边界、理由和替代方案；新建公共组件/服务也要记录决策。

## 覆盖与复核

- 冻结验收 Markdown 是详设覆盖率基线；其中每个原子验收点都应追溯到一个或多个需求台账 ID，再映射到具体数据、接口、规则、流程、页面或质量约束，并关联验证方式。设计覆盖率为 100%。
- 独立语义复核核对 PRD 来源单元、结构化需求台账、每项提取差异处置、验收点拆分，以及“需求 → AC → 设计对象”链路；结构化字段、ID 集合、引用和 Markdown/JSON 一致性由机械检查核对。机械检查 PASS 不代表语义正确、需求完整或设计合理，语义评审须单独作出结论。
- 不适用的设计类型写明原因；不能留空，也不能以“无”掩盖未知。
- 为适用的表、字段、接口、规则、流程、页面和验收点建立全量索引或计数。摘要数字必须与逐项正文相符。
- 评审按全量清单核对，而非只抽查样例；检查 PRD、数据、接口、流程、页面、权限和测试之间是否一致。
- 每个问题记录精确位置、触发场景、影响、建议和复审证据。阻断问题关闭后才进入开发；零发现时留下实际检查范围与证据。

## 详尽度与体量

对小型变更只展开受影响对象，并明确不适用项；对完整模块逐项展开所有适用对象。详尽度由需求和风险决定，不以页数、表数或图数为目标。文档确需拆分时使用可定位的章节锚点，并维护统一的验收点追溯和全量目录。
