# 开发交付流程

按 **PRD → 详设 → 开发 → 测试验收 → 复盘** 推进。交付文档使用 Markdown；固定章节由 `契约/文档清单.json` 定义，`模板/` 负责内容引导，`脚本/` 负责生成和格式校验。

## 流程

1. **盘点需求及技术来源**：运行 `scan-prd <directory>`，扫描登记的主 PRD、其中显式链接的图片/原型/附件，以及 `01-需求来源配置.json` 明确登记的补充 Markdown。补充来源按技术约束、澄清、领域评审、架构决策、API/数据库契约、实现基线等角色记录路径、哈希和来源单元。未登记的其他文档不会自动发现；属于本次事实来源时先登记再扫描。API 路径、数据库结构等实施事实若来自源码，先整理成带代码路径、符号/行号依据的 `implementation_baseline` Markdown，不凭空从 PRD 推断。
2. **提取需求并建立台账**：从全部已登记来源单元提取需求，整理结构化需求台账，保留需求 ID、原文/来源定位、规范化表述、是否强制、约束/依赖和待确认状态；同步起草验收 Markdown。已有非 develop 格式的冻结验收清单，可用 `import-acceptance <directory> --source <path> --requirements-map <path>` 导入；适配器保留原 AC ID、描述、验证方式和 PRD 锚点，需求映射由显式映射 JSON 提供。导入状态为“待复核”，需复核映射、原子性、前置条件/操作/结果并独立冻结，才能继续。导入生成的“旧版清单未单独列出”“复核时确认”“待业务补充”等占位文本，即使手动改成冻结状态，机械校验也会拒绝；必须将其改成可执行、可观察的验收条件。
3. **独立复核并冻结验收基线**：由未负责初次提取的人逐来源单元复核 PRD 与台账；复核记录必须绑定主 PRD 哈希、完整登记来源集指纹和来源单元数量，任何补充来源变化都要重新审阅；逐条记录提取差异、处置、理由和复核结果。分类不能为省事而批量标成 `context`：每个功能说明、业务规则、字段/校验行、流程、权限、质量要求和待确认项都要分类，并连接到相应需求 ID；只有背景信息可标 `context`，且需给出覆盖/不重复等理由。标题和表头是结构单元，不能继承相邻内容的分类；混合边界、异常和验收章节必须按每条来源内容分类，不能按章节名批量套标签。一个功能块关联多个需求时，以块内的明确需求/依据行及具体来源语义确定映射；引用其他功能或需求的依赖关系不能自动算作本条的直接需求覆盖。补充澄清、PRD 评审与历史验收须逐项核对其中的决议/发现，新增或改变的决定都记入 `review_deltas`，并更新需求约束、开放问题和验收映射；不能只登记文件或只挑少数差异。差异须引用来源证据，处置不得仍为“待确认”。仍未解决的强制需求或提取差异会阻止冻结，也不得开始详设。关闭差异后，将已确认需求拆成可独立判断的原子验收点；每点有稳定 ID、需求来源、前置条件/操作/可观察结果和验证方式。对于 PRD 中表格化的验收场景，还要在“PRD验收场景映射”中逐来源单元链接一个或多个 AC；按功能组或 REQ 的汇总映射不能代替逐场景对应。验收 Markdown 是冻结的验收基线，也是详设覆盖率的完整分母；需求覆盖表和场景映射不能保留“待独立复核”“未映射”等未关闭标记。将其标记为“已冻结”后，运行 `check-prd <directory>` 校验来源清单、需求台账、复核记录、冻结状态和逐场景验收映射。`check-prd` 检查记录和结构，不证明复核者独立或业务语义正确；这些由人工语义评审确认。

   - **逐行语义映射**：对照每个来源行的前置状态、触发动作和预期结果，只链接结果语义确实一致的 AC；不得按相邻行、功能编号、REQ 组或同一页面机械挂接。一个来源行拆成多个 AC 时，映射行列出全部拆分点；某个 AC 来自 §9、决议或实现基线时，列出其真实来源并说明为何不属于 §7.1 场景表，不要把它标成“无来源”。
   - **原子性**：一条 AC 只验证一个起始状态和一个可判定结果。成功与拒绝、确认与取消、保存与不保存、有效与无效输入、多个独立请求或不同用户状态应拆成不同 AC；每个分支都要有对应来源和可观察断言。历史导入点若已由新 AC 拆开，必须显式标成“仅迁移追溯、不可执行”，不得继续当作多个行为的可执行覆盖点。
   - **可复跑性**：每条 AC 明确角色/权限、隔离数据、关键字段值、对象关系、初始状态、具体操作、结果检查位置和清理边界。不要使用“准备相关数据”“按步骤执行”“检查页面/持久化结果”等泛化句。依赖时钟、作业、故障注入、短信/加密等环境的场景，要写出可控入口和确定性 fixture。设计阶段可以定义尚待开发的 test-only trigger、clock、repository fault injector、浏览器路由拦截或固定测试密钥；必须标为“待实现测试夹具”，并写明其隔离范围，不能说成当前已存在。只有 PRD/已裁决来源没有确定业务结果，或连可确定的 fixture 步骤也无法从已知行为设计出来时，才记为业务未决并阻止冻结。
4. **编写详设**：详设覆盖范围与约束，以及四类设计主体：
   - **表**：逐表写清字段、类型、约束、默认值、关系、主键和索引。
   - **接口**：逐功能/API写清方法、路径、权限、请求/响应字段、校验和错误语义。
   - **关键流程**：说明触发者、前置条件、步骤、状态变化、失败分支，以及适用的事务和并发处理。
   - **前端页面**：列出页面、弹窗/抽屉、权限、控件和操作，并映射到接口与规则。
   - **横向要求**：以冻结的验收 Markdown 中全部原子验收点为完整分母，逐条保持“PRD 需求 → 验收点（AC）→ 设计对象”的可追溯关系，并映射到验收/测试方式，设计覆盖率为 100%；安全、性能、兼容、依赖和复用按范围说明，不适用时给出理由。每个重点不要用“同上”或样例代替契约。
   - 用户要求“完整/详尽详设”或需求涉及多个数据域、接口、流程或页面时，先读 `标准/详尽详设标准.md` 和 `示例/03-详细设计-输出示例.md`，对照 JSON 样例填写每种设计对象，再逐项展开真实完整清单。示例只展示输出形态，不提供项目事实，不得照搬示例数据。
   - 其他文档模板的填写效果见 `示例/示例索引.md`；按需查看 PRD、需求提取、验收点、评审、开发、测试验收和复盘示例。示例中的项目事实、路径、来源 ID、哈希及结果均为虚构，不能作为项目证据或直接用于冻结/验收。项目基线证据示例用于展示源码定位格式，使用时必须替换为目标仓库的真实定位。
   - 验收基线冻结后，依次运行 `python3 /path/to/develop/脚本/develop.py render-design <directory>` 和 `python3 /path/to/develop/脚本/develop.py check-design <directory>`。JSON/schema、验收集合、需求→AC→设计对象追溯、跨对象引用、覆盖率或 Markdown 对账失败时不得放行。
   - **模式决策（详设开始前冻结）**：结合模块/服务拆分、跨域依赖、单模块独立演进需求和团队并行方式，先决定 `single` 或 `total_subdocuments`，把选择依据写进 `03-详设输出.json` 的 `mode_reason`。一个模块或简单功能、单份文档能清楚承载全部契约时选 `single`；跨多个模块/服务、复杂度需要独立演进或多团队并行时评估 `total_subdocuments`。模块数量只是权衡输入，不作硬阈值。总分模式要先列完整的总文档和模块文档路径，再开始写详设；模式随架构或范围改变时先更新决策和输出配置。
   - 单份模式将全量设计对象和验收点写入一个 JSON 正本并生成一个 Markdown；总分模式额外为每份子文档声明对象归属和验收点子集，生成总详设及各分详设。`init` 默认单份；可用 `--design-mode total_subdocuments` 与 `--design-mode-reason "..."` 预填冻结决策。总文档路径可配置，例如 `--design-output docs/详细设计/m01-base-详细设计.md`。两种模式的所有 Markdown 输出都纳入同一份生成收据。
   - **全量详设内容**：除表、字段、接口、规则、流程、页面和质量决定外，按需逐项填写术语、权限矩阵、ER/架构/时序/状态图、内外部依赖、失败补偿、组件与公共能力复用决策；以稳定 ID 连回需求、来源、验收点和设计对象。适用类别不得用摘要代替清单；无适用对象时说明原因。
   - 在 `03-详设输出.json` 中设置模式。`single` 自动从 JSON 正本和冻结基线推导总文档的对象/验收清单；`total_subdocuments` 必须登记总文档及至少一份子文档，子文档验收点并集须等于冻结集合，每个设计对象须归属至少一个子文档，共享对象显式登记。覆盖行引用的对象必须在相应子文档内闭合。约束、假设和范围外事项作为全局上下文保留。所有输出路径必须是项目内唯一的 Markdown 相对路径，并使用清单登记的详设模板版本。
5. **评审详设并放行**：按范围选择架构、前后端、数据、安全和测试等相关视角，核对需求覆盖、四类设计之间的一致性、可实现性和可测试性，并走查关键正常、边界、失败和权限场景。详尽模式逐项清点源需求和设计对象，不只抽查样例。记录问题位置、触发场景、影响、修订建议和复审结果；阻断项关闭后再进入开发，重要遗留项须记录接受理由和后续措施。零发现也要记录检查范围与依据。机械检查 PASS 只说明结构与引用满足可检查条件，不代表需求提取语义正确、需求已完整、设计可实现或方案合理。评审者必须独立核对 PRD 原文、结构化需求台账、差异处置记录、冻结验收 Markdown 与详设；语义问题未关闭时，即使机械检查 PASS 也不得放行。
6. **开发**：先按目标仓库现有约定创建或更新 OpenSpec change，把相关验收点 ID 纳入规格/任务追溯；完成 proposal/spec/design/tasks 等适用产物并校验，再按任务切片实现。每个切片遵循 TDD：先写失败测试，再实现到通过，最后重构并重跑相关测试。需求或设计变化时先更新 OpenSpec 和受影响的验收点映射。
7. **测试验收**：以冻结验收点清单设计测试；每个验收点至少关联一个测试用例，一个验收点可拆成多个测试覆盖不同场景。记录用例 ID、执行命令、结果、环境和证据；结论区分通过、失败、阻塞和未验证，没有证据的项不得写成通过。
8. **复盘**：总结目标达成情况、有效做法、问题和可执行改进项；将可复用经验写清适用条件。

OpenSpec 的目录、命令和产物格式以目标仓库现有配置及已安装工具为准，不自行臆造格式。目标仓库未配置 OpenSpec 时，说明阻塞点并先完成不依赖它的梳理工作。

## 文档

**模板与 JSON 契约必须和示例同步维护。** 新增、修改或删除 `模板/` 中的 JSON/Markdown 模板，或 `契约/` 中的 JSON 结构契约时，必须在同一变更中检查并更新所有受影响的输出示例及 `示例/示例索引.md`；尚无对应示例时新增示例。同步核对必填字段、枚举、约束、章节和追溯关系，避免模板/契约与示例展示不一致。

`01-产品需求.md` 是用户提供的输入源文档，可以使用任意标题和章节编号；`scan-prd` 与 `check-prd` 按内容及来源指纹核验，不强制套 develop PRD 模板。编号和固定章节契约适用于 develop 生成的其他文档，包括冻结验收清单；`import-acceptance` 导入旧清单时会补章节编号。

```bash
python3 /path/to/develop/脚本/develop.py init /path/to/project --name "M01 基础模块" --design-mode single --design-mode-reason "单一基础能力模块，完整对象和追溯可由一份详设承载" --design-output docs/详细设计/m01-base-详细设计.md
# 在 01-需求来源配置.json 登记同项目内的约束、澄清、评审、API/数据库契约和实现基线 Markdown。
python3 /path/to/develop/脚本/develop.py scan-prd /path/to/project
# 旧验收清单可先导入为待复核草稿，再映射需求并审阅。
python3 /path/to/develop/脚本/develop.py import-acceptance /path/to/project --source /path/to/project/docs/需求/现有验收清单.md
# 完成需求台账/独立语义复核、关闭差异并冻结验收 Markdown 后，执行机械检查。
python3 /path/to/develop/脚本/develop.py check-prd /path/to/project
# 验收 Markdown 已冻结、详设 JSON 填写完成后再执行。
python3 /path/to/develop/脚本/develop.py render-design /path/to/project
python3 /path/to/develop/脚本/develop.py check-design /path/to/project
# 通用文档集合检查；它不能替代以上 PRD 和详设检查。
python3 /path/to/develop/脚本/develop.py check /path/to/project
```

先填结构化详设 JSON，再运行 `render-design` 更新 Markdown；评审前要求 `check-design` 通过。`check` 只检查文档集合和固定章节；`check-design` 检查详设填写完整、引用闭环、验收点全覆盖及文档/JSON 一致性。机器校验不替代设计判断、需求评审或测试验收。
